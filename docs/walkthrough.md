# 처음부터 읽는 안내서

이 저장소를 처음 보는 사람이 "무슨 프로젝트이고, 어떤 순서로 뭘 했고,
왜 하필 그 도구를 썼는지" 를 한 번에 따라올 수 있게 쓴 글이다.

각 단계의 상세한 숫자와 원문 로그는 [`docs/labs/`](labs/) 에 10편으로 나눠 있다.
여기서는 **흐름과 의사결정 근거**만 다룬다.

---

## 1. 무엇을 만들었나

티켓 예약 API 라우트 **하나**를 만들어 놓고, 그 앞뒤 계층을 하나씩 일부러 터뜨렸다.
로드밸런서 → 앱 CPU → 커넥션 풀 → DB 프록시 → 캐시 → 큐 순서로 내려간다.

목표는 처음에 못 박고 시작했다.

```
1,000 RPS 지속 · p99 < 200ms · 에러율 < 0.1%
```

10단계 끝에 넘겼다.

|  | Phase 01 (튜닝 전) | Phase 09 (최종) |
|---|---|---|
| 처리량 | 2,000 RPS 에서 붕괴 | 1,005 RPS · 10분 지속 |
| p99 | — | 105ms |
| 에러율 | — | 0.05% |

**결과물은 코드가 아니라 측정 기록이다.** 앱 코드는 부하를 걸 대상이 필요해서 만든 것에 가깝다.

### 왜 라우트가 하나뿐인가

이게 이 프로젝트의 첫 번째 설계 결정이고, 나머지가 전부 여기서 나온다.

라우트를 여러 개 두면 어떤 계층이 터졌을 때 **어느 라우트 때문인지 분리가 안 된다.**
라우트가 하나면 "이번에 바뀐 건 방금 내가 만진 계층 하나뿐" 이 보장된다.
대신 그 하나를 최대한 잔인하게 골랐다.

```sql
BEGIN
  SELECT ... FROM idempotency WHERE key = $1     -- 멱등키 조회
  SELECT ... FROM events WHERE id = $1 FOR UPDATE -- 행 잠금 (경합 지점)
  UPDATE events SET remaining = remaining - 1     -- 재고 차감
  INSERT INTO reservations ...                    -- 예약 생성
COMMIT
```

트랜잭션 하나 안에서 DB 왕복 5번, 그 사이 내내 커넥션 1개를 붙잡고,
같은 이벤트 행을 두고 모든 요청이 줄을 선다. **락 경합 · 커넥션 점유 · 재고 정합성**이
한 라우트에 다 들어 있어서, 계층을 바꿀 때마다 어디가 반응하는지 볼 수 있다.

그리고 티켓 예약은 **초과 판매가 절대 나면 안 되는** 도메인이라,
뒤에서 캐시와 큐를 붙일 때 "빠르게 만드는 것" 과 "틀리지 않는 것" 이 정면으로 부딪힌다.
이 충돌이 Phase 07~08 의 핵심이 된다.

## 2. 일하는 규칙 — 도구보다 먼저 정한 것

측정 프로젝트는 규칙이 없으면 결과가 전부 자기합리화가 된다. 네 가지를 먼저 정했다.
([`docs/conventions.md`](conventions.md))

**① 한 번에 한 계층만 건드린다.**
두 개를 같이 바꾸면 좋아졌을 때 어느 쪽 공인지 영원히 모른다.
그래서 Phase 02 에서 TLS 를 재고 나서 Phase 03 에서는 TLS 를 아예 껐다 — 변수에서 뺀 것이다.

**② 가설은 실험 전에 쓰고, 나중에 고치지 않는다.**
사람은 결과를 보고 나면 "나는 원래 그럴 줄 알았다" 로 기억을 고쳐 쓴다.
틀린 가설이 문서에 그대로 남아 있어야 그게 왜 틀렸는지가 배움이 된다.
실제로 Phase 01 의 주 가설(H1)은 **틀렸고**, 그 틀린 기록이 프로젝트 전체 방향을 정했다.

**③ 재기 전에는 숫자를 예측하지 않는다.**
"대략 30% 개선될 것" 같은 문장을 쓰면 결과가 그 근처로 보이기 시작한다.
방향(오른다/내린다)까지만 예측하고 배수는 재서 채운다.

**④ 부하 생성기부터 의심한다.**
서버가 1,000 RPS 에서 막히는 게 아니라 **k6 가 1,000 RPS 밖에 못 쏘는 것**일 수 있다.
그래서 매 측정 전에 `make sanity` — DB 를 안 타는 빈 라우트로 목표의 3~5배가 나오는지 먼저 본다.
이게 안 나오면 그날 잰 숫자는 서버가 아니라 노트북을 잰 것이다.

## 3. 도구를 왜 이걸로 골랐나

각 도구는 "유명해서" 가 아니라 **이 실험에서 뭘 관찰해야 하는가**에 맞춰 골랐다.

| 도구 | 대안 | 이걸 고른 이유 |
|---|---|---|
| **k6** | ab, wrk, JMeter, Locust | **open model(도착률 고정)을 지원한다.** 아래에서 따로 설명 |
| **Fastify** | Express | 오버헤드가 작아 앱 프레임워크가 병목이 되지 않는다. 실측 요청당 52µs |
| **Drizzle ORM** | Prisma, TypeORM | **풀을 내가 직접 쥔다.** 아래에서 따로 설명 |
| **node-postgres** | postgres.js | 풀 이벤트(`connect`/`acquire`/`remove`)를 노출해서 지표로 뽑을 수 있다 |
| **Postgres** | MySQL | **커넥션 = OS 프로세스** 라 커넥션 비용이 메모리로 눈에 보인다. Phase 05 의 전제 |
| **HAProxy** | nginx | **오픈소스판에 액티브 헬스체크가 있다.** 아래에서 따로 설명 |
| **nginx** | — | Phase 02 의 TLS 종료 전용. LB 역할은 안 맡겼다 |
| **PgBouncer** | RDS Proxy, pgpool-II | 트랜잭션 풀링이 가볍고, `SHOW POOLS` 로 내부 상태를 직접 읽을 수 있다 |
| **Redis** | Memcached | `DECR` 이 원자적이다. 재고 선점 게이트가 이거 하나로 성립한다 |
| **RabbitMQ** | Kafka, SQS | **이 실험에 필요한 건 순서 보장이 아니라 재시도/DLQ** 다. 아래에서 따로 설명 |
| **Prometheus + Grafana** | Datadog 등 SaaS | 로컬에서 닫히고, 지표 정의를 내가 다 쓴다. 카디널리티 사고까지 직접 겪는 게 목적이었다 |
| **colima** | Docker Desktop | VM 자원(CPU/메모리)을 명시적으로 고정할 수 있다. 재현성의 전제 |

### k6 — open model 때문에 골랐다

부하 생성기는 크게 두 가지로 나뉜다.

- **closed model** (VU 기반): 가상 사용자 N명이 "응답 받으면 다음 요청" 을 반복한다.
- **open model** (도착률 기반): 응답과 무관하게 초당 N건씩 계속 도착한다.

closed model 에는 함정이 있다. **서버가 느려지면 부하도 같이 줄어든다.**
응답이 안 오니 다음 요청도 안 나가고, 그래서 서버가 가장 괴로운 구간이 표본에서 빠진다.
결과적으로 **망가진 서버가 실제보다 좋아 보인다.**

실제 트래픽은 그렇게 동작하지 않는다. 서버가 느리든 말든 사용자는 계속 들어온다.
k6 의 `constant-arrival-rate` 는 이 진짜 모양을 재현한다.
Phase 01 에서 같은 서버를 두 모델로 재서 이 차이를 직접 확인했고(가설 H3),
그 뒤로는 전부 open model 로 갔다.

### Drizzle — 풀을 감추지 않아서 골랐다

Prisma 는 쿼리 엔진(Rust 바이너리)이 커넥션을 관리한다. 편하지만
**이 프로젝트에서 재야 할 것이 그 안에 숨는다** — 풀 대기 시간, 활성/유휴 커넥션 수, 획득 실패.

Drizzle 은 그냥 SQL 빌더라서 밑에 있는 `pg.Pool` 이 내 것이다.
그래서 이런 지표를 직접 만들 수 있었고, Phase 05 의 관찰이 전부 여기에 얹혀 있다.

```js
db_pool_connections{state="active"|"idle"|"waiting"}
db_pool_acquire_wait_seconds
```

### HAProxy — 오픈소스판에 액티브 헬스체크가 있어서

Phase 03 의 실험 절반이 **"죽은 백엔드를 언제 알아채는가"** 다.
그런데 오픈소스 nginx 에는 능동 헬스체크가 없다.
`interval`/`timeout`/`threshold` 를 가진 주기적 확인은 상용판(nginx Plus) 기능이고,
오픈소스는 실제 요청이 실패해야 반응하는 패시브 방식(`max_fails`)만 지원한다.

패시브만으로는 "감지까지 몇 초" 를 잴 수가 없다 — 감지하려면 사용자 요청이 먼저 죽어야 하니까.
HAProxy 는 오픈소스판에 `check inter 2s fall 3 rise 2` 가 다 들어 있다.
Phase 09 의 "앱 1대를 죽였는데 18.3만 요청 중 실패 2건" 은 이 설정 덕분이다.

### RabbitMQ — Kafka 가 아닌 이유

Kafka 는 **순서와 대용량 로그**에 최적화돼 있다. 파티션 단위 순서 보장, 디스크 순차 쓰기.

그런데 이 프로젝트에서 큐에 요구한 건 그게 아니었다.

- 실패한 메시지를 **몇 초 뒤에 다시** 시도 → RabbitMQ 는 `x-message-ttl` + dead-letter 로 한 줄
- 계속 실패하면 **DLQ 로 격리** → RabbitMQ 는 큐 인자로 선언만 하면 끝
- **컨슈머 랙을 실시간으로 관찰** → 관리 API 가 큐 depth 를 바로 준다

순서는 애초에 필요 없었다. 재고 차감은 `remaining = remaining - 1` 이라 교환법칙이 성립하고,
정합성은 순서가 아니라 **Redis DECR 게이트와 UNIQUE 제약**으로 지킨다.
필요 없는 보장에 운영 복잡도를 낼 이유가 없었다.

## 4. 단계별로 무엇을 물었고 무엇을 알았나

각 단계는 앞 단계의 결론을 입력으로 받는다. 순서가 임의가 아니다.

### Phase 01 · 취약 기준선

> 아무것도 튜닝하지 않았을 때 이 서버의 좌표는 어디인가?

여기서 SLO 를 달성할 생각은 없었다. **비교 대상을 만드는 게 목적**이다.

가설은 "커넥션 풀(기본 10개)이 먼저 마른다" 였다. DB 왕복 5회짜리 트랜잭션이
커넥션을 오래 붙잡으니 리틀의 법칙상 풀이 천장일 거라고 봤다.

**틀렸다.** 풀이 마르기 전에 **Node 의 단일 JS 스레드 CPU** 가 먼저 1.0 코어에 붙었다.
100~1,200 RPS 구간을 선형 회귀하니 `CPU = 0.068 + 0.000518 × RPS` 가 나왔다.
요청당 518µs. 천장은 약 2,000 RPS.

이 틀린 가설이 프로젝트의 방향을 정했다. **병목은 CPU 다.**
그래서 Phase 02(TLS 도 그 CPU 를 먹는다), Phase 03(그럼 앱을 늘리자), Phase 04(CPU 자체를 태워보자)
가 차례로 나온다.

### Phase 02 · TLS 핸드쉐이크

> HTTPS 는 그 CPU 예산을 얼마나 가져가나?

핸드쉐이크의 비대칭키 연산은 앱과 **같은 스레드**에서 돈다. 그래서 경쟁 관계다.

keep-alive 가 살아 있으면 핸드쉐이크는 커넥션당 한 번뿐이라 차이가 거의 없었다.
**끄자 요청마다 핸드쉐이크가 발생하면서 천장이 절반으로 내려갔다.**

해법은 TLS 를 nginx 로 옮기는 것. 합계 CPU 는 오히려 늘지만 이득인 이유가 핵심이다 —
**앱은 코어를 하나밖에 못 쓰고 nginx 는 여러 개를 쓴다.** 병목 자원이 서로 다르다.

프록시 홉 자체의 비용을 빼려고 "nginx 평문 통과" 를 따로 쟀다.
이걸 안 빼면 TLS 비용이 과대평가된다.

### Phase 03 · 로드밸런서

> 앱을 3대로 늘리면 병목은 어디로 옮겨가나?

LB 는 CPU 가 아니라 **네트워크 자원**(커넥션 슬롯, 파일 디스크립터, 임시 포트, accept 큐)에서
터지는 계층이다. 그래서 그것들을 하나씩 좁혀 봤다.

가장 크게 나온 두 가지.

- **least-conn 대 round-robin**: 느린 백엔드가 1대 섞이면 round-robin 은 계속 그쪽으로 보낸다.
  least-conn 은 알아서 피한다. **p99 차이 7.4배.**
- **drain 유무**: graceful shutdown 없이 인스턴스를 죽이면 헬스체크가 알아챌 때까지 죽은 구간이 생긴다.
  **p99 차이 45배.** 배포 방식이 아키텍처만큼 중요하다는 게 여기서 나온다.

### Phase 04 · 앱서버의 물리적 한계

> 요청당 CPU 를 인위적으로 늘리면 천장은 예측대로 내려가나?

Phase 01 에서 세운 모델 `천장 = CPU 상한 ÷ 요청당 CPU` 를 검증했다.
요청당 10ms 를 태우니 **100.20 RPS**, 30ms 를 태우니 **34.30 RPS**.
이론값 `1000/X` 와 오차 3% 안이었다. 모델이 맞았다.

여기서 두 가지를 배웠다.

**스레드풀로 옮겨도 처리량은 안 는다.** 같은 연산을 워커 스레드로 보내니
이벤트 루프 지연은 0이 됐는데 처리량은 **34.3 → 24.1 RPS 로 떨어졌다.**
일을 다른 데로 보낸 것이지 없앤 게 아니고, 오히려 전달 비용이 붙었다.
CPU 병목은 CPU 를 줄여야 풀린다.

**빨리 거절하는 편이 낫다.** load shedding 을 넣으니 실패율이 **9.6% → 68.7%** 로 뛰었다.
그런데 성공 처리량은 그대로면서 **p50 이 21,914ms → 493ms** 가 됐다.
실패율이 7배 는 게 개선이라는 게 이상하게 들리지만,
21초 기다리다 이미 떠난 사용자를 위해 서버가 계속 일하는 것보다는 낫다.
**응답하지 않는 것도 실패고, 늦게 응답하는 것도 실패다.**

### Phase 05 · DB 커넥션 풀

> 이제 앱 CPU 는 수평 확장으로 풀린다. 다음 벽은 DB 인가?

Postgres 는 **커넥션 하나가 OS 프로세스 하나**다. 그래서 커넥션은 공짜가 아니다.
실측하니 커넥션당 **3.1MB** 가 선형으로 늘었다.

(여기서 한 번 틀렸다. 처음엔 `VmRSS` 를 합산해서 커넥션당 30MB 가 나왔는데,
`VmRSS` 는 공유 메모리를 프로세스마다 중복으로 센다. 사적 메모리인 `RssAnon` 으로 바꾸니 3.1MB.)

이 단계의 제일 큰 교훈은 따로 있다.

**"풀이 마른다" 는 증상이지 원인이 아니다.**
200만 행짜리 순차 스캔 쿼리 **하나**가 커넥션 30개를 전부 붙잡아서 실패율 85.8% 를 만들었다.
풀 크기는 손도 안 대고 **인덱스 하나**를 추가했더니 처리량 7.9배, 실패율 0%.
풀을 키우는 건 대개 증상 완화고, 원인은 그 커넥션을 오래 잡는 쿼리 쪽에 있다.

### Phase 06 · DB 프록시 (PgBouncer)

> 앱에 이미 풀이 있는데 왜 프록시를 또 두나?

이유는 **앱 풀은 앱마다 따로 놀기 때문**이다. 앱 6대 × 풀 20 = DB 는 120개를 받아야 한다.
앱을 늘릴 때마다 DB 커넥션이 곱셈으로 는다.

실제로 앱을 3→6대로 늘려서 확인했다.

- **직결**: 커넥션 상한 98개에 닿고 `too_many_clients` 47건
- **PgBouncer 경유**: DB 가 받는 커넥션 **22개로 고정**, DB 메모리 53% 절감

핵심은 **transaction 모드**다. 커넥션을 세션 단위가 아니라 트랜잭션 단위로 빌려준다.
트랜잭션이 끝나면 즉시 반납되니 실제 동시 트랜잭션 수만큼만 있으면 된다.
대신 세션 상태(임시 테이블, 세션 레벨 advisory lock, 이름 있는 prepared statement)를
못 쓴다. 그래서 코드에서 `pg_advisory_xact_lock` 처럼 **트랜잭션 범위** 함수로 바꿔야 했다.

서버리스에서 이게 사실상 필수인 이유도 같다 — 함수 인스턴스가 수백 개로 늘면
각자 커넥션을 여는데, DB 는 그걸 감당할 수 없다.

### Phase 07 · 캐시

> DB 를 아예 안 치게 만들 수 있나?

시작하자마자 문제가 있었다. **캐시할 게 없었다.**
`total_seats` 가 1억이라 아무것도 매진되지 않았고, 그래서 모든 요청이 쓰기였다.
재고를 희소하게 바꾸는 `db/reset-scarce.sql` 을 먼저 만들었다.
읽기 트래픽(매진 조회)이 생겨야 캐시가 의미가 있다.

키 분포도 **Zipf** 로 바꿨다. 균등 분포에서는 핫키가 안 생기는데,
실제 티켓팅은 인기 공연 몇 개에 트래픽이 몰린다.

결과.

- **DB 접촉 71% 감소**
- **로컬 캐시는 인스턴스가 늘수록 손해다.** 앱 3대가 각자 캐시를 가지니 같은 키에 miss 가 3번 난다.
  균등 분포에서 로컬 hit 37.6%, 공유(Redis) 64.5%. **26.9%p 차이.**

그리고 통념 하나가 깨졌다.

**Stampede 는 TTL 이 짧아서 생기는 게 아니다.**
TTL 을 1초로 줄이고 지터를 0으로 둬도 스파이크가 거의 안 났다(1.05배).
키마다 캐시에 들어간 시각이 다르니 만료도 자연히 흩어지기 때문이다.
`FLUSHALL` 로 **동시 만료를 강제**하자 그제야 3.23배가 났다.
즉 위험한 건 짧은 TTL 이 아니라 **동기화된 만료**(배포 직후 콜드 스타트, 일괄 무효화)다.

쓰기 전략은 **cache-aside** 로 갔다. 선택지가 없었다 —
재고 차감은 조건부 원자 UPDATE(`WHERE remaining > 0`)라서 결과를 DB 가 정한다.
캐시에 먼저 쓰고 DB 에 반영하는 write-through 는 여기서 성립하지 않는다.

### Phase 08 · 메시지 큐

> 쓰기를 큐 뒤로 빼면 스파이크를 흡수할 수 있나?

여기서 제일 어려운 결정이 나온다. **어디까지 동기로 하고 어디부터 비동기인가.**

순진하게 하면 "요청 받으면 큐에 넣고 202 리턴" 이다. 그런데 티켓팅에서는 못 쓴다.
매진인데 202 를 주고 나중에 "죄송합니다 취소됐습니다" 를 보내게 된다.

그래서 이렇게 잘랐다.

```
판정은 동기로 — Redis DECR 로 재고를 선점한다. 실패하면 그 자리에서 409
반영은 비동기로 — 선점에 성공한 것만 큐에 넣고 202 Accepted
```

`DECR` 이 원자적이라 초과 판매가 구조적으로 안 난다.
실제로 모든 시나리오에서 `async_inconsistency_total` 이 **0** 이었다.

측정 결과가 흥미로웠다.

- **저부하(600 RPS)에서는 오히려 나빠졌다.** p99 95.87 → **233.56ms**.
  DB 트랜잭션 1회(1.9ms)를 Redis + 브로커 왕복 2회로 바꾼 셈이니 당연하다.
- **고부하(1,500 RPS)에서 3배 좋아졌다.** p99 241.05 → **80.58ms**.
- **3,000 RPS 스파이크를 흡수했다.** 큐 depth 가 1,833까지 쌓였다가 8초 만에 빠졌다.

**큐는 빠르게 만드는 도구가 아니라 밀린 일을 미루는 도구다.**
평소에 여유가 있으면 손해고, 순간적으로 넘칠 때 이득이다.

그리고 진짜 대가는 성능이 아니라 **약속**이다.
응답이 `201 Created`(확정)에서 `202 Accepted`(접수)로 바뀐다.
사용자에게 하는 말과 UI 를 같이 바꿔야 한다.

멱등성은 UNIQUE 제약으로 잡았다. at-least-once 라 같은 메시지가 두 번 올 수 있는데,
두 번째는 `23505` 로 튕기고 그걸 **성공으로 간주해서 ack** 한다.

재시도는 지연 큐로 구현했다. 실패하면 TTL 이 걸린 `retry` 큐에 넣고,
만료되면 dead-letter 로 본 큐에 되돌아온다. 정해진 횟수를 넘기면 DLQ 로 격리한다.

> 참고 — 이 단계 문서에 "1,189 RPS 에서 천장" 이라고 잘못 쓴 부분이 있다.
> 워밍업 구간이 섞인 평균이었다(`(100×20 + 1500×90) ÷ 115 = 1,191`).
> 지우지 않고 정정 표시를 달아 뒀다.

### Phase 09 · 최종 검증

> 목표를 실제로 넘겼는가? 그리고 이론과 실측이 맞는가?

**리틀의 법칙 `L = λ × W`** 에 앞 단계의 실측치만 넣어 필요 용량을 계산하고,
실제 구성과 비교했다.

| 계층 | 계산 | 필요 | 실제 | 배수 |
|---|---|---|---|---|
| 앱 CPU | `1000 ÷ (1÷518µs)` | 0.52 코어 | 6.0 | 11.5× |
| DB 커넥션 | `(1000×0.288) × 1.9ms` | 0.55개 | 22 | 40× |
| 워커 | `(1000×0.288) × 44.9ms ÷ 20` | 1대 | 4 | 4× |
| DB 메모리 | `10MB + 3.1MB × 22` | 78MB | 79MB | 1.01× |

DB 메모리 회귀식은 Phase 05 에서 뽑아 06 과 09 에서 다시 맞았다. **세 번 재현, 오차 1~2%.**

시나리오 3종을 돌렸다.

| 시나리오 | 유지구간 RPS | p95 | p99 | 진짜 실패 |
|---|---|---|---|---|
| soak · 1,000 RPS × 10분 | 1,005.0 | 22.1ms | 105.0ms | 300 (전부 시작 15초에) |
| spike · 0 → 2,000 RPS | 1,728.9 | 67.5ms | 182.0ms | 0 |
| fault · 앱 1대 강제 종료 | 997.2 | 21.6ms | 49.5ms | 2 |

여기서 **"진짜 실패" 의 정의**가 중요하다. 무응답 + 502 + 503 + 504 만 셌고,
**409 매진은 정상 거절이라 뺐다.** 안 그러면 티켓이 잘 팔릴수록 실패율이 오른다 —
지표로서 의미가 없어진다. 이 정의를 [`docs/slo.md`](slo.md) 에 SLI 로 못 박았다.

알람은 **다중 윈도 소진율(burn-rate)** 방식으로 짰다.
"에러율 1% 넘으면 알람" 같은 단일 임계값은 짧은 스파이크에 계속 울려서 결국 무시하게 된다.

### Phase 10 · 클라우드 이전 설계 (배포는 안 함)

> 이걸 그대로 클라우드로 옮기면 뭐가 달라지나?

배포는 하지 않고 설계만 했다. 결론 두 가지가 재미있다.

**서버리스가 부딪히는 문제는 대부분 커넥션이다.**
Lambda 가 수백 개로 늘면 각자 DB 커넥션을 연다. Phase 06 에서 본 곱셈이 그대로 재현된다.
그래서 RDS Proxy 가 선택이 아니라 전제가 된다.

**1,000 RPS 지속 부하에서는 상주가 2.5배 싸다.**

```
전부 상주 (ECS Fargate)      ~$905/월
워커만 서버리스 (Lambda+SQS) ~$2,245/월
```

이유는 단순하다 — **서버리스는 "안 쓸 때 0원" 으로 버는데 우리는 쉬지 않는다.**
손익분기를 거꾸로 계산하면 평균 27 RPS 이하일 때만 서버리스가 싸다. 목표의 3% 수준이다.

> 다만 진짜 티켓팅이라면 **평소 0, 오픈 시각에 폭증** 패턴이라 평균이 낮다.
> 즉 답은 "트래픽 모양에 달렸다" 이지 "서버리스가 비싸다" 가 아니다.
> (금액은 전부 공개 가격표 기반 추정이다. 자릿수 감각용이다.)

## 5. 반복해서 밟은 함정

같은 종류의 실수를 여러 번 했다. 이게 이 프로젝트에서 제일 실무적인 부분일 수 있다.

### 관측 도구가 측정을 두 번 죽였다

- **Phase 02** — cAdvisor 가 컨테이너 라벨로 시계열을 폭발시켜 Prometheus OOM
- **Phase 07** — k6 가 요청 URL 을 라벨로 붙여 시계열 **154만 개** → Prometheus OOM

Phase 07 에서는 실험 12개가 통째로 날아갔다.
`name` 태그를 고정하고 `url` 을 `systemTags` 에서 빼자 154만 → **2,901개**.

**모니터링은 공짜가 아니다.** 재려는 대상보다 재는 도구가 먼저 죽을 수 있다.
라벨에 요청마다 달라지는 값(URL, ID, 타임스탬프)을 넣으면 카디널리티가 폭발한다.

### 평균을 처리량으로 읽었다

워밍업이 섞인 전체 평균 RPS 를 "달성한 처리량" 으로 읽어서 Phase 08 에서 틀린 결론을 냈다.
**유지 구간만 잘라서 봐야 한다.**

### 그 외

| 증상 | 원인 | 교훈 |
|---|---|---|
| 실패율 100% 보고 | k6 `expectedStatuses` 에 202 없음 | 새 상태코드를 쓰면 부하 스크립트도 같이 고친다 |
| 실험이 1시간 43분 정지 | `docker compose exec` 이 맥 절전 후 무한 대기 | **모든 대기에 상한을 둔다** (`/dev/tcp` + 타임아웃) |
| 워커 지표가 통째로 없음 | 설정 추가 후 Prometheus 미재시작 | 설정을 고쳤으면 다시 읽었는지 확인한다 |
| RPS 가 `—` 로 나옴 | 분석 스크립트가 로그를 latin1 로 읽음 | 한글 로그는 utf8 |
| 커넥션당 30MB? | `VmRSS` 합산은 공유 메모리를 중복 계산 | 사적 메모리는 `RssAnon` |
| `SHOW POOLS` 파싱 오류 | PgBouncer 1.23 이 컬럼을 추가 | 문서 말고 **실제 출력**을 보고 파싱한다 |
| 워커 재시도가 안 됨 | 두 분기 모두 `nack(requeue=false)` → 항상 DLQ 행 | 지연 큐로 분리 |

## 6. 아직 못 한 것

틀린 가설이나 미측정 항목은 지우지 않고 남겼다.

- **메모리 누수는 판정 보류.** 10분 soak 에서 힙 기울기가 +0.64MB/분이었는데,
  워밍업 잔여인지 느린 누수인지 10분으로는 구분이 안 된다. 1시간 이상 돌려야 한다.
- **진짜 처리량 천장은 안 재봤다.** 1,500 RPS 를 요청했고 그만큼 나왔을 뿐이다.
  CPU 는 6코어 중 2.4코어만 썼으니 여유가 있었다.
- **soak 큐 샘플러가 헤더만 남겼다.** 원인 미상.
- **모든 측정이 단일 노트북 VM(6코어/8GB)에서 나왔다.**
  네트워크 지연이 사실상 0이라, RTT 가 존재하는 환경에서는 결론이 달라질 수 있는 항목이 있다
  (특히 TLS 1.3 의 왕복 이득, 큐 왕복 비용).
