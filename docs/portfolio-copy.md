---

## 1. 한 줄 소개

> 티켓 예약 API 하나를 10단계에 걸쳐 일부러 터뜨리며 백엔드 병목을 찾아낸 부하 테스트 기록

## 2. 세 줄 요약 (이력서 · 링크드인용)

> 티켓 예약 API 라우트 하나를 놓고 로드밸런서·앱 CPU·커넥션 풀·캐시·큐를 차례로 무너뜨리며
> 각 계층의 한계를 실측했습니다. 가설을 먼저 쓰고 재서 확인하는 방식으로 10단계를 진행했고,
> 목표였던 **1,000 RPS 지속 · p99 200ms · 에러율 0.1%** 를 최종 **1,005 RPS · 105ms · 0.05%** 로 넘겼습니다.

## 4. 같은 내용, 텍스트만 (Notion · PDF 이력서용)

**loadtest-sim** — 개인 프로젝트 · 2026.08
github.com/Jin-s-work/load-simulation

티켓 예약 API 하나를 10단계에 걸쳐 터뜨리며 백엔드 병목을 찾아낸 기록

백엔드가 어디서 왜 무너지는지 글로만 알고 있었습니다. 그래서 티켓 예약 API 라우트 하나를
만들어 두고 로드밸런서·앱 CPU·커넥션 풀·DB 프록시·캐시·큐를 차례로 무너뜨렸습니다.
라우트를 하나로 묶은 건 계층을 한 번에 하나씩만 바꿔 원인을 분리하기 위해서입니다.
가설은 실험 전에 쓰고 틀려도 고치지 않았고, 재지 않은 숫자는 문서에 적지 않았습니다.

- "풀이 마른다"를 원인이 아닌 증상으로 보고 추적 — 순차 스캔 쿼리 하나가 커넥션 30개를 점유하고
  있었고, 풀은 손대지 않고 인덱스 하나로 처리량 7.9배 · 실패율 85.8% → 0%
- 매진 판정은 Redis DECR로 동기 처리하고 DB 반영만 큐로 분리해 초과 판매를 구조적으로 차단
  — 전 시나리오에서 정합성 위반 0건
- 요청당 CPU를 인위적으로 늘려 `천장 = CPU 상한 ÷ 요청당 CPU` 모델을 검증(오차 3% 이내).
  같은 연산을 스레드풀로 옮기자 처리량이 오히려 하락 — 일을 옮긴 것이지 없앤 게 아니었음을 확인
- 리틀의 법칙으로 계층별 필요 용량을 계산해 실측과 대조 — DB 메모리 회귀식은 서로 다른
  세 단계에서 오차 1~2%로 재현
- 관측 도구가 측정을 두 번 죽인 사고(Prometheus OOM)를 겪고 라벨 카디널리티를
  154만 → 2,901 시계열로 축소 — 모니터링 자체가 부하라는 것을 실측으로 확인

**성과** 목표 대비 1,005 RPS 10분 지속 · p99 105ms · 에러율 0.05% (목표 1,000 RPS · 200ms · 0.1%),
앱 1대를 강제 종료한 상태에서도 18.3만 요청 중 실패 2건

**기술** Node.js · Fastify · Drizzle · PostgreSQL · Redis · RabbitMQ · HAProxy · PgBouncer ·
k6 · Prometheus/Grafana · Docker

## 5. 면접에서 한 개만 고른다면

이 프로젝트에서 제일 설명하기 좋은 건 **Phase 05** 다. 기술 스택 나열이 아니라
문제 해결 방식이 드러나는 사례이기 때문이다.

> 커넥션 풀이 마르고 실패율이 85.8%까지 올라갔습니다. 보통은 풀을 키우는데,
> 풀이 마르는 건 증상이지 원인이 아니라고 봤습니다. 커넥션을 오래 붙잡는 쪽을 찾아보니
> 200만 행짜리 순차 스캔 쿼리 하나가 커넥션 30개를 전부 묶고 있었습니다.
> 풀은 그대로 두고 인덱스만 하나 추가하니 처리량이 7.9배, 실패율이 0%가 됐습니다.

**"왜 이 프로젝트를 했나"** 를 물으면 — 부하 상황을 겪어본 적이 없어서
성능 이야기를 전부 남의 글로만 알고 있었고, 그게 불편해서 직접 재보기로 했다는 답이 정확하다.
