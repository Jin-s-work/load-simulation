# 08. 쓰기 경로를 큐로 분리한다

Phase: 08 · 2026-08-12

Phase 07 에서 캐시로 DB 접촉을 71% 줄였다(40,205 → 11,572). 남은 11,572회는
**전부 실제 쓰기**(재고 차감 + INSERT)라 캐시로는 더 줄일 수 없다.

이번엔 그 쓰기를 큐 뒤로 보낸다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — 비동기로 바꾸면 앱이 발행만 하고 응답하므로 p99 가 짧아진다.
**H2** — CPU 제약을 풀면 비동기 쪽이 더 높은 최대 RPS 를 낸다.
**H3** — 3000 RPS 스파이크를 큐가 흡수한다(depth 가 자랐다가 빠진다).
**H4** — 워커를 늘리면 컨슈머 랙과 복구 시간이 줄어든다.
**H5** — 워커를 계속 늘리면 어느 지점부터 DB 가 다시 병목이 된다.
**H6** — 중복 메시지를 UNIQUE 제약이 막아 재고가 두 번 깎이지 않는다.

## 설명: 동기와 비동기의 경계

기준은 **사용자에게 무엇을 약속하는가** 다.

| 작업 | 동기? | 이유 |
|---|:--:|---|
| **재고가 남았는지 판정** | **동기** | 매진이면 사용자는 다른 걸 사야 한다 |
| 재고 차감 커밋 | 비동기 가능 | 판정만 됐다면 |
| 예약 행 INSERT | 비동기 가능 | 사용자가 즉시 안 읽는다 |

**핵심은 재고 판정**이다. 이걸 큐로 보내면 응답의 의미가 바뀐다.

```
201 Created   "예약됐습니다"    <- 확정
202 Accepted  "접수됐습니다"    <- 확정 아님. 나중에 거절될 수 있음
```

**이게 MQ 도입의 진짜 대가다.** 처리량이나 지연이 아니라, 사용자에게 하는 약속과
그에 맞춘 UI 를 바꿔야 한다는 것.

그래서 **판정은 동기, 반영은 비동기**로 잘랐다.

```
① Redis DECR 로 재고 선점   <- 즉시. 매진이면 여기서 409
② 선점 성공하면 큐에 발행 -> 202
③ 워커가 DB 에 실제로 반영
```

Phase 07 이 세운 Redis 가 여기서 쓰인다. 이 게이트가 없으면
"매진인데 202 주고 나중에 취소 통보" 가 되어 티켓팅에서 쓸 수 없다.

## 설명: MQ 가 스파이크를 흡수하는 원리

```
유입  ▁▁▁█████▁▁▁   3000 RPS 스파이크
큐    ▁▁▂▅▇▇▆▄▂▁▁   버퍼가 차올랐다 빠진다
처리  ▁▁▃▃▃▃▃▃▃▃▁   워커 용량만큼 일정하게
```

Phase 04 의 리틀의 법칙이 그대로 적용된다. λ > μ 이면 큐가 자란다.
**다만 이번엔 그게 장애가 아니라 설계다.** 차이는 하나뿐이다 —
**큐가 앱의 이벤트 루프 위가 아니라 밖에 있다.** 앱은 발행만 하고 즉시 응답하니
큐 길이가 응답 지연으로 번역되지 않는다.

**대가 세 가지**

① **최종 일관성.** 발행 직후 조회하면 아직 없다.
② **실패 시점이 옮겨간다.** 이미 202 를 받은 뒤에 실패하므로 별도 통보 경로가 필요하다.
③ **버퍼는 무한하지 않다.** λ > μ 가 계속되면 큐가 터지고, 그때는 Phase 04 의
   load shedding 을 큐 앞에서 해야 한다.

> **MQ 는 용량을 늘리지 않는다.** 순간 유입과 처리 용량의 시간차를 흡수할 뿐이다.

## 설명: at-least-once · 멱등성 · DLQ · 컨슈머 랙

```
at-most-once   중복 없음, 유실 가능
at-least-once  유실 없음, 중복 가능    <- 실무 기본
exactly-once   분산에서는 사실상 불가. "중복 + 멱등성" 으로 흉내낸다
```

**유실보다 중복이 낫다** — 중복은 멱등성으로 지울 수 있지만 유실은 못 되돌린다.

**멱등성에 함정이 하나 있다.**

```
INSERT      reservations_idempotency_key_uidx(UNIQUE) 가 막는다   ✅
재고 차감   UNIQUE 가 못 막는다. 두 번 실행되면 두 번 깎인다      ❌
```

그래서 **차감과 INSERT 를 한 트랜잭션에 묶었다.** 중복이면 INSERT 가 제약 위반으로
터지고 트랜잭션이 통째로 롤백되어 **차감도 함께 되돌아간다.**
워커는 `23505`(UNIQUE 위반)를 **정상 동작으로 보고 ack** 한다 — 재시도하면 무한 반복이다.

**DLQ** 가 없으면 독약 메시지 하나가 큐 전체를 막는다. 처리 실패 → 재큐 → 다시 실패의
무한 루프다. Phase 04 의 "타임아웃만으로는 최악" 과 같은 구조 — **포기할 줄 알아야 한다.**

**컨슈머 랙** = 발행 수 − 처리 수. 랙이 계속 자라면 λ > μ 이고,
스파이크 후 랙이 0 으로 돌아오는 데 걸리는 시간이 **복구 시간**이다.

## 설정

| 항목 | 값 |
|---|---|
| 앱 | 3대, `cpus=0.8` (max-* 실험만 2.0) |
| 브로커 | RabbitMQ 3.13-management-alpine, `cpus=1.0` |
| 워커 | 1/2/4대, `cpus=0.4`, prefetch 20 |
| 하부 | Redis + PgBouncer(transaction) + Phase 05 최적화 경로 |
| 부하 | 600 RPS / 90초, Zipf. 스파이크는 3000 RPS × 30초 추가 |
| 재고 | 총 29,000석 (Phase 07 과 동일) |

### RabbitMQ 를 고른 이유

VM 이 6 CPU / 8GB 인데 이미 앱 3대 + Redis + PgBouncer + Postgres + HAProxy + k6 가 돈다.
**Kafka 는 브로커만 1GB 급이라 여유가 없다.**

그리고 Kafka 의 강점인 **파티션 순서 보장이 우리에겐 필요 없다** —
재고 차감은 교환법칙이 성립하고(누가 먼저 깎든 결과가 같다), 경쟁은 DB 의
조건부 원자 UPDATE 가 처리한다. 그래서 워커를 여러 개 띄워도 안전하다.
DLQ 가 1급 기능인 것도 실험 설계에 유리했다.

### 캐시와 큐는 실패를 다르게 다뤄야 한다

```js
// cache.js — 실패해도 요청은 산다
catch { return undefined; }          // miss 로 강등

// queue.js — 실패하면 던진다
catch { mqPublishErrors.inc(); throw err; }
```

발행 실패를 삼키면 **"202 를 줬는데 큐에 없는"** 최악의 상태가 된다.
**캐시는 최적화지만 큐는 유일한 처리 경로다.** 발행이 실패하면 선점한 재고도 되돌린다.

## 병목 원인

### H1 **반증** — 비동기가 오히려 느렸다

```
sync-base   p99  95.87ms
async-w1    p99 233.56ms   <- 2.4배 나쁘다
```

**"큐로 빼면 빨라진다" 가 이 워크로드에서는 틀렸다.**

이유는 무엇을 무엇으로 바꿨는지 보면 바로 나온다.

```
동기:   DB 트랜잭션 1회 (원자적 UPDATE + INSERT)      ≈ 2ms
비동기: Redis DECR 1회 + RabbitMQ 발행 1회(confirm)  ≈ 왕복 2회
```

**왕복이 1회에서 2회로 늘었다.** 게다가 publisher confirm 은 브로커가
메시지를 디스크에 기록했음을 확인할 때까지 기다린다(persistent 메시지).

Phase 05 에서 잰 트랜잭션 p50 이 **1.9ms** 였다. 원래 뺄 게 별로 없었던 것이다.

> **동기 경로가 이미 가벼우면 큐로 빼는 것이 손해다.**
> MQ 는 "무거운 작업" 을 뒤로 미룰 때 값을 한다. 우리 트랜잭션은 무겁지 않았다.

### 다만 워커를 늘리자 회복됐다 — 그리고 이게 H1 이 틀린 이유를 더 정확히 말해준다

```
async-w1  p99 233.56ms   앱 p99 145.1ms   드롭 280
async-w2  p99 194.36ms   앱 p99  77.4ms   드롭 129
async-w4  p99 110.77ms   앱 p99  57.7ms   드롭   0
```

워커가 1대일 때 **앱 p99 가 145ms** 로 매우 높다. 발행만 하는 앱이 왜 느린가?

**브로커가 밀렸기 때문이다.** 워커가 못 따라가면 큐가 쌓이고, RabbitMQ 는
디스크에 쓰느라 느려지며, 그 지연이 publisher confirm 을 통해 **앱까지 전파된다.**
워커 4대에서 앱 p99 가 57.7ms 로 떨어진 것이 그 증거다.

> **비동기라고 앞단이 뒷단에서 자유로운 게 아니다.** confirm 을 쓰는 한 연결돼 있다.

### H2 확인 — CPU 를 풀자 비동기가 명확히 이겼다

앱 cpus 를 0.8 → 2.0 으로 풀고 1500 RPS 를 주입했다.

| | k6 RPS | **k6 p99** | 앱 p99 | 드롭 |
|---|--:|--:|--:|--:|
| max-sync | 1,183.73 | **241.05ms** | 128.2ms | 1,261 |
| **max-async** | **1,188.93** | **80.58ms** | **22.7ms** | 269 |

**처리량은 같은데 p99 가 3배 좋고 드롭이 1/4.7 이다.**

여기서 비동기의 값이 드러난다. 부하가 높아질수록 **동기 경로는 DB 트랜잭션이
길어지지만**(경합 때문), 비동기 경로는 발행 시간이 거의 일정하다.
`max-async` 의 E2E p99 가 **0.08초**로 전 실험 중 가장 짧았던 것도 같은 이야기다 —
워커 4대가 여유로웠다.

> ~~**둘 다 1,183~1,189 RPS 에서 멈췄다.** 목표 1,000 RPS 는 넘겼지만~~
> ~~그 이상은 못 갔다. 병목이 앱 CPU 에서 다른 곳으로 옮겨간 것으로 보이는데,~~
> ~~이번 실험으로는 어디인지 특정하지 못했다.~~
>
> **[정정 · Phase 09]** 위 서술은 틀렸다. **천장이 아니라 내가 숫자를 잘못 읽은 것이다.**
>
> k6 의 "평균 RPS" 는 **워밍업을 포함한 런 전체 평균**이다. 이 실험의 구성은
> 워밍업 100 RPS × 20초 + 갭 5초 + 유지 1,500 RPS × 90초 였다.
>
> ```
> (100 × 20 + 1500 × 90) ÷ 115초 = 1,191.30 RPS
> 실측 max-async 1,188.93 / max-sync 1,183.73   <- 오차 0.2%
> ```
>
> **유지구간은 요청한 1,500 RPS 를 그대로 냈다.** 드롭도 13.5만 건 중 269건(0.2%)이었다.
> Phase 09 에서 `docker stats` 를 다시 확인해 보니 **VM 6 CPU 중 2.4 코어(242%)만 썼다** —
> 아무것도 포화되지 않았다.
>
> **교훈**: 워밍업이 섞인 평균을 "달성 처리량" 으로 읽으면 안 된다.
> 유지구간만 잘라서 봐야 한다. 다른 Phase 의 분석기는 유지구간만 보도록 짜 두었는데,
> 이 한 문장만 k6 요약의 전체 평균을 그대로 인용했다.

### H3 확인 — 큐가 스파이크를 흡수했다

3000 RPS × 30초를 얹었을 때 워커 1대 기준:

```
평상시      depth 1~10
스파이크    depth 1,833      <- 183배
8초 뒤      depth 3          <- 배수 완료
```

**큐가 정확히 버퍼로 동작했다.** 그리고 결정적인 것은 **앱이 멀쩡했다**는 점이다.

```
spike-sync       앱 p99 200.9ms
spike-async-w1   앱 p99  35.8ms   <- 5.6배 좋다
```

동기는 스파이크를 **DB 까지 그대로 전달**해 앱 p99 가 200ms 로 뛰었다.
비동기는 **큐에서 끊어** 앱이 35.8ms 를 유지했다. 이게 평탄화다.

### H4 확인, 그런데 spike-async-w4 가 이상하다

| | depth max | E2E p99 |
|---|--:|--:|
| spike-async-w1 | 1,833 | 4.89s |
| spike-async-w4 | **849** | **1.91s** |

**워커 4대가 큐 depth 를 절반 이하로, E2E 지연을 2.6배 줄였다.** H4 대로다.

**그런데 앱 쪽 p99 는 반대로 나빴다.**

```
spike-async-w1   k6 p99  68.79ms   드롭   464
spike-async-w4   k6 p99 669.45ms   드롭 5,986
```

이건 **CPU 경합**으로 보인다. VM 이 6 CPU 인데 스파이크 구간에서
앱 3대(2.4) + 워커 4대(1.6) + RabbitMQ(1.0) + Redis + PgBouncer + Postgres + k6 가
동시에 피크를 친다. 워커가 CPU 를 가져가면 앱과 k6 가 굶는다.
드롭이 5,986 이라는 것은 **k6 자신이 도착률을 유지하지 못했다**는 뜻이기도 하다.

> **이 수치는 "워커를 늘리면 앱이 느려진다" 는 결론의 근거로 쓸 수 없다.**
> 호스트 자원이 부족해서 생긴 간섭이고, 워커와 앱을 다른 기계에 두면 사라질 문제다.
> 이 VM 에서 6 CPU 로 7개 서비스의 동시 피크를 재는 것 자체가 무리였다.

### H5 미확인 — 워커가 DB 를 다시 병목으로 만드는 지점을 못 찾았다

워커 1/2/4 를 재봤지만 **DB 쪽에서 병목 징후가 안 나왔다.**
`202후 DB실패` 0건, DLQ 0건, 워커 처리 p99 최대 212ms.

이유는 명확하다 — **워커 4대가 처리하는 양이 초당 130건 남짓**이고,
Phase 05 에서 확인한 DB 용량은 그보다 훨씬 크다. 워커를 8대, 16대로 늘려야
DB 경합이 보이겠지만, 위에서 본 대로 이 VM 은 이미 CPU 가 모자란다.

**측정 환경의 한계로 미확인으로 남긴다.**

### H6 확인 — 멱등성이 정확히 동작했다

멱등키를 50% 확률로 재사용해 중복을 강제 주입했다.

```
발행           6,991건 (created 4,195 + duplicate 2,796)
UNIQUE 가 막음  2,796건
최종 예약행     4,176건
```

**`created`(4,195)와 최종 예약행(4,176)이 거의 정확히 일치한다.**
차이 19건은 분석 창(유지구간)과 전체 런의 경계 차이다.

**재고도 중복 차감되지 않았다.** 차감과 INSERT 를 한 트랜잭션에 묶었기 때문이다.
중복 메시지는 INSERT 에서 `23505` 로 터지고, 트랜잭션이 롤백되며 차감이 되돌아간다.
워커는 그걸 정상으로 보고 ack 한다 — **DLQ 0건**이 그 증거다.

### 재고 선점 게이트가 최종 일관성을 지켰다

**`202후 DB실패`가 전 실험 0건이다.**

Redis DECR 로 선점한 뒤에만 큐에 넣으므로, 워커가 DB 에 갔을 때 재고가 없는 일이
한 번도 없었다. 선점 거절(409)은 344~3,672건 발생했고, 그건 전부 **큐에 들어가기 전에**
막힌 것이다.

> **"202 를 줬는데 예약이 안 되는" 상황이 0건이었다.**
> 판정을 동기로 남긴 설계가 그 값을 했다.

## 개선

### 적용

| 개선 | 근거 |
|---|---|
| **Redis 선점 게이트** | 202후 DB실패 0건. 최종 일관성을 지켰다 |
| 차감+INSERT 를 한 트랜잭션에 | 중복 2,796건이 재고를 두 번 깎지 않았다 |
| `23505` 를 정상으로 보고 ack | 재시도 무한 반복을 막는다 |
| DLQ | 이번엔 안 쓰였지만(0건) 없으면 독약 메시지가 큐를 막는다 |
| 브로커 재연결 + 소비 재개 | 아래 사고 기록 참고 |

### 버린 대안

- **publisher confirm 끄기** — 발행이 빨라져 p99 가 개선될 것이다.
  하지만 브로커가 못 받아도 앱이 모르게 되어 **유실 가능성**이 생긴다.
  재고가 걸린 라우트에서 받아들일 수 없다. **측정하지 않았다.**
- **Kafka** — 위에서 설명한 대로 자원과 필요성 양쪽에서 맞지 않았다.
- **판정까지 비동기로** — "매진인데 202 주고 나중에 취소 통보" 가 된다. 설계상 배제.

## 사고 기록

### ① `docker compose exec` 이 절전에서 깨어나며 영원히 매달렸다

맥이 절전에 들어간 사이 `docker compose exec` 세션이 끊겼는데, **끊긴 채로 매달렸다.**
대기 루프에 타임아웃이 없어 감지도 못 했다.

```
1차: 기동 대기에서 1시간 43분 정지
2차: 큐 배수 확인에서 1시간 4분 정지   <- 1차 수정이 불완전했다
```

`docker compose exec` 는 상한을 걸 방법이 없다. 두 곳 모두 **호스트에서 직접 확인**하는
방식으로 바꿨다.

```bash
# 기동 대기: bash /dev/tcp 로 포트 확인 (절전 후엔 즉시 실패하지 매달리지 않는다)
(exec 3<>/dev/tcp/127.0.0.1/5672) 2>/dev/null

# 큐 상태: management HTTP API + curl --max-time (상한을 걸 수 있다)
curl -s --max-time 3 -u lts:lts 'http://localhost:15672/api/queues/%2F'
```

> **측정 스크립트의 모든 대기에는 상한이 있어야 한다.** 상한 없는 대기는
> 장애가 아니라 "조용한 정지" 로 나타나 원인 파악이 훨씬 어렵다.

### ② 앱이 브로커보다 먼저 떠서 영영 포기했다

```
mq_init_failed connect ECONNREFUSED 172.18.0.10:5672
-> 56,001건 전부 500, 예약행 0
```

`initQueue()` 를 한 번 호출하고 실패하면 그만이었다. **재연결을 넣었다**(지수 백오프, 상한 5초).
기동 순서 문제이기도 하지만, 더 중요한 건 **브로커 장애 후 스스로 복구**하는 것이다.

워커도 재연결 시 **`consume` 을 다시 걸어야** 한다. 채널이 새로 만들어지면
consumer 등록이 사라진다. 이걸 빼먹으면 "브로커는 살아났는데 아무도 안 먹는" 상태가 된다.

### ③ 계측 버그 세 개

**k6 `expectedStatuses(200, 201)` 에 202 가 없었다.** 워커가 20,323건을 정상 처리했는데도
실패율 100% 로 집계됐다. Phase 01 부터 쓰던 설정이라 202 를 몰랐다.

**409 매진이 "기타" 에 섞여 있었다.** 정상 거절과 진짜 오류가 구분되지 않았다. 분리했다.

**분석기가 로그를 `latin1` 로 읽고 있었다.** UTF-8 한글이 깨져 정규식이 전부 안 맞아
RPS·실패율이 `—` 로 나왔다. Phase 05~07 분석기에도 같은 버그가 있어 함께 고쳤다.

**`MQ_NOT_READY` 를 500 으로 답하고 있었다.** 재시도하면 되는 일시적 장애다.
Phase 06 의 `ENOTFOUND` 와 **같은 종류의 실수** — 새 의존성을 추가할 때마다
"이 실패는 일시적인가" 를 분류표에 넣는 것을 잊는다.

### ④ Prometheus 가 워커 스크레이프 설정을 안 읽었다

설정에 워커 잡을 추가했지만 Prometheus 를 재시작하지 않아, 실험이 도는 내내
워커 지표가 하나도 수집되지 않았다. **비동기 실험 7개를 다시 돌려야 했다.**

> **설정 파일을 고쳤으면 그 프로세스가 다시 읽었는지 확인해야 한다.**
