# 01. 취약 기준선 (baseline)

Phase: 01 · 작성 시작 2026-08-04

목표 SLO(프로젝트 최종 목표): 1000 RPS / p99 < 200ms / 에러율 < 0.1%
이 Phase 의 목적은 SLO 달성이 아니라 **아무것도 튜닝하지 않았을 때의 좌표를 찍는 것**이다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1 (주 가설) — 커넥션 풀(max 10)이 앱 CPU보다 먼저 고갈된다.**
이 라우트는 트랜잭션 하나 안에서 DB 왕복을 5번 한다(BEGIN / 멱등키 조회 / SELECT FOR UPDATE /
UPDATE / INSERT / COMMIT). 그동안 커넥션 1개를 계속 붙잡고 있다.
리틀의 법칙으로 상한이 정해진다: **최대 처리량 = 풀 크기 ÷ 트랜잭션 소요시간**.
풀이 10개이므로 트랜잭션이 10ms면 약 1000 RPS, 20ms면 약 500 RPS가 천장이다.
따라서 어느 지점부터 요청이 DB가 아니라 **풀 앞에서 줄을 서기 시작**할 것이다.

관찰될 신호: `db_pool_connections{state="waiting"} > 0`, `db_pool_acquire_wait_seconds` p99 급증,
반면 `process_cpu_seconds_total` rate 는 1.0 코어에 못 미침.

**H2 (대안 가설) — Node 단일 스레드가 먼저 포화된다.**
Fastify 라우팅 + Drizzle 쿼리 빌드 + pg 프로토콜 파싱 + JSON 직렬화가 전부 한 스레드에서 돈다.
이쪽이면 CPU 가 1.0 에 붙고 `nodejs_eventloop_lag_p99_seconds` 가 먼저 치솟는다.

**나는 H1 을 예상한다.** 왕복 5번짜리 트랜잭션은 커넥션 점유 시간을 크게 만들고,
풀 기본값 10 은 그 점유 시간을 감당하기에 작기 때문이다.

**H3 — closed model(ramping-vus)은 같은 서버를 더 좋게 보이게 만든다.**
VU 기반은 서버가 느려지면 부하도 같이 줄어서, 느린 구간이 표본에서 빠진다.
같은 서버인데 p99 가 open model 보다 낙관적으로 나올 것이다.

*(숫자 예측은 하지 않는다. 측정 전 수치는 근거가 없다 — CLAUDE.md 규칙 4.)*

### 스택

- **단일 프로세스. 클러스터링 없음. 레플리카 없음.**

### 라우트

`POST /api/v1/events/{eventId}/reservations`

트랜잭션 하나 안에서 순진하게 5번 왕복한다:
BEGIN → 멱등키 조회 → `SELECT ... FOR UPDATE` → `UPDATE events` → `INSERT reservations` → COMMIT.
최적화하지 않았다. 이게 기준선이다.

### 의도적으로 내린 결정

| 결정 | 이유 |
|---|---|
| `HOT_RATIO=0` (이벤트 1000개에 균등 분산) | 락 경합을 끈다. 경합을 섞으면 "커넥션 부족"과 "락 대기"가 구분되지 않는다 |
| `remaining = 100,000,000` | SOLD_OUT(409)이 섞이지 않게 한다. 재고 소진은 이 실험의 대상이 아니라 노이즈다 |
| 요청 로그 비활성화 | 1000 RPS 로 요청 로그를 남기면 Docker json-file 드라이버가 먼저 병목이 된다. 그러면 앱/DB 가 아니라 로깅 처리량을 재게 된다 |
| 매 실행 전 DB 초기화 + 앱 재기동 | 직전 런이 남긴 수십만 행과 워밍업된 상태가 다음 런의 조건을 바꾼다 |
| 멱등키를 이터레이션마다 새로 생성 | 키가 겹치면 서버가 replay 로 응답해서, 쓰기 경로가 아니라 조회 경로를 재게 된다 |

### 부하 모델

| 스크립트 | executor | 목적 |
|---|---|---|
| `generator-sanity.js` | ramping-arrival-rate | DB 미사용 라우트로 **생성기 상한 + 앱 단독 상한** 확인 |
| `breaking-point.js` | ramping-arrival-rate (open) | **주 시나리오.** RPS 를 계단식으로 올려 breaking point 탐색 |
| `closed-model.js` | ramping-vus (closed) | **대조군.** 측정 방법이 결과를 바꾸는지 확인 |

워밍업은 별도 시나리오(`phase:warmup` 태그)로 분리해 분석에서 제외한다.
각 계단은 5초 램프 + 60초 유지이고, **분석은 유지구간의 앞 15초를 버린 뒤쪽만** 사용한다
(램프 직후는 큐가 차오르는 중이라 정상 상태가 아니다).

계단 전환(램프) 구간에 몰린 것으로 판단한다.

### 3) 대조군 — `closed-model` (ramping-vus, 25 → 800 VU)

같은 서버, 같은 라우트. 부하 모델만 바꿨다.

```
요청 수    : 869554  (평균 1870 RPS)
이터레이션 : 869554 완료 / 0 드롭   <- closed model 은 구조적으로 드롭이 나올 수 없다
실패율     : 0.000 %
지연       : avg=118.38ms med=47.95ms p95=448.77ms p99=570.34ms max=1039.18ms
```

| 계단 | 실측 RPS | p50 | p95 | p99 | 풀 사용 avg | 획득대기 p99 | 앱 CPU |
|---|---|---|---|---|---|---|---|
| 25 VU | **2032** | 13.1ms | 23.8ms | **24.8ms** | 10.0 | 15.4ms | 1.06 |
| 50 VU | **2034** | 18.9ms | 42.3ms | 48.8ms | 9.9 | 41.9ms | 1.07 |
| 100 VU | 1872 | 44.1ms | 74.0ms | 136.9ms | 10.0 | 123.1ms | 1.09 |
| 200 VU | 1921 | 95.6ms | 146.2ms | 224.3ms | 10.0 | 216.3ms | 1.12 |
| 400 VU | 1942 | 194.5ms | 290.9ms | 323.9ms | 10.0 | 311.9ms | 1.13 |
| 800 VU | **1760** | 423.2ms | 703.9ms | 890.9ms | 10.0 | 872.4ms | 1.14 |

세 가지가 한눈에 보인다.

**(1) VU 를 32배 올렸는데 처리량은 0% 늘었다.** 25 VU 에서 2032 RPS, 800 VU 에서 1760 RPS.
RPS 는 입력이 아니라 `VU ÷ 응답시간` 의 결과값이라는 게 그대로 드러난다.
**VU 수는 부하 강도의 단위가 될 수 없다.**

**(2) 800 VU 에서는 처리량이 오히려 떨어졌다** (2032 → 1760, -13%). 동시성을 계속 밀어 넣으면
큐 관리 비용만 늘고 유효 처리량이 줄어드는 구간이 있다.

**(3) 같은 처리량인데 p99 가 28배 차이 난다.** 이게 coordinated omission 이다.

| 부하 모델 | 실측 RPS | p50 | p99 |
|---|---|---|---|
| closed (25 VU) | 2032 | **13.1ms** | **24.8ms** |
| open (2200 RPS 요구) | 2012 | **406.6ms** | **709.4ms** |

**같은 서버가 같은 초당 2000건을 처리하고 있는데, 한쪽은 p99 25ms, 다른 쪽은 709ms 로 보고한다.**
closed model 은 VU 25개가 응답을 기다리는 동안 새 요청을 보내지 않으므로 큐가 25 를 넘을 수 없다.
즉 **"도착이 처리 능력을 넘어서는 세계"를 표현할 수 없다.** 실제 사용자는 서버 사정과 무관하게
도착하므로, 그 세계에서 진짜로 겪게 될 대기시간이 측정에서 통째로 빠진다.

closed model 로만 쟀다면 이 서버의 결론은 **"2032 RPS 를 p99 25ms, 에러 0 으로 처리한다"** 였을 것이다.
전부 사실이지만, "2000 RPS 를 감당할 수 있는가"라는 질문에 대한 답으로는 틀렸다.

### 4) p99 스파이크 2건 — 부하와 무관한 원인

정상 상태 지표는 멀쩡한데 p99 만 순간적으로 튄 구간이 두 번 있었다. 부하 곡선에는 안 보이지만
p99 를 지배하는 종류의 사건이라 원인을 추적했다.

**사건 A — 15:07:23~15:07:30, p99 3.6ms → 9.3ms**

Postgres 로그에 정확히 대응하는 항목이 있다:

```
2026-08-04 15:07:27.025 UTC [57] LOG:  checkpoint starting: time
2026-08-04 15:09:31.501 UTC [57] LOG:  checkpoint complete: wrote 1274 buffers (7.8%);
    write=124.462 s, sync=0.008 s, total=124.477 s; distance=31024 kB
```

`checkpoint_timeout` 기본값 5분에 의한 시간 기반 체크포인트다. 부하와 무관하게 주기적으로 발생하며,
**충분히 긴 테스트라면 반드시 한 번은 맞는다.** 원인 확정.

**사건 B — 15:06:11~15:06:21, p99 3.7ms → 139.9ms (최대값)**

이쪽은 컨테이너 안에서 원인이 나오지 않았다. 같은 시각의 관측값:

| 지표 | 값 | 해석 |
|---|---|---|
| 앱 CPU | 0.29~0.33 코어 | 포화 아님 |
| GC (major+minor+incremental) | 합계 약 4ms/s | 스톨 아님 |
| Postgres `blks_read` | 0/s | 디스크 읽기 없음, 전부 shared_buffers |
| Postgres active 백엔드 | 1~2 | DB 는 한가함 |
| Postgres `conflicts` | 0 | 락 경합 없음 |
| 앱 in-flight | 20 (순간) | **앱 안에 요청이 쌓임** |
| 풀 대기 | 9 (순간) | 커넥션을 못 받고 대기 |

앱도 DB 도 한가한데 앱 안에서만 요청이 쌓였다. **컨테이너 바깥, 즉 호스트/VM 레벨에서
프로세스가 잠깐 스케줄되지 못한 것**으로 판단한다.

유력 후보는 **이 저장소가 놓인 위치**다. `~/Desktop` 은 iCloud Drive 동기화 대상이고 디스크가
100% 차 있어서(여유 4.3GB/460GB) macOS 가 파일 축출/동기화를 계속 돌리고 있었다.
확정하지는 못했다 — 호스트 레벨 계측이 없기 때문이다. **미해결로 남긴다.**

여기서 얻은 교훈은 원인 자체보다 크다: **노트북에서 부하를 재면 호스트 자신이 측정 대상의 일부가 된다.**
컨테이너 지표가 전부 정상인데 지연만 튀면, 그 다음에 의심할 곳은 컨테이너 밖이다.

## 병목 원인

### 결론: 앱의 단일 JS 스레드(CPU)가 먼저 터졌다. H2 가 맞고 H1 은 틀렸다.

**근거 1 — CPU 천장에 붙는 시점과 처리량이 평평해지는 시점이 일치한다.**

앱 프로세스 CPU 가 1.14~1.15 코어에서 더 오르지 않고, 정확히 그 지점에서 RPS 도 2000 에서 멈춘다.
컨테이너 상한은 **2.0 코어**인데 1.15 에서 멈춘 것이 핵심이다. 남은 0.85 코어를 못 쓰는 이유는
**Node 의 JS 실행 스레드가 하나**이기 때문이다. 여분 0.15 는 GC 등 보조 스레드 몫이다.
CPU 상한을 더 준다고 해결되지 않는다는 뜻이고, 이게 "수평 확장이 필요하다"는 Phase 04 의 근거가 된다.

**근거 2 — 풀 대기가 폭증할 때 정작 풀은 비어 있었다. (가장 결정적)**

| 계단 | 풀 대기 max | 풀 사용 avg (최대 10) |
|---|---|---|
| 1400 RPS | 64 | **4.0** |
| 1600 RPS | 119 | **3.8** |
| 1800 RPS | 119 | 5.4 |
| 2200 RPS | 889 | 10.0 |

1600 RPS 지점에서 **커넥션 6개가 놀고 있는데 119개가 대기 중**이었다.
풀이 작아서가 아니다. `pool.connect()` 의 결과를 넘겨주는 콜백이 이벤트 루프 위에서 돌기 때문에,
**루프가 밀리면 커넥션을 나눠주는 일 자체가 지연된다.**
풀 대기 큐는 원인이 아니라 증상이다. 풀이 실제로 고갈된 것은 2200 RPS 부터이고,
그때는 이미 CPU 가 천장에 붙은 뒤다.

> 이 구분이 Phase 02 의 출발점이다. "풀 대기가 보이니 풀을 키우자"는 여기서 오답이다.

**근거 3 — DB 는 끝까지 한가했다.**

Postgres 백엔드 12개 고정, `blks_read` 0/s(전부 shared_buffers), 락 충돌 0.
2600 RPS 를 요구하는 시점에도 동일하다.
트랜잭션 p99 가 714ms 까지 오르지만, 그 안에 **획득대기 709ms 가 포함**되어 있다.
둘의 차이는 처음부터 끝까지 5ms 안팎으로 일정하다 — **DB 가 실제로 일한 시간은 부하와 무관하게 변하지 않았다.**

| 계단 | 트랜잭션 p99 | 획득대기 p99 | 차이(= 실제 DB 작업) |
|---|---|---|---|
| 100 RPS | 4.4ms | <1ms | ~4ms |
| 1800 RPS | 73.5ms | 71.6ms | ~2ms |
| 2600 RPS | 714.1ms | 709.4ms | ~5ms |

**왜 CPU 가 먼저 탔나 — 요청당 CPU 가 10배다.**

| 라우트 | 요청당 앱 CPU |
|---|---|
| `/_sanity` (DB 없음) | 약 52µs |
| 예약 라우트 (DB 왕복 5회) | 약 518µs |

*(1차 스윕 100~1200 RPS 구간을 선형 회귀: CPU = 0.068 + 0.000518 × RPS)*

DB 가 느려서가 아니다. **앱 프로세스가** pg 프로토콜 직렬화/파싱과 Drizzle 쿼리 빌드를
트랜잭션 하나당 5번 수행하는 비용이다. 왕복 횟수가 곧 앱 CPU 비용이다.

### 계측의 한계 (정직하게 남긴다)

- **이벤트루프 지연 지표는 근거로 쓰지 않았다.** `nodejs_eventloop_lag_p99_seconds` 는 저부하에서도
  12~22ms 를 보인다(모니터 해상도 10ms 의 노이즈 바닥). 1400~1800 구간에서 28~33ms 로 오르긴 하나
  포화 구간(2200~2600)에서 오히려 18~22ms 로 내려간다. 판별력이 없어 결론의 근거에서 제외했다.
- **k6 자신이 병목이 아니라는 근거는 간접적이다.** `generator-sanity` 에서 5000 RPS 를 냈고,
  1800 RPS 계단에서 드롭이 3건뿐이었다는 점으로 판단했다. 다만 sanity 는 GET + 작은 응답이고
  본 시나리오는 POST + JSON 바디라 요청당 k6 비용이 더 크다. 컨테이너별 CPU 계측(cAdvisor)이
  없어서 직접 확인하지는 못했다. **Phase 02 에서 보완할 것.**
- 2200/2600 계단의 드롭은 `maxVUs=900` 상한에 걸린 결과이기도 하다. p50 407ms × 2000 RPS ≈ 820 VU 이므로
  900 은 서버 지연이 VU 를 전부 소진시킨 상태다. 서버 포화의 표현이지만, 상한이 더 컸다면
  드롭 수치는 달라졌을 것이다.

### 부수적으로 확인한 것: 에러율 SLO 는 이 실패를 못 잡는다

2600 RPS 를 요구해 **25,778건이 드롭되고 p99 가 714ms** 인 상태에서도 **5xx 는 0건**이었다.
실패 모드가 에러가 아니라 지연이었기 때문이다.
게다가 드롭된 25,778건은 **서버 지표 어디에도 남지 않는다** — 서버는 자기가 받지 못한 요청을 모른다.
부하 생성기 쪽 지표(`dropped_iterations`)를 같이 보지 않으면 존재 자체가 보이지 않는 실패다.

## 재측정

개선을 하지 않았으므로, 이 절은 **같은 조건으로 다시 재서 결론이 유지되는지** 확인하는 데 쓴다.

### A) 동일 프로토콜 반복 (100~1200 사다리, 2회차)

| 계단 | RPS 1회 / 2회 | p50 1회 / 2회 | **p99 1회 / 2회** | CPU 1회 / 2회 |
|---|---|---|---|---|
| 100 | 100 / 100 | 1.8 / 1.9ms | **4.7 / 7.9ms** | 0.12 / 0.14 |
| 200 | 200 / 200 | 1.8 / 1.8ms | **4.7 / 7.4ms** | 0.19 / 0.20 |
| 400 | 400 / 400 | 1.5 / 1.2ms | **5.0 / 4.1ms** | 0.30 / 0.27 |
| 600 | 600 / 598 | 1.3 / 1.6ms | **4.5 / 72.5ms** | 0.40 / 0.45 |
| 800 | 800 / 800 | 1.4 / 1.4ms | **4.6 / 10.3ms** | 0.51 / 0.52 |
| 1000 | 1000 / 1000 | 1.4 / 1.4ms | **4.7 / 22.6ms** | 0.60 / 0.62 |
| 1200 | 1200 / 1197 | 1.5 / 1.6ms | **10.0 / 49.6ms** | 0.69 / 0.72 |

**재현되는 것과 재현되지 않는 것이 갈린다.**

| 재현됨 | 재현 안 됨 |
|---|---|
| 처리량 (전 계단 1% 이내) | **p99 (최대 16배 차이: 4.5ms vs 72.5ms)** |
| p50 (0.3ms 이내) | |
| 앱 CPU (0.05 코어 이내) | |
| 풀 사용량 추세 | |

**p99 는 저부하 구간에서 부하가 아니라 "드문 사건"이 결정한다.**
2회차 600 RPS 계단에서도 1회차와 같은 위치에 스파이크가 났다(풀 대기 79, in-flight 90).
우연이 아니다 — 이 실험 구조상 600 RPS 계단이 런 시작 후 약 4.5~5.5분 지점에 오는데,
`checkpoint_timeout` 기본값이 **5분**이다. **시간 기반 체크포인트가 매번 그 계단에 떨어진다.**

따라서 이 Phase 의 결론은 **재현되는 양(처리량 / p50 / CPU / 풀 거동)에만 근거한다.**
"단일 JS 스레드가 ~2000 RPS 에서 천장"이라는 결론은 이 조건을 만족한다.
반면 "1000 RPS 에서 p99 4.7ms" 같은 문장은 단독으로 인용하면 안 된다. 다시 재면 22.6ms 가 나온다.
(다만 둘 다 SLO 200ms 로부터 한참 아래라 SLO 판정 자체는 뒤집히지 않는다.)

### B) 실패한 재측정 시도 — 프로토콜을 바꾸면 같은 지점이 아니다

처음에는 시간을 아끼려고 계단을 2개(1000, 1800)로 줄여 반복했다. 결과가 딴판이었다.

| 계단 | 7계단 사다리로 도달 | **2계단으로 점프** |
|---|---|---|
| 1000 RPS | p99 4.7ms, in-flight 8, 드롭 0 | p99 **136.0ms**, in-flight 148, 드롭 **478** |
| 1800 RPS | p99 73.6ms | p99 **486.6ms** |

원본은 100 → 1000 까지 6분에 걸쳐 올라갔고, 축약본은 워밍업 50 RPS 에서 5초 만에 1000 RPS 로 점프했다.
**사다리 자체가 워밍업 역할을 하고 있었다.**

이건 재현성 실패가 아니라 별개의 발견이다:
**어떤 부하 수준에 도달하는 경로가 그 수준의 측정값을 바꾼다.**
"1000 RPS 에서 p99 4.7ms" 는 불완전한 서술이고,
"100 부터 60초 계단으로 올라와 도달한 1000 RPS 에서 4.7ms" 가 정확한 서술이다.
부하 시나리오를 기록할 때 **목표 RPS 만이 아니라 도달 경로까지** 적어야 하는 이유다.

> 주의: 축약본 실행 중 Grafana 를 5초 자동갱신으로 띄워둔 채 스크린샷을 찍고 있었다.
> 호스트 부하에 기여했을 수 있어 정식 2회차에서는 껐다. 두 원인(램프 충격 / 호스트 노이즈)의
> 기여도를 분리하지는 못했다. **미해결로 남긴다.**

## Phase 01 결론

| 항목 | 값 | 근거의 신뢰도 |
|---|---|---|
| 처리량 천장 | **약 2000 RPS** | 높음 (반복 재현) |
| SLO(p99<200ms) 붕괴 지점 | **1800 ~ 2000 RPS** | 중간 (p99 변동 있으나 자릿수는 안정) |
| 최초 병목 | **앱 단일 JS 스레드 CPU** | 높음 (CPU 천장 1.15코어 + 풀 미고갈 동시 관측) |
| 커넥션 풀(10) | 병목 아님. 2200 RPS 이후에야 고갈 | 높음 |
| Postgres | 끝까지 병목 아님 | 높음 |
| 목표 SLO(1000 RPS) | **기준선이 이미 통과** (p99 4.7~22.6ms) | 높음 |

**Phase 02 로 넘길 것**

1. 커넥션 풀 크기를 키우는 실험을 하되, **먼저 "풀 대기 = 풀 부족" 이 아님을 확인**하고 들어간다.
   이 Phase 에서 풀 대기 119 / 풀 사용 3.8 을 관측했다.
2. 왕복 5회를 줄이면 앱 CPU(요청당 518µs)가 얼마나 내려가는지. 병목이 CPU 이므로 여기가 직접 효과가 있다.
3. 컨테이너별 CPU 계측(cAdvisor)을 추가한다. k6 가 병목이 아니라는 근거가 아직 간접적이다.
4. `checkpoint_timeout` 등 배경 작업이 p99 를 지배하는 문제 — 측정 신뢰도의 문제이므로 우선순위 높음.
5. **저장소를 iCloud 동기화 대상 밖으로 옮긴다.** 호스트 노이즈의 유력 후보이며,
   측정값을 신뢰할 수 없게 만드는 원인이다.
