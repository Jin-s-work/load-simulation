# 03. 로드밸런서 — 이 계층을 의도적으로 터뜨린다

Phase: 03 · 2026-08-06

Phase 01 결론: 병목은 **앱의 단일 JS 스레드 CPU**, 천장 약 2000 RPS.
Phase 02 결론: TLS 핸드쉐이크가 그 스레드를 갉아먹고, 프록시로 옮기면 앱이 무사하다.

이번엔 앱을 3대로 늘리고 앞에 LB 를 세운다. 앱 CPU 병목은 3배로 풀리므로,
**병목이 어디로 이동하는지** 볼 수 있다. 그리고 LB 는 CPU 가 아니라 **네트워크 자원**
(커넥션 슬롯, 파일 디스크립터, 임시 포트, accept 큐)에서 터지는 계층이다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — maxconn/nofile 을 낮추면 LB 가 커넥션을 받지 못해 요청이 큐에 쌓이거나 거부된다.
**H2** — 업스트림 keepalive 를 끄고 임시 포트를 좁히면 포트가 마르고 연결 실패가 난다.
**H3** — accept 큐(backlog)를 좁히면 커널이 SYN 을 버려 `ListenOverflows` 가 증가한다.
**H4** — 느린 백엔드가 1대 있을 때 round-robin 은 계속 보내고, least-conn 은 자동으로 피한다.
**H5** — source(ip-hash) 는 클라이언트 IP 가 하나뿐인 이 환경에서 **한 대로만** 보낼 것이다.
**H6** — graceful shutdown 없이 인스턴스를 죽이면 헬스체크가 감지할 때까지 죽은 구간이 생긴다.

---

## 설정

### 구조

```
k6 → HAProxy(L7) → app1, app2, app3 → Postgres
```

TLS 는 껐다. Phase 02 에서 비용을 알아냈으니 변수에서 제외한다. nginx 는 경로에서 뺐다.

### nginx 가 아니라 HAProxy 를 쓴 이유

**오픈소스 nginx 에는 액티브 헬스체크가 없다.** interval/timeout/threshold 를 가진 능동 확인은
상용판(nginx Plus) 기능이고, 오픈소스는 패시브(`max_fails`/`fail_timeout`)만 지원한다.
HAProxy 는 액티브·패시브 둘 다 기본이고, 알고리즘 3종과 Prometheus 익스포터를 내장한다.

### 리소스

| 서비스 | CPU | 메모리 | 비고 |
|---|---|---|---|
| app1/2/3 | 각 1.2 | 각 512m | Phase 01 관측 상한 1.15 코어라 사실상 비구속 |
| haproxy | 1.5 | 512m | `nbthread 2`, worker 여러 개 |
| postgres | 2.0 | 2g | 변경 없음 |
| k6 | 1.5 | 2g | 변경 없음 |

VM 은 6코어다. 앱 3대가 동시에 포화되면 VM 이 먼저 한계다.
따라서 **이번 Phase 는 최대 처리량이 아니라 LB 의 거동을 재는 것**이고,
부하는 포화보다 낮은 900 RPS 를 기본으로 썼다.

### 앱에 추가한 실험용 손잡이

| 환경변수 | 용도 |
|---|---|
| `INSTANCE_ID` | 응답 헤더 `X-Served-By` 로 분배 확인 |
| `SLOW_MS` | 인위적 지연. `setTimeout` 이라 CPU 를 태우지 않는 순수 "느린 백엔드" |
| `DRAIN_WAIT_MS` | 종료 시 readiness 를 내린 뒤 대기할 시간 |
| `APP_BACKLOG` / `APP_SOMAXCONN` | accept 큐 길이 |

### 헬스체크 엔드포인트를 3개로 분리

| 경로 | 확인 내용 | 쓰는 곳 |
|---|---|---|
| `/healthz` | **의존성 없음.** 즉시 200 | **LB 판정** |
| `/health/deep` | DB `SELECT 1` 포함 | **사람/모니터링 전용. LB 에 쓰지 않는다** |
| `/debug/info` | 인스턴스 상태 | 디버깅 |

이유는 아래 "헬스체크가 장애를 키우는 경우" 참고.

### 관측

`ss` / `netstat` 를 설치하지 않고 `/proc/net/*` 을 직접 읽는다.
도구를 설치하면 그 컨테이너가 실험 전과 달라진다. `/proc` 읽기는 아무것도 바꾸지 않는다.

| 파일 | 얻는 것 |
|---|---|
| `/proc/net/sockstat` | TCP inuse / orphan / **TIME_WAIT** / alloc |
| `/proc/net/snmp` | CurrEstab, ActiveOpens, PassiveOpens, **AttemptFails** |
| `/proc/net/netstat` | TcpExt: **ListenOverflows**, ListenDrops |
| `/proc/net/tcp` | TIME_WAIT 을 로컬 포트별로 분류(리슨 포트 vs 임시 포트) |

## 측정결과

### 0) 기준선 — `base-rr`

```
900 RPS / 90초 · round-robin · 정상 상태
요청 83,002 · 드롭 0 · 실패율 0.000%
p50 1.99ms · p95 4.80ms · p99 17.02ms
분배: app1 33.3% / app2 33.3% / app3 33.3%
HAProxy ActiveOpens 675  (요청 83,002건에 대해)
```

**ActiveOpens 675 / 요청 83,002** 이 핵심이다. 커넥션 하나가 요청 123개를 실어 날랐다.
keep-alive 가 정상 작동 중이고, TIME_WAIT 은 0 이다.

### (a) 커넥션 자원 고갈

**a-maxconn** — `maxconn 60`, frontend 50, 서버당 20

```
요청 81,777 · 드롭 849 · 실패율 0.322%
status 0 (응답 없음) 263건
p50 2.36ms · p99 73.48ms · **max 60,014ms**
HAProxy ActiveOpens 81,700  (기준선 675 대비 121배)
```

두 가지가 동시에 일어났다.

1. **max 60초.** `timeout queue 10s` 를 넘긴 요청이 있었다는 뜻이 아니라, 클라이언트가
   커넥션 슬롯을 기다린 시간이다. **LB 는 거부하기 전에 먼저 큐에 세운다.**
   즉 커넥션 고갈의 첫 증상은 에러가 아니라 **지연**이다.
2. **커넥션 재사용이 무너졌다.** ActiveOpens 가 675 → 81,700 으로 121배 늘었다.
   슬롯이 부족하니 유휴 커넥션을 유지할 여유가 없어 매번 새로 열었다.
   **한 자원을 조이면 다른 최적화가 같이 무너진다.**

**a-nofile** — `ulimit -n 256`

```
실패율 100.000%   (82,995건 전부 status 0)
분배: app1 0% / app2 0% / app3 0%
네트워크 캡처 없음 (컨테이너가 존재하지 않음)
```

HAProxy 가 **기동 자체를 거부**했다.

```
[ALERT] (1) : [haproxy.main()] Cannot raise FD limit to 40032, limit is 256.
```

`maxconn 20000` 으로부터 필요한 fd 수(20000 × 2 + 여유 = 40032)를 계산하고,
`ulimit -n` 이 그보다 낮으면 시작하지 않는다.

**이건 좋은 설계다.** 반쯤 동작하다 부하가 몰릴 때 터지는 것보다,
처음부터 정확한 숫자를 대며 거부하는 편이 훨씬 낫다.
컨테이너 재배포 후 갑자기 안 뜨는 흔한 원인이기도 하다.

### (b) 임시 포트 — **재현 실패. 이유를 규명했다**

조건: `http-reuse never`, `pool-max-conn 0`, 임시 포트 300개(60000~60299), 600 RPS

| 대상 | TIME_WAIT (총/리슨/임시) | TCP inuse max | 연결 | 연결실패 |
|---|---|---|---|---|
| HAProxy | 0 / 0 / **0** | 1,171 | 808 | **0** |
| app1 | 16 / 4 / **14** | 299 | 319 | **0** |

```
요청 38,001 · 실패율 0.000% · p99 13.84ms
```

**임시 포트에 쌓인 TIME_WAIT 이 0 이었다. 포트는 마르지 않았다.**

원인은 두 가지다.

**① HAProxy 는 클라이언트 커넥션과 백엔드 커넥션을 1:1 로 잡지 않는다.**
요청 38,001건에 대해 백엔드 연결 시도는 **808건**뿐이었다. L7 프록시는 여러 클라이언트 요청을
소수의 백엔드 커넥션에 다중화한다. 그래서 `http-reuse never` 를 켜도 백엔드 커넥션 수는
요청 수를 따라가지 않는다.

**② TIME_WAIT 은 "먼저 닫는 쪽"에 쌓인다.**
`c-app-backlog` 실험에서 HAProxy 의 TIME_WAIT 이 11,498개까지 올라갔는데,
포트별로 나눠 보니 **전부 리슨 포트(11,559) 쪽이고 임시 포트는 0** 이었다.
리슨 포트(8000)에 쌓인 TIME_WAIT 은 임시 포트를 소모하지 않는다.

> 즉 "keepalive 를 끄면 포트가 마른다"는 서술은 불완전하다.
> **누가 먼저 닫는지, 그리고 그 소켓의 로컬 포트가 리슨 포트인지 임시 포트인지**까지 봐야 한다.

**한 번 잘못된 결론을 낼 뻔했다.** 이 실험의 첫 실행에서 503 이 13,095건(34.5%) 나왔고
포트 고갈로 읽힐 뻔했다. 원인은 아래 "계측 사고" 참고 — **백엔드가 뜨기 전에 부하를 건 것**이었다.

### (c) accept 큐 — **재현 실패. 대신 다른 것이 먼저 무너졌다**

두 번 시도했다.

| 시도 | 조건 | ListenOverflows |
|---|---|---|
| 1차 | HAProxy backlog 8 / somaxconn 8 | **0** |
| 2차 | app backlog 4 / somaxconn 4, 커넥션 재사용 전부 끔, 1800 RPS | **0** |

2차의 결과:

```
요청 109,688 · 드롭 318 · 실패율 0.000%
p50 5.78ms · p95 51.28ms · **p99 1,079.74ms** · max 5,722ms
HAProxy ActiveOpens 109,968  (요청당 1개 = 재사용 완전히 끔)
app1 수락 36,557건
```

**accept 큐가 넘치기 전에 지연이 먼저 무너졌다.** 같은 1800 RPS 급 부하에서
커넥션을 재사용했을 때 p99 가 155ms 였는데, 재사용을 끄자 **1,079ms** 가 됐다.

큐가 안 넘친 이유:
- **accept 큐에 압력을 주는 것은 요청률이 아니라 커넥션 생성률이다.** 1차 시도는 클라이언트가
  keep-alive 를 쓰고 있어서, 1500 RPS 를 쏴도 커넥션은 수백 개뿐이었다.
- 2차에서 커넥션 생성률을 요청률과 같게 만들었지만(초당 1800개, 백엔드당 600개),
  Node 의 accept 는 그 정도를 소화했다. **큐가 넘치려면 accept 하는 쪽이 더 느려야 한다.**

우리 생성기가 낼 수 있는 커넥션 생성률로는 이 환경에서 `ListenOverflows` 를 만들지 못했다.
**미해결로 남긴다.**

### (d) 알고리즘 비교 — app3 만 300ms 느리게

| 알고리즘 | app1 | app2 | **app3(느림)** | p50 | **p99** |
|---|---|---|---|---|---|
| round-robin | 33.3% | 33.3% | **33.3%** | 12.42ms | **2,257ms** |
| **least-conn** | 49.3% | 49.2% | **1.5%** | **1.90ms** | **303ms** |
| source (ip-hash) | 0% | 0.04% | **100%** | 302ms | 2,343ms |

세 알고리즘 모두 에러는 0 이었다. 차이는 전부 **지연**으로 나타났다.

**round-robin** — 백엔드 상태를 보지 않는다. 죽지만 않았으면 똑같이 보낸다.
느린 서버로 간 1/3 이 300ms 를 그대로 먹고 p99 를 2,257ms 로 끌어올렸다.

**least-conn** — 설정 한 줄로 **p99 가 7.4배 좋아졌다.** app3 로 보낸 요청은 300ms 동안
"처리 중"으로 남으므로, 처리 중 개수가 가장 적은 곳을 고르는 방식이 자연히 app3 를 피한다.
**헬스체크처럼 물어보는 게 아니라 큐 길이라는 부작용으로 느림을 감지**하기 때문에,
"죽지는 않았는데 느린" 상태에 강하다.

**source** — 예상대로 최악이었다. k6 컨테이너의 IP 가 하나뿐이라 해시 결과가 항상 같고,
**100% 가 한 대로, 그것도 하필 느린 app3 로** 갔다. p50 이 302ms 로 모든 요청이 느려졌다.
LB 3대 앞에 두고 실질적으로 1대만 쓴 셈이다.

> 인위적 상황이 아니다. 클라이언트가 NAT·모바일 캐리어 게이트웨이·다른 프록시 뒤에 있으면
> 수많은 사용자가 같은 IP 로 보인다. 세션 고정을 얻으려다 로드밸런싱을 잃는다.

### (e) 인스턴스 종료와 죽은 구간

부하 중(시작 40초 시점) `docker stop -t 30 lts-app3`.

| | SIGTERM→종료 | 5xx | **p99** | max | app3 처리 비율 |
|---|---|---|---|---|---|
| `DRAIN_WAIT_MS=0` | **0초 (즉시)** | 503 × 1 | **3,010ms** | 5,053ms | 6.2% |
| `DRAIN_WAIT_MS=8000` | **8초** | **0** | **66ms** | 2,050ms | 7.9% |

**에러율만 보면 차이가 거의 없다(1건 vs 0건). p99 는 45배 차이난다.**

에러가 이렇게 적은 이유는 HAProxy 가 재시도했기 때문이다.

```
retries 2
option redispatch      # 재시도 시 다른 백엔드로
```

**L7 이라 가능한 일이다.** 요청 내용을 알고 있으니 다른 서버로 다시 보낼 수 있다.
L4 였다면 TCP 스트림을 되돌릴 수 없어 불가능하다.

그러나 재시도는 공짜가 아니다. 실패를 감지하고 재연결해 다시 보내는 시간이
**그대로 사용자 대기 시간**이 된다. 그게 p99 3,010ms 다.

drain 8초를 주면(헬스체크 `inter 2s × fall 3 = 6초`보다 길게) LB 가 먼저 app3 를 빼고,
그 다음에 프로세스가 죽는다. 재시도할 일 자체가 없어져 p99 가 66ms 로 떨어졌다.

## 계측 사고 — 이번 Phase 에서 잡은 것들

### ① 준비 게이트가 프론트엔드를 세고 있었다 (가장 위험했던 것)

실행 스크립트가 백엔드 3대가 뜰 때까지 기다리는 코드:

```bash
up=$(curl -s .../metrics | grep -c 'state="UP"} 1')   # 잘못됨
[ "$up" -ge 3 ] && break
```

이 패턴은 `haproxy_frontend_status`, `haproxy_backend_status` 까지 세어 **6** 을 반환한다.
**서버가 한 대도 안 떴는데 게이트를 통과한다.**

첫 `b-portexhaust` 실행의 503 13,095건(34.5%)이 여기서 나왔다.
포트 고갈로 읽힐 뻔했으나, 계측을 고치고 다시 재니 **실패율 0%** 였다.
`grep -c '^haproxy_server_status{proxy="be_app",server="app[123]",state="UP"} 1'` 로 고쳤다.

### ② `strtonum` 은 GNU awk 전용이다

TIME_WAIT 을 포트별로 나누려고 16진수를 변환했는데, macOS 기본 awk 에는 `strtonum` 이 없다.
**없는 함수를 불러도 awk 는 에러를 내지 않고 조용히 0 을 반환한다.**
그 열이 계속 0 으로 찍혀 "TIME_WAIT 이 안 쌓였다"고 읽을 뻔했다. 16진 파싱을 직접 구현해 고쳤다.

> **틀린 계측은 계측이 없는 것보다 나쁘다.** 없으면 모른다는 걸 알지만, 틀리면 안다고 착각한다.
> 이걸 잡을 수 있었던 건 "503 이 34.5% 인데 왜 커널 지표는 전부 0인가"라는 모순 때문이었다.
> **서로 다른 출처(k6 결과 vs 커널 카운터)를 대조하면 이런 게 걸린다.**

## 병목 원인 정리 — 무엇이 먼저 반응했나

| 실험 | 먼저 반응한 지표 | 그 다음 | 최종 증상 |
|---|---|---|---|
| a-maxconn | LB 큐 대기 (max 60s) | ActiveOpens 121배 증가 | status 0 263건 |
| a-nofile | (기동 실패) | — | 100% 실패 |
| b-portexhaust | — | — | **재현 실패** |
| c-app-backlog | **p99 155→1,079ms** | ActiveOpens 요청당 1개 | ListenOverflows 0 |
| d-slow-* | 인스턴스별 분배 비율 | 지연 분포 | p99 7.4배 차이 |
| e-kill | HAProxy 재시도 | p99 45배 | 에러는 거의 없음 |

**공통점: LB 계층의 실패는 에러가 아니라 지연으로 먼저 나타난다.**
LB 는 거부하기 전에 큐에 세우고, 실패하면 재시도한다. 둘 다 시간을 쓴다.
에러율만 보는 감시로는 LB 계층의 문제를 놓친다. Phase 01·02 와 같은 결론이다.

## 설명 요청 항목

### L4 vs L7 로드밸런싱

**L4(전송 계층)** 는 봉투(IP·포트)만 보고 배달한다.
**L7(응용 계층)** 은 편지를 열어 읽고(HTTP 파싱) 판단한다.

| | L4 | L7 |
|---|---|---|
| 분배 단위 | **커넥션** | **요청** |
| 재시도 | 불가 | **가능** (이번 (e) 에서 확인) |
| TLS 종료 | 불가 | 가능 (Phase 02) |
| 헬스체크 | TCP 연결 성공 여부 | **HTTP 200 확인** |
| CPU 비용 | 낮음 | 높음 |
| 클라이언트 IP | 보존 | `X-Forwarded-For` 필요 |

**가장 실무적인 차이는 분배 단위다.** L4 는 커넥션을 나누는데, keep-alive 를 쓰면
커넥션 하나가 요청 수천 개를 실어 나른다. 기준선 실험에서 커넥션 1개가 요청 123개를 처리했다.
그런 상황에서 커넥션을 균등 분배해도 실제 부하는 전혀 균등하지 않다.

L4 가 나은 경우: HTTP 가 아닌 프로토콜(DB, 스트리밍), 초당 수십만 커넥션으로 파싱 비용이 부담될 때,
클라이언트 IP 를 그대로 보존해야 할 때.

### 액티브 vs 패시브 헬스체크

**액티브** — LB 가 주기적으로 먼저 물어본다. 트래픽이 없어도 감지한다.
감지 시간 = `interval × fall`. 이번 설정은 2초 × 3 = **최대 6초**.

**패시브** — 실제 트래픽의 실패를 보고 판단한다. 추가 비용 0.
대신 **실제 사용자 요청이 탐지용 미끼**가 된다. 사용자가 에러를 먹어야 안다.

실무에서는 둘 다 쓴다. 액티브로 빠르게 감지·복귀하고, 패시브로 액티브가 놓치는 것
(예: `/healthz` 는 200 인데 실제 요청만 500)을 잡는다.

### 헬스체크가 오히려 장애를 키우는 경우

**① 연쇄 제거** — 부하로 전부 느려짐 → 헬스체크도 타임아웃 → **전부** unhealthy → 전멸.
느리지만 일부는 응답하던 상태를 완전 장애로 **승격**시킨다.

**② 상관 실패** — 공유 의존성(DB)이 흔들리면 모든 인스턴스가 **동시에** 같은 답을 낸다.
"서버들이 독립적으로 실패한다"는 로드밸런싱의 전제가 깨진다.

**③ 플래핑** — 임계값이 민감하면 up↔down 을 반복하고, 그때마다 커넥션이 끊기며 부하가 재분배된다.
**재분배 자체가 남은 서버를 밀어붙인다.**

**④ 재시작 폭풍** — liveness probe 실패가 컨테이너를 죽이면, 부하가 남은 인스턴스로 몰리고,
걔들도 느려져 죽고, 연쇄로 전멸한다.

**⑤ 헬스체크 자체가 부하** — interval 100ms × 백엔드 100대 = 초당 1,000 요청.

### 헬스체크에 DB 체크를 넣으면 왜 위험한가

헬스체크가 답해야 하는 질문은 **"나한테 트래픽을 보내도 되나?"** 이지
"우리 시스템 전체가 건강한가?" 가 아니다. `SELECT 1` 을 넣으면 두 번째 질문에 답하게 된다.

```
DB 가 3초 느려짐
  → app1, app2, app3 헬스체크가 동시에 타임아웃
  → LB: 보낼 곳 없음 → 503
  → DB 는 회복됐는데 rise 조건을 채울 때까지 서비스는 계속 죽어 있음
```

그 순간에도 캐시로 처리되거나 DB 가 필요 없는 요청은 서빙할 수 있었다. **스스로 문을 닫은 것이다.**

**더 고약한 경우 — 자기 실현적 장애.**
헬스체크가 DB 를 확인하면 커넥션 풀에서 커넥션을 빌린다.

```
부하 폭증 → 풀 고갈 → 헬스체크가 커넥션을 못 받음 → 타임아웃
→ unhealthy → 인스턴스 제거 → 남은 인스턴스에 부하 집중 → 또 풀 고갈 → ...
```

Phase 01 에서 "풀 대기 119개 / 풀 사용 3.8개" 를 관측했다.
그때 헬스체크가 DB 를 봤다면 서버가 통째로 빠졌을 것이다.

**올바른 구조**

| 종류 | 확인 내용 | 판정 주체 |
|---|---|---|
| liveness | 의존성 없이 즉시 200 | 오케스트레이터(죽일지) |
| readiness | 기동 초기화 완료 여부 | **LB(뺄지)** |
| deep/dependency | DB·캐시·외부 API | **모니터링 전용. LB 에 쓰지 않는다** |

꼭 포함해야 한다면 결과를 캐싱하고(예: 10초 갱신), "느려도 일단 서빙"을 기본으로 하며,
전 인스턴스가 동시에 실패하지 않도록 해야 한다.

이 프로젝트는 `/healthz` 에서 DB 를 보지 않고, `/health/deep` 을 따로 두었다.

### graceful shutdown / connection draining 이 왜 필요한가

그냥 죽이면:
- 처리 중이던 요청이 중간에 끊긴다 → 502 / Connection reset
- LB 가 열어둔 keep-alive 커넥션이 갑자기 닫힌다
- **LB 는 아직 모른다** → 헬스체크가 감지할 때까지 계속 보낸다 = **죽은 구간**

**올바른 순서 (순서가 전부다)**

```
1. readiness 를 false 로        → 헬스체크가 503 을 받기 시작
2. ★ LB 가 감지할 때까지 대기    → interval × fall 이상. 이걸 빼면 1)이 무의미
3. 새 커넥션 수락 중단 + 처리 중인 요청 완료 대기
4. keep-alive 커넥션 정리, 자원 해제 후 종료
```

**2번을 빠뜨리는 것이 가장 흔한 실수다.** 프로세스가 먼저 죽고 LB 가 나중에 아는 게 아니라,
**LB 가 먼저 빼고 그 다음에 죽어야** 한다.

이번 실험이 그 값을 보여준다: 2번이 없으면 p99 3,010ms, 8초를 주면 66ms.
