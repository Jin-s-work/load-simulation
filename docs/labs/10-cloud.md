# 10. 클라우드 이전 설계 (배포 없음)

Phase: 10 · 2026-08-13

**이 문서는 설계만 한다. 아직 배포하지 않았고, 여기 나오는 비용·지연 수치는 측정치가 아니다.**

Phase 01~09 는 전부 로컬 실측이었다. 이 문서는 성격이 다르다.
클라우드 요금과 cold start 는 **공개 문서와 가격표를 근거로 한 추정**이며,
이 프로젝트에서 잰 값이 아니다. **어느 쪽 근거인지 문장마다 구분해서 적는다.**

---

## 1. 로컬 → 매니지드 매핑

| 로컬 | AWS | GCP | 왜 이 서비스인가 (이 프로젝트 근거) |
|---|---|---|---|
| HAProxy (least-conn) | **ALB** | Cloud Load Balancing | ALB 는 least-outstanding-requests 를 지원한다. Phase 03 에서 least-conn 이 roundrobin 대비 p99 7.4배였으므로 이 알고리즘이 있는 게 조건이다 |
| app × 3 (컨테이너) | **ECS Fargate** | Cloud Run | 상주 컨테이너. 이유는 3절 |
| worker × 4 | **ECS Fargate (별도 서비스)** | Cloud Run Jobs | Phase 09 에서 다음 병목 1순위. **앱과 다른 노드에 둬야 한다** |
| PostgreSQL 16 | **RDS PostgreSQL** | Cloud SQL | — |
| PgBouncer | **RDS Proxy** | Cloud SQL Auth Proxy + PgBouncer | Phase 06 에서 DB 커넥션을 22개로 고정한 계층. 없애면 안 된다 |
| Redis 7.4 | **ElastiCache Redis** | Memorystore | 캐시 + 재고 선점 카운터 |
| RabbitMQ | **Amazon MQ (RabbitMQ)** | Pub/Sub | 아래 주의 참고 |
| Prometheus + Grafana | **AMP + AMG** | Cloud Monitoring | Phase 02·07 에서 두 번 OOM 났다. 매니지드로 넘기면 그 사고가 사라진다 |

### 브로커 선택에 주의가 필요하다

Phase 08 에서 RabbitMQ 를 고른 이유는 **DLQ 가 1급 기능이고 파티션 순서가 불필요**해서였다.
클라우드에서는 선택지가 달라진다.

| 후보 | 우리 요구와 맞는가 |
|---|---|
| **Amazon MQ (RabbitMQ)** | 코드 변경 0. 하지만 **매니지드 브로커라 인스턴스 요금이 상주로 나간다** |
| **SQS** | 서버리스 요금(요청당). DLQ 1급. **다만 AMQP 가 아니라 코드를 고쳐야 한다** |
| Pub/Sub | GCP. 마찬가지로 코드 변경 필요 |

**SQS 를 권한다.** 이유는 두 가지다.

① 우리는 RabbitMQ 의 고급 기능을 안 쓴다. exchange 라우팅도, 우선순위도 없다.
   쓰는 건 **큐 하나 + DLQ + 지연 재시도**뿐이고 SQS 가 전부 지원한다.
② Phase 08 에서 확인했듯 **파티션 순서가 필요 없다.** 재고 차감은 교환법칙이 성립하고
   경쟁은 DB 의 조건부 원자 UPDATE 가 처리한다.

다만 **지연 재시도 구현이 바뀐다.** Phase 10 에서 만든
`x-message-ttl` + dead-letter 조합 대신 SQS 는 `VisibilityTimeout` 을 쓴다.
개념은 같지만 코드는 다르다.

## 2. 서버리스로 바꿀 때 생기는 문제들

### ① Cold start 와 p99

**우리 SLO 는 p99 < 200ms 다.** 로컬 실측은 유지구간 105ms 였다(Phase 09).
여유가 95ms 뿐이다.

```
Node.js Lambda cold start:  수백 ms ~ 1초대 (일반적으로 알려진 범위)
우리 p99 여유:              95ms
```

> **이 cold start 수치는 추정이다.** 이 프로젝트에서 측정하지 않았다.
> 다만 **한 자릿수 ms 가 아니라는 것만은 분명**하고, 그것만으로도 판단이 선다.

문제는 cold start 자체가 아니라 **p99 에 걸린다**는 점이다.
cold start 비율이 1%만 돼도 p99 는 그 값이 된다.

**대응책과 대가**

| 대응 | 효과 | 대가 |
|---|---|---|
| Provisioned Concurrency | cold start 제거 | **상주 요금.** 서버리스의 비용 이점이 사라진다 |
| SnapStart (Java) | 초기화 스냅샷 | Node.js 미지원 |
| 번들 크기 축소 | 초기화 단축 | 우리 앱은 이미 작다. 효과 제한적 |
| **cold start 가 p99 에 안 걸리는 경로에만 서버리스** | 근본적 | 어떤 경로인지 판단이 필요 → 3절 |

### ② 함수 인스턴스 폭증 → DB 커넥션 고갈

**Phase 06 에서 이미 잰 문제가 훨씬 심한 형태로 돌아온다.**

```
Phase 06 실측:  앱 6대 × 풀 20 = 120 시도 → max_connections 98 도달
                → too_many_clients 47건, psql 조차 접속 불가

서버리스:       동시실행 1000 × 풀 1 = 1000 시도
                → 상한이 트래픽에 연동된다. 잘 될수록 커넥션이 는다
```

**Phase 06 의 결론이 그대로 답이다.**

```
직결   앱 6대 × 풀 20 → DB 98개 (상한 도달)
프록시 같은 조건       → DB 22.0개 고정, 실패 0%
```

**RDS Proxy 가 필수다.** 선택이 아니라 전제다.

그리고 Phase 05 의 회귀식이 비용 계산에 그대로 쓰인다.

```
사적메모리 ≈ 10MB + 3.1MB × 커넥션수     (Phase 05, 06·09 에서 세 번 재현)

커넥션 1000개면 → 10 + 3100 = 3,110MB
커넥션 22개면   → 10 + 68   =    78MB
```

**프록시 하나가 DB 메모리 3GB 를 아낀다.**

### ③ 로컬 캐시가 무력화되는 이유

Phase 07 에서 이미 쟀다.

```
앱 3대:   로컬 hit 37.6%  vs  Redis 64.5%   (균등 분포)
```

**인스턴스가 3대일 때 이미 26.9%p 차이가 났다.** 서버리스는 인스턴스가 수백~수천 개고,
게다가 **수명이 짧다.**

```
로컬 캐시가 성립하려면:  프로세스가 오래 살고, 같은 키가 같은 프로세스로 와야 한다
서버리스의 현실:        프로세스가 몇 분 살고, 라우팅을 통제할 수 없다
```

**로컬 캐시는 서버리스에서 거의 항상 손해다.** 워밍 비용만 내고 hit 를 못 얻는다.

> 예외가 하나 있다. **불변 데이터**(설정, 스키마, 정적 룩업)는 로컬에 둘 만하다.
> 하지만 우리가 캐시하는 건 재고 상태 — 계속 바뀌는 값이라 해당 없다.

### ④ 동시성 제한과 큐 기반 완충

서버리스의 동시성 제한은 **양날이다.**

```
제한이 없으면  → 인스턴스 폭증 → DB 커넥션 고갈 (②)
제한을 걸면    → 초과분이 throttle(429) 로 거절된다
```

**Phase 04 에서 이미 답을 냈다.**

> 빨리 거절하는 게 느려지는 것보다 낫다 — load shedding 으로 p50 이 21,914ms → 493ms

throttle 은 클라우드가 대신 해주는 load shedding 이다. **문제는 사용자에게 429 가 간다는 것.**

그래서 **큐를 앞에 둔다.**

```
[API Gateway] → [큐] → [함수(동시성 제한)] → [DB]
                 ↑
                 여기가 완충. 함수가 못 따라가면 큐가 자란다
```

Phase 08 에서 이 구조의 효과를 실측했다.

```
3000 RPS 스파이크:  큐 depth 1 → 1,833 → 8초 만에 배수
앱 p99:            동기 200.9ms  vs  비동기 35.8ms
```

**큐가 스파이크를 흡수하면 함수 동시성이 튀지 않는다.**
동시성이 안 튀면 커넥션도 안 튄다. ②와 ④는 같은 해법으로 풀린다.

## 3. 무엇을 서버리스로, 무엇을 상주로

**이 프로젝트의 라우트를 기준으로 판단한다.**

우리 라우트가 하는 일을 Phase 09 의 흐름대로 쪼개면 이렇다.

```
① 캐시 조회 (Redis)            ─┐
② 재고 선점 (Redis DECR)        ├─ 동기. 사용자가 기다린다
③ 큐 발행 → 202                ─┘
④ 워커: DB 차감 + INSERT        ─── 비동기. 사용자가 안 기다린다
```

### 판단 기준

| 기준 | 서버리스가 유리 | 상주가 유리 |
|---|---|---|
| p99 여유 | 넉넉함 | **빠듯함** |
| 트래픽 패턴 | 간헐적·불규칙 | **꾸준함** |
| 상태 | 무상태 | 커넥션 풀·캐시를 오래 유지 |
| 실행 시간 | 짧음 | 길거나 스트리밍 |

### 결론

| 부분 | 판단 | 근거 |
|---|:--:|---|
| **① ~ ③ 동기 경로** | **상주** | p99 여유가 **95ms 뿐**이다(Phase 09: 105ms / 목표 200ms). cold start 가 여기 걸리면 SLO 를 깬다. 게다가 티켓팅은 오픈 시각에 트래픽이 꾸준히 몰린다 — 서버리스의 "안 쓸 때 0원" 이점이 안 산다 |
| **④ 워커** | **서버리스 후보** | 사용자가 안 기다린다. cold start 가 E2E 지연에만 영향을 주고, Phase 08 실측 E2E p99 는 0.08초였다. 수백 ms 가 늘어도 SLO 와 무관하다 |
| 재고 선점(Redis) | 상주 안에 | 동기 경로의 일부 |
| 관측 | 매니지드 | Phase 02·07 에서 두 번 OOM. 우리가 운영할 이유가 없다 |

**핵심은 "누가 기다리는가" 다.**

```
사용자가 기다리는 경로  → 상주.  cold start 를 감당할 여유가 없다
아무도 안 기다리는 경로 → 서버리스.  cold start 가 SLO 에 안 걸린다
```

Phase 08 에서 동기/비동기를 자른 경계가 **그대로 서버리스/상주의 경계가 된다.**
이건 우연이 아니다. 둘 다 "사용자에게 무엇을 약속하는가" 로 자른 선이기 때문이다.

### 다만 워커도 조건부다

워커를 Lambda 로 옮기면 **DB 커넥션 문제가 워커 쪽에서 재현된다.**
Phase 09 에서 워커가 다음 병목 1순위였고, 부하가 늘면 Lambda 동시성도 는다.

**RDS Proxy 를 반드시 통과시켜야 한다.** 그러면 Phase 06 처럼 DB 커넥션이 고정된다.

## 4. 월 비용 러프 비교 (1,000 RPS)

> **⚠️ 이 절의 모든 금액은 공개 가격표 기반 추정이다. 실제 청구액이 아니다.**
> 리전·약정·데이터 전송량에 따라 크게 달라진다. **자릿수 감각용으로만 쓴다.**
> 계산 근거를 전부 적어 두었으니 숫자가 의심되면 직접 다시 계산할 것.

**전제**

```
1,000 RPS 지속 = 월 25.9억 요청  (1000 × 86400 × 30)
그중 DB 를 치는 비율 28.8%       (Phase 07 실측)
그중 큐로 가는 비율도 28.8%      (= 쓰기 요청)
   → 월 큐 메시지 약 7.46억 건
```

### A안 — 전부 상주 (ECS Fargate)

| 항목 | 구성 | 근거 | 월 추정 |
|---|---|---|--:|
| 앱 | Fargate 3 태스크 × 2vCPU/4GB | Phase 09 구성 그대로 | ~$210 |
| 워커 | Fargate 4 태스크 × 0.5vCPU/1GB | Phase 09 구성 | ~$70 |
| ALB | 1개 + LCU | — | ~$30 |
| RDS | db.m6g.large Multi-AZ | 커넥션 22개면 여유 | ~$250 |
| RDS Proxy | 1개 | Phase 06 근거로 필수 | ~$45 |
| ElastiCache | cache.t4g.medium × 2 | — | ~$100 |
| Amazon MQ | mq.m5.large 단일 | — | ~$150 |
| 관측 | AMP + AMG | — | ~$50 |
| | | **합계** | **~$905** |

### B안 — 워커만 서버리스 (Lambda + SQS)

| 항목 | 구성 | 근거 | 월 추정 |
|---|---|---|--:|
| 앱 | Fargate 3 태스크 (동일) | 동기 경로는 상주 | ~$210 |
| **워커** | **Lambda 7.46억 실행 × 100ms × 512MB** | Phase 08 워커 처리 p99 44.9ms → 100ms 로 잡음 | **~$680** |
| **큐** | **SQS 7.46억 요청** | 발행+수신+삭제 = 약 22억 API 콜 | **~$880** |
| ALB / RDS / Proxy / Cache / 관측 | A안과 동일 | — | ~$475 |
| | | **합계** | **~$2,245** |

### 비교와 해석

```
A안 (전부 상주)      ~$905/월
B안 (워커 서버리스)  ~$2,245/월    <- 2.5배 비싸다
```

**1,000 RPS 지속 부하에서는 상주가 명백히 싸다.** 이유는 단순하다 —
**서버리스는 "안 쓸 때 0원" 으로 버는데, 우리는 쉬지 않는다.**

손익분기를 거꾸로 계산하면 이렇다.

```
Fargate 워커 4대 = 월 ~$70 = 상시 가동
Lambda 로 $70 을 쓰려면 → 대략 월 7천만 실행 이하
                        → 평균 27 RPS 이하일 때만 서버리스가 싸다
```

**우리 목표(1,000 RPS)의 3% 수준**이다. 그 아래로 떨어지는 서비스라면 서버리스가 맞고,
티켓팅처럼 특정 시각에 몰리는 서비스는 **"평소 0, 오픈 시각에 폭증"** 이라
평균이 낮아 서버리스가 유리할 수 있다.

> **즉 답은 "트래픽 모양에 달렸다" 이지 "서버리스가 비싸다" 가 아니다.**
> 우리 SLO 는 "1,000 RPS 지속" 이므로 A안이 맞다.
> 실제 티켓팅이라면 **오픈 시각만 스파이크인 패턴**이므로 다시 계산해야 한다.

### 비용에서 빠진 것

- **데이터 전송료.** 리전 간·인터넷 아웃바운드는 계산에 안 넣었다. 실제로는 무시 못 한다.
- **NAT Gateway.** Lambda 를 VPC 에 두면 필요하고, 시간당 + 처리량 요금이 붙는다.
- **백업·스냅샷·로그 보관.** RDS 백업과 CloudWatch Logs 는 별도다.
- **약정 할인.** Savings Plans / Reserved 를 쓰면 A안이 더 싸진다(서버리스는 해당 없음).

## 5. 마이그레이션 순서

**원칙: 한 번에 한 계층만 옮긴다.** Phase 02 규칙과 같은 이유다 —
두 개를 같이 옮기면 문제가 생겼을 때 원인 귀속이 안 된다.

### 0단계 — 옮기기 전에

로컬에서 **부하 프로파일을 확정**한다. 이미 있다.

```
docs/labs/09-final.md   계층별 한계치와 다음 병목
docs/slo.md             SLO/SLI 와 알람 임계치
scripts/capacity.mjs    리틀의 법칙 용량 산정
```

**이게 없으면 클라우드에서 인스턴스 크기를 감으로 고르게 된다.**

### 1단계 — 상태부터 (DB)

```
RDS 생성 → 스키마 이관 → RDS Proxy 앞에 세움
```

**Proxy 를 처음부터 넣는다.** Phase 06 에서 확인한 대로 나중에 넣으면
커넥션 수가 이미 문제를 일으킨 뒤다.

검증: `db/init.sql` 적용 후 로컬 앱이 RDS 를 보게 해서 Phase 09 soak 을 돌린다.
**로컬 대비 p99 차이가 네트워크 지연으로 설명되는지** 확인한다.

### 2단계 — 캐시와 큐

```
ElastiCache 생성 → CACHE_MODE=redis 의 REDIS_URL 만 교체
SQS 생성        → queue.js 의 AMQP 구현을 SQS 로 교체 (코드 변경 발생)
```

SQS 로 가면 **지연 재시도 구현이 바뀐다.** 지금은 `x-message-ttl` + dead-letter 인데
SQS 는 `VisibilityTimeout` 이다. 이 부분은 **로컬에서 먼저 테스트**해야 한다
(LocalStack 또는 실제 SQS 개발 큐).

### 3단계 — 워커

```
Fargate 서비스로 먼저 올린다 (Lambda 아님)
```

**Lambda 는 나중에 검토한다.** 이유는 4절 — 지속 부하에서는 비싸고,
Phase 09 에서 워커가 다음 병목 1순위라 **먼저 안정적으로 돌리는 게 우선**이다.

### 4단계 — 앱과 LB

```
ALB + Fargate 3 태스크 → least-outstanding-requests 로 설정
헬스체크와 draining 을 반드시 켠다
```

**draining 을 빼먹으면 안 된다.** Phase 03 에서 drain 유무가 p99 45배였다.
ALB 의 `deregistration_delay` 가 그 역할이다.

### 5단계 — 관측

```
AMP + AMG 로 옮기고, docs/slo.md 의 알람을 그대로 옮긴다
```

임계치는 이미 실측 기반으로 정해져 있다. **다시 정할 필요가 없다.**

### 6단계 — 검증

**Phase 09 의 시나리오 3종을 클라우드에서 그대로 돌린다.**

```
./scripts/run-final.sh soak|spike|fault   (BASE_URL 만 ALB 로 교체)
```

로컬 결과와 나란히 놓고 **차이가 설명되는지** 본다.
설명 안 되는 차이가 있으면 그게 다음 조사 대상이다.

### IaC 구성

```
terraform/
├── modules/
│   ├── network/      VPC, 서브넷, 보안그룹
│   ├── data/         RDS + RDS Proxy + ElastiCache
│   ├── queue/        SQS + DLQ
│   ├── compute/      ECS 클러스터, 앱·워커 서비스, ALB
│   └── observability/ AMP + AMG + 알람
└── envs/
    ├── dev/
    └── prod/
```

**`docker-compose.yml` 의 환경변수가 그대로 Terraform 변수가 된다.**
`PG_POOL_MAX`, `CACHE_TTL_MS`, `MQ_MAX_RETRY` 같은 값들은
Phase 05~08 에서 근거를 가지고 정한 것이라 **그대로 옮기면 된다.**

## 6. 이 문서의 한계

**측정하지 않았다.** 이 문서의 어떤 숫자도 이 프로젝트에서 잰 값이 아니다
(Phase 01~09 에서 인용한 실측치는 예외이며, 출처를 표시했다).

특히 이 셋은 실제로 배포해서 재봐야 한다.

1. **cold start 실측.** "수백 ms" 는 추정이다. 우리 번들·런타임에서 얼마인지 모른다.
2. **네트워크 지연.** 로컬은 같은 VM 안이라 왕복이 거의 0 이었다.
   클라우드는 AZ 간 왕복이 붙는다. **p99 105ms 가 그대로 유지될 리 없다.**
3. **실제 요금.** 4절은 자릿수 감각용이다. 데이터 전송·NAT·백업이 빠져 있다.
