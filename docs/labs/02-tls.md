# 02. HTTPS / TLS 와 서버 부하

Phase: 02 · 작성 시작 2026-08-05

Phase 01 결론을 입력으로 받는다: **앱의 단일 JS 스레드가 병목이고, 천장은 약 2000 RPS,
요청당 앱 CPU 는 약 518µs.** TLS 핸드쉐이크는 그 스레드에서 도는 암호 계산이므로
같은 예산을 두고 경쟁한다. 이번 Phase 는 그 경쟁의 크기를 재는 것이다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1 — keep-alive 가 살아 있으면 HTTPS 는 HTTP 와 거의 차이가 없다.**
핸드쉐이크는 커넥션을 새로 뚫을 때만 발생한다. 커넥션 하나로 요청을 계속 보내면
비싼 비대칭 연산은 처음 한 번뿐이고, 이후에는 대칭키 암호화(AES-GCM)만 남는다.
M1 에는 AES 하드웨어 가속이 있으므로 이 비용은 작을 것이다.

**H2 — keep-alive 를 끄면 요청당 앱 CPU 가 눈에 띄게 오르고, 그만큼 처리량 천장이 내려간다.**
요청마다 전체 핸드쉐이크를 하게 되므로 서명 연산이 요청 수만큼 발생한다.
Phase 01 에서 검증한 모델(`천장 = CPU 상한 ÷ 요청당 CPU`)에 따라 천장이 내려가야 한다.

**H3 — RSA-2048 이 ECDSA P-256 보다 서버 CPU 를 훨씬 많이 쓴다.**
서버는 핸드쉐이크마다 개인키로 서명한다. RSA 개인키 연산이 ECDSA 보다 비싸다.
차이는 keep-alive 를 껐을 때만 드러나고, 켜면 둘이 비슷해질 것이다.
**배수는 예측하지 않는다.** 재서 확인한다.

**H4 — nginx 로 TLS 를 옮기면 앱 CPU 가 내려가고, 그 비용이 nginx 로 이동한다.**
합계 CPU 는 오히려 늘 수 있다(프록시 홉이 추가되므로). 그런데도 이득인 이유는
**앱은 코어를 하나밖에 못 쓰고 nginx 는 여러 개를 쓰기 때문**이다. 병목 자원이 서로 다르다.

**H5 — 프록시 홉 자체에도 비용이 있다.**
그래서 `nginx 평문 통과`를 따로 잰다. 이걸 빼지 않으면 TLS 비용이 과대평가된다.

### 예상하지만 이 환경에서는 못 재는 것

- **TLS 1.3 이 1.2 보다 왕복 1번 적은 효과**: localhost 라 RTT 가 거의 0 이다.
  지연 시간으로는 안 보인다. CPU 차이는 보인다.
- **OCSP stapling**: 자체서명 인증서라 인증기관이 없다. 설명으로만 남긴다.
- **0-RTT**: 세션 재개를 껐고, 재전송 위험 때문에 쓰기 라우트에는 어차피 부적합하다.

## 설정

### Phase 01 대비 바뀐 것

| 항목 | 내용 |
|---|---|
| 앱 | `TLS_MODE` 환경변수 추가 (`off` / `ecdsa` / `rsa`). **한 실행에 한 모드만** |
| 인증서 | 자체서명 2종. ECDSA P-256, RSA 2048. 나머지 조건(유효기간·SAN·SHA-256) 동일 |
| 세션 재개 | **끔** (`SSL_OP_NO_TICKET`, nginx 는 `ssl_session_cache off`). 핸드쉐이크 비용을 희석 없이 재기 위함 |
| nginx | 신규. 8080=평문 통과, 8443=TLS 종료. `worker_processes auto`, 업스트림 keepalive 128 |
| cAdvisor | 신규. **Phase 01 의 숙제**(k6 가 병목이 아니라는 근거가 간접적)를 해결. nginx CPU 측정에도 필요 |
| HTTP/2 | **끔.** 별개의 변수다. 한 번에 하나만 바꾼다 |

바꾸지 않은 것: 앱 코드의 라우트 로직, 커넥션 풀(기본값 10), Postgres 설정, `HOT_RATIO=0`.

### 측정 방식 — 왜 계단이 아니라 고정 부하인가

Phase 01 은 계단으로 breaking point 를 찾았다. 이번엔 **고정 300 RPS / 90초**로 잰다.

이유:
1. 구성이 8가지다. 매번 사다리를 타면 한 시간이 넘는다.
2. 더 중요한 이유 — **포화 구간에서는 요청당 CPU 를 깨끗하게 잴 수 없다.** 큐가 쌓이면
   CPU 가 대기열 관리에도 쓰여서 "요청 하나의 순수 비용"이 오염된다.
3. Phase 01 에서 `천장 = CPU 상한 ÷ 요청당 CPU` 모델이 실측과 맞는 것을 확인했다
   (518µs → 예측 1930 RPS, 실측 2000 RPS). 그래서 **천장보다 한참 낮은 곳에서 요청당 CPU 만
   정확히 재고 천장은 환산**한다. 환산값은 마지막에 사다리 1회로 검증한다.

RSA + 핸드쉐이크 강제 구성은 비싸므로, 300 RPS 는 모든 구성에서 포화되지 않을 만큼 낮게 잡은 값이다.

### 8개 구성

| 이름 | TLS 종료 | 인증서 | keep-alive | 재는 것 |
|---|---|---|---|---|
| `a-http` | 없음 | — | 켬 | Phase 01 기준선 재확인 |
| `b-ecdsa-reuse` | 앱 | ECDSA | 켬 | **TLS 평상시 비용** |
| `c-ecdsa-noreuse` | 앱 | ECDSA | **끔** | **핸드쉐이크 진짜 비용** |
| `d-rsa-reuse` | 앱 | RSA | 켬 | (b)와 비교 |
| `e-rsa-noreuse` | 앱 | RSA | **끔** | **RSA vs ECDSA** |
| `f-nginx-http` | 없음 | — | 켬 | **프록시 홉만의 비용** |
| `g-nginx-tls-reuse` | nginx | ECDSA | 켬 | |
| `h-nginx-tls-noreuse` | nginx | ECDSA | **끔** | **오프로딩 효과** |

`insecureSkipTLSVerify: true` 를 쓴다. 자체서명이라 필요하지만, **실서비스에서는 절대 쓰면 안 되는 설정**이다.

VM 을 재기동했음에도 기준선이 재현됐다는 뜻이고, 이번 비교의 토대가 흔들리지 않았다는 근거다.

### 2) 환산 천장 검증 — 사다리 실측 (ECDSA, 핸드쉐이크 강제)

`TLS 핸드쉐이크 avg=135.15ms p99=2126.39ms` — 핸드쉐이크가 실제로 발생했음을 요약에서 확인했다.

| 계단 | 실측 RPS | p50 | p95 | p99 | **앱 CPU avg/max** | 풀 대기 max | 획득대기 p99 | k6 드롭 |
|---|---|---|---|---|---|---|---|---|
| 600 | 600 | 2.4ms | 20.3ms | 24.7ms | 0.81/0.96 | 0 | <1ms | 0 |
| 700 | 700 | 2.5ms | 18.7ms | 24.3ms | 0.88/0.93 | 0 | 5.0ms | 0 |
| 800 | 800 | 5.5ms | 19.1ms | 32.1ms | 0.93/1.01 | 0 | 18.2ms | 105 |
| 900 | 893 | 7.1ms | 36.2ms | 108.8ms | **1.00/1.06** | 18 | 93.8ms | 425 |
| 1000 | **1004** | 7.2ms | 37.7ms | 87.7ms | **1.01/1.07** | 109 | 75.8ms | 109 |
| 1100 | **969** | 8.2ms | 136.5ms | **214.0ms** | 1.04/1.09 | 146 | 195.7ms | **5486** |

**실측 천장 약 1000 RPS.** (1000 요구 → 1004 소화, 1100 요구 → 969 로 후퇴 + 드롭 5486)

| | 값 |
|---|---|
| 환산 예측 | 848 RPS |
| 실측 | 약 1000 RPS |
| 오차 | **약 +18% (예측이 비관적)** |

**왜 빗나갔나 — 가정이 부분적으로 틀렸다.**
"TLS 증분은 부하 수준에 덜 의존한다"고 가정했는데, 실제로는 증분도 부하에 따라 줄었다.

```
300 RPS  구간: 증분 741µs/req   (0.474 − 0.252) ÷ 300
1000 RPS 구간: 증분 408µs/req   (1.01 − 0.60) ÷ 1004     ← Phase 01 의 1000 RPS HTTP CPU 0.60 과 비교
```

부하가 높을수록 요청 하나가 싸지는 현상(배칭·캐시 지역성)이 **기본 처리에도, TLS 처리에도** 나타난다.
그래서 낮은 부하에서 잰 증분으로 천장을 환산하면 비관적으로 나온다.
방향과 자릿수는 맞았지만(2000 → 절반 수준), 정확한 절대값은 결국 사다리로 재야 했다.

## 병목 원인

### 결론: TLS 핸드쉐이크는 앱의 단일 JS 스레드를 직접 갉아먹는다. 다만 keep-alive 가 있으면 거의 무료다.

**근거 1 — keep-alive 가 있으면 HTTPS 는 HTTP 와 구분되지 않는다. (H1 맞음)**

ECDSA 재사용 구성의 TLS 증분은 **−14µs**다. 음수이므로 측정 노이즈 범위이고, 곧 **차이 없음**이다.
핸드쉐이크는 커넥션을 새로 뚫을 때만 발생하고, 이후 남는 것은 대칭키 암호화(AES-GCM)뿐이다.
M1 에는 AES 하드웨어 가속이 있어 이 비용이 측정에 잡히지 않았다.

**근거 2 — 핸드쉐이크를 강제하면 천장이 절반이 된다. (H2 맞음)**

```
HTTP           : 2000 RPS (Phase 01 실측)
HTTPS 핸드쉐이크: 1000 RPS (이번 실측)
```

요청 하나의 순수 처리 비용이 515µs 인데, 300 RPS 구간에서 핸드쉐이크가 741µs 를 더 썼다.
**핸드쉐이크가 실제 업무보다 비싸다.** 스위치 하나(keep-alive)로 서버 용량이 2배 갈린다.

**근거 3 — 인증서 키 종류가 서버 용량을 바꾼다. (H3 맞음)**

| | TLS 증분/req | 클라 핸드쉐이크 대기 | 환산 천장 |
|---|---|---|---|
| ECDSA P-256 | +741µs | 0.75ms | 848 RPS |
| RSA 2048 | +1323µs | 1.45ms | 580 RPS |

두 구성의 나머지 조건은 전부 동일하므로, 차이 **582µs/핸드쉐이크**는 순수하게 서명 알고리즘 몫이다.
**코드 한 줄 안 바꾸고 인증서 파일만 교체해도 처리 용량이 1.46배 차이난다.**
그리고 재사용 구성에서는 +47µs vs −14µs 로 차이가 사라진다 — 예상대로 **핸드쉐이크할 때만** 드러난다.

**근거 4 — 프록시로 옮기면 앱은 TLS 를 전혀 느끼지 않는다. (H4 맞음)**

```
앱이 직접 핸드쉐이크 : 앱 CPU 0.474  → 848 RPS
nginx 가 핸드쉐이크  : 앱 CPU 0.253  → 2053 RPS      (HTTP 의 0.252 와 사실상 동일)
                       nginx CPU 0.175
```

**단, nginx 가 마법처럼 싼 것이 아니다.** nginx 의 핸드쉐이크당 비용을 계산하면
`0.175 코어 ÷ 300/s ≈ 583µs` 로, Node 의 741µs 와 같은 자릿수다.
**진짜 차이는 그릇의 크기다.** Node 의 JS 실행은 스레드 하나라 1 코어가 상한이고,
nginx 는 워커 프로세스를 여러 개 띄워 여러 코어에 흩는다. 비용이 아니라 **확장 가능성**이 다르다.

**근거 5 — 프록시 홉 자체도 공짜가 아니다. (H5 맞음)**

`nginx HTTP 경유` 구성에서 앱 CPU 증분 +31µs, p99 는 4.7 → 8.9ms 로 올랐다.
이 값을 빼지 않으면 TLS 비용이 과대평가된다. 대조군을 따로 둔 이유다.

### Phase 01 의 숙제 해결

`k6 CPU` 열이 0.163~0.411 로, 상한 1.5 의 최대 27% 였다.
Phase 01 에서 "k6 가 병목이 아니라는 근거가 간접적"이라 남겨둔 항목을 **직접 측정으로 확정**했다.

### 계측 자체가 시스템을 죽인 사건

측정 도중 **Prometheus 가 OOM 으로 강제 종료**됐다(`exit 137`, `oom=true`).

원인은 이번에 추가한 **cAdvisor** 였다. cAdvisor 는 컨테이너뿐 아니라 호스트의 모든 cgroup 에 대해
지표를 내보내는데, 이를 2초 간격으로 수집하자 Prometheus 의 1GB 한도를 넘겼다.
로그에 `Error on ingesting out-of-order samples ... num_dropped=76` 가 반복되고 있었다.

**그리고 cAdvisor 는 실제로 쓰이지도 않았다.** colima 환경에서 컨테이너 이름 라벨(`name`)을 붙이지
못해 이미 `docker stats` 샘플러로 대체한 상태였다. **쓰지 않는 관측 도구가 관측 시스템을 죽였다.**

조치: cAdvisor 제거, Prometheus 메모리 2GB 로 상향, k6 원격쓰기 주기 1초 → 5초
(`flushed ... took 1.27s while flush period is 1s. Some samples may be dropped` 경고가 있었다).

교훈: **관측은 공짜가 아니며, 관측 자체가 측정 대상의 일부가 된다.**
Phase 01 의 "노트북에서는 측정하는 사람도 시스템의 일부"와 같은 이야기의 다른 얼굴이다.

## 개선

Phase 02 도 기준선 확장이 목적이라 **성능 개선을 시도하지 않았다.**
다만 이번 측정이 곧바로 알려주는 실무 조치는 명확하다.

| 조치 | 근거 | 효과 |
|---|---|---|
| **keep-alive 를 반드시 살린다** | 재사용 시 TLS 증분 ≈ 0 | 천장 2배 |
| **ECDSA 인증서를 쓴다** | RSA 대비 582µs/핸드쉐이크 절약 | 핸드쉐이크 많은 환경에서 1.46배 |
| **TLS 는 프록시에서 종료한다** | 앱 CPU 0.474 → 0.253 | 앱 천장 유지 |
| 세션 재개를 켠다 | 이번엔 일부러 껐다 | 재접속 시 서명 연산 생략 (미측정) |

## 재측정

### 재현된 것

`HTTP 직결` 구성을 Phase 01 과 다른 날, VM 재기동 후에 다시 쟀다.

| | Phase 01 | Phase 02 |
|---|---|---|
| 요청당 CPU 기반 천장 | 2000 RPS (실측) | 2068 RPS (환산) |
| 300 RPS 지점 앱 CPU | 0.240 (회귀선 예측) | 0.252 (실측) |

**기준선이 재현됐다.** 이 확인이 없었다면 이번 Phase 의 모든 비교가 의심스러웠을 것이다.

### 재현되지 않은 것 / 미해결

- **환산 천장이 18% 비관적이었다.** 원인은 위에 적었다(증분의 부하 의존성).
  Phase 03 이후 환산을 쓸 때는 **비교 대상과 같은 부하 수준에서 잰 증분**을 써야 한다.
- **결과 파일이 두 번 갱신되지 않았다.** `results/tls-ceiling.json` 이 이전 실행 내용 그대로 남았다.
  iCloud dataless 상태의 파일을 컨테이너가 덮어쓰지 못한 것으로 추정하나 **확정하지 못했다.**
  스케줄을 수동 재구성해 분석했고, 원본 로그는 정상이었다.
  → 저장소를 동기화 대상 밖으로 옮기는 일의 우선순위를 올린다.
- **1100 RPS 계단에서 상태코드 0(무응답) 19건**이 나왔다(에러율 0.006%).
  Phase 01 에서는 포화 상태에서도 에러가 0 이었는데, TLS 는 커넥션 수립 단계에서 실패가 발생한다.
  **TLS 는 실패 모드를 하나 더 만든다.**

## TLS termination: 앱서버가 직접 vs LB/프록시가

이번 측정을 근거로 정리한다.

### 실측 대비

| | 앱이 직접 | nginx 가 종료 |
|---|---|---|
| 앱 CPU (핸드쉐이크 강제, 300 RPS) | 0.474 | **0.253** |
| 앱 천장 | 848 RPS | **2053 RPS** |
| 추가 컴포넌트 | 없음 | nginx (0.175 코어) |
| 평문 경유만 해도 드는 비용 | — | +31µs/req, p99 4.7→8.9ms |

### 앱서버가 직접 종료

**유리한 때**
- 컴포넌트가 하나 적다. 배포·장애 지점·설정이 단순해진다.
- **종단간 암호화가 유지된다.** 프록시에서 끊으면 프록시~앱 구간이 평문이 된다.
  금융·의료처럼 내부망도 신뢰하지 않는(제로 트러스트) 요구가 있으면 이쪽이거나, 재암호화가 필요하다.
- 앱이 클라이언트 인증서(mTLS)나 협상된 암호 정보를 직접 봐야 하는 경우.
- 트래픽이 작아서 핸드쉐이크 비용이 무의미한 경우. **대부분의 서비스가 여기 해당한다.**

**불리한 때**
- **런타임이 코어를 못 늘리면 치명적이다.** 이번 실측이 그 사례다.
  Node 는 JS 스레드가 하나라 TLS 계산이 곧바로 요청 처리 예산을 깎았다(천장 2000 → 848).
  Go/Java 처럼 멀티스레드로 도는 런타임이면 타격이 훨씬 작다. **런타임에 따라 결론이 달라진다.**
- 인증서 갱신을 앱 인스턴스 수만큼 배포해야 한다. 재기동 없이 갱신하기도 번거롭다.

### LB / 프록시가 종료

**유리한 때**
- **병목 자원을 분리한다.** 이번 실험의 핵심이다. nginx 는 핸드쉐이크당 비용이 Node 와 비슷했지만
  워커를 여러 개 띄워 여러 코어를 쓴다. 앱은 못 하는 일이다.
- **인증서를 한 곳에서 관리한다.** 갱신·교체가 앱 배포와 분리된다.
- 앱을 여러 대로 늘려도 TLS 설정은 한 벌이다.
- 프록시가 느린 클라이언트를 흡수하고, 뒤쪽으로는 keep-alive 로 커넥션을 재사용한다
  (이번 nginx 설정의 `keepalive 128` 이 그 역할이다).

**불리한 때 / 주의**
- **프록시~앱 구간이 평문이 된다.** 같은 호스트나 신뢰 네트워크가 아니면 위험하다.
- 프록시 자신이 새 단일 장애점이자 새 병목이 된다. → Phase 04(로드밸런싱·헬스체크)의 주제다.
- 홉이 하나 늘어난 값을 낸다(실측 +31µs/req, p99 +4.2ms).
- 클라이언트 IP·프로토콜 정보가 사라진다. `X-Forwarded-For` 같은 헤더로 넘겨줘야 하고,
  그걸 신뢰할지 말지가 또 하나의 보안 문제가 된다.
- **세션 재개가 깨질 수 있다.** 프록시가 여러 대면 재접속이 다른 프록시로 갈 수 있다.
  session ID 방식은 그 서버의 기억이 없어 재개에 실패한다.
  session ticket 방식은 **티켓 암호화 키를 프록시들끼리 공유**해야 한다. → Phase 04 에서 다룬다.

### 판단 기준 한 줄

> **런타임이 코어를 늘려 쓸 수 있으면 앱에서 끊어도 된다. 못 늘리면 반드시 앞에서 끊어야 한다.**
> 그리고 프록시~앱 구간을 평문으로 두어도 되는 신뢰 경계인지를 먼저 확인해야 한다.

이번 프로젝트는 Node 단일 프로세스이므로 **앞에서 끊는 쪽이 정답**이고, 실측이 그것을 보여준다.

### 이 환경에서 답하지 못한 것

- **TLS 1.3 이 1.2 보다 왕복 1번 적은 이득**: localhost 라 RTT ≈ 0 이다.
  서버 간 거리가 있는 환경(예: 왕복 150ms)이면 첫 응답이 눈에 띄게 빨라지지만, 여기서는 안 보인다.
  CPU 비용 차이는 이번 측정에 포함되어 있다.
- **OCSP stapling**: 자체서명 인증서라 인증기관이 없어 측정 불가.
  개념상 이것이 아끼는 것은 **서버 CPU 가 아니라 클라이언트의 왕복**이다.
  stapling 이 없으면 클라이언트가 인증서 폐기 여부를 확인하러 CA 에 따로 접속해야 한다.
- **0-RTT**: 세션 재개를 끄고 측정했다. 또한 재전송 공격에 노출되므로
  이 프로젝트의 쓰기 라우트에는 부적합하다. 다만 `Idempotency-Key` 가 있어 재전송 자체는 안전하다.
