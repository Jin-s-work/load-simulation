# 04. 앱서버 자체의 물리적 한계

Phase: 04 · 2026-08-06 ~ 08-07

Phase 01~03 의 병목은 늘 **앱의 단일 JS 스레드**였다. 다만 그건 "DB 왕복 5번"이 만든
자연스러운 비용이었다. 이번엔 CPU 와 메모리를 **직접 태워서** 물리적 벽을 만든다.

컨테이너를 `cpus=1.0, mem=512m` 로 못 박아 벽을 정확히 만들고,
이벤트 루프 지연·GC 일시정지가 p99 와 어떤 관계인지 보고, 큐가 폭발하는 순간을 잡은 뒤
보호 장치를 넣어 전후를 비교한다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — 요청당 CPU 를 X ms 넣으면 처리량 천장은 `1000/X` RPS 가 된다. 스레드가 하나이므로.
**H2** — 동기 연산은 이벤트 루프를 막고, 루프 지연이 p99 를 끌어올린다.
**H3** — 같은 연산을 비동기(스레드풀)로 옮기면 루프 지연은 사라지고 처리량은 유지되거나 좋아진다.
**H4** — 요청당 큰 객체를 만들면 GC 압박으로 p99 꼬리가 길어지고, 한계를 넘기면 OOM 이 난다.
**H5** — 워커 수를 늘리면 처리량이 그만큼 늘어난다.
**H6** — 유입이 용량을 넘으면 in-flight 가 선형으로 자라고 지연이 폭발한다(λ>μ).
**H7** — load shedding 을 넣으면 성공 처리량은 유지되면서 지연이 극적으로 짧아진다.

## 설정

### 자원 한계 (이번 Phase 의 전제)

| 항목 | 값 |
|---|---|
| 앱 컨테이너 | **`cpus: 1.0`, `mem_limit: 512m`** |
| 구조 | **앱 1대 직결.** LB 를 거치지 않는다 (앱 자체의 한계를 보려면 변수를 줄여야 한다) |
| 부하 | 고정 300 RPS / 90초 (실험별로 조정) |
| DB / 풀 | 변경 없음 (Postgres 기본값, 풀 10) |

### 앱에 추가한 손잡이 — `app/src/overload.js`

**[부하 주입]**

| 변수 | 하는 일 |
|---|---|
| `CPU_BURN_MS` | 요청당 `pbkdf2Sync` 로 지정 시간만큼 CPU 를 태운다 |
| `CPU_BURN_ASYNC` | 1 이면 비동기 `pbkdf2` — libuv 스레드풀에서 돌아 루프를 막지 않는다 |
| `ALLOC_KB` | 요청당 객체를 그만큼 만든다 |
| `ALLOC_HOLD` | 만든 것을 몇 개나 붙잡아 둘지 (GC 가 바로 회수 못 하게) |

반복 횟수는 하드코딩하지 않고 **기동 시 한 번 재서** 정한다. 하드코딩하면 다른 기계에서
전혀 다른 부하가 된다. 로그에 `cpuBurn=20ms(9695iter/ms,sync)` 처럼 찍힌다.

**[보호 장치]**

| 변수 | 하는 일 |
|---|---|
| `MAX_CONCURRENT` | bulkhead — 동시 처리 상한 |
| `SHED_INFLIGHT` | 큐 길이 기반 load shedding |
| `SHED_LOOP_LAG_MS` | 루프 지연 기반 load shedding |
| `REQUEST_TIMEOUT_MS` | 요청 타임아웃 |
| `CLUSTER_WORKERS` | Node cluster 워커 수 |
| `UV_THREADPOOL_SIZE` | libuv 스레드풀 크기 |

판단은 **일을 시작하기 전에** 한다. DB 트랜잭션을 연 뒤 거절하면 자원을 쓰고도 실패한 것이 된다.

### 이벤트 루프 지연을 직접 잰다

```js
let expected = Date.now() + 100;
setInterval(() => {
  loopLagMs = Math.max(0, Date.now() - expected);   // 예약 시각 vs 실제 시각
  expected = Date.now() + 100;
}, 100);
```

Phase 01 에서 `prom-client` 의 `nodejs_eventloop_lag_*` 가 저부하에서도 12~22ms 의
노이즈 바닥을 보여 **판별력이 없다**고 판단했다. 이건 그 대안이고, load shedding 판단에
쓰려면 요청마다 즉시 읽을 수 있어야 해서 스크레이프 시점에만 읽히는 히스토그램으로는 부족했다.

### 클러스터에서 지표가 깨지는 문제

워커가 N 개면 프로세스가 N 개이고 각자 지표를 센다. `/metrics` 는 포트 3000 하나이고
커널이 요청을 워커들에게 나눠주므로, **긁을 때마다 아무 워커 하나의 지표**만 받게 된다.
요청 수가 1/N 로 보이는 완전히 틀린 값이 된다.

처음엔 `prom-client` 의 `AggregatorRegistry`(프라이머리가 IPC 로 수집)를 썼으나
워커 응답이 오지 않아 타임아웃했다. 원인을 더 파는 대신 **워커마다 전용 지표 포트**(3010+id)를
여는 쪽으로 갔다. 부수 효과로 **워커별 루프 지연을 따로 볼 수 있게 되어** 오히려 분석에 유리해졌다.

분석 시에는 워커 수에 따라 선택자를 바꾼다.

```
단일: job="app"          클러스터: job="app_worker"
```

둘을 합치면 이중 계산된다. 실제로 처음엔 `cpus=1.0` 상한인데 CPU 가 **1.62** 로 나왔고,
그 모순으로 버그를 발견했다.

## 병목 원인

### (a) CPU — 이론값이 그대로 맞았다. H1·H2 확인, **H3 반증**

```
요청당 CPU 10ms  →  이론 1000/10 = 100 RPS  →  실측 100.20 RPS
요청당 CPU 30ms  →  이론 1000/30 =  33 RPS  →  실측  34.30 RPS
```

Phase 01 에서 "요청당 515µs → 천장 약 2000 RPS" 를 계산했던 것과 **같은 공식**이다.
그때는 DB 왕복 5번이 만든 자연스러운 비용이었고, 지금은 일부러 넣은 비용일 뿐이다.

**H3 는 틀렸다.** 같은 30ms 를 비동기(스레드풀)로 옮기자:

| | 실측 RPS | 루프지연 avg | 앱 CPU |
|---|---|---|---|
| 동기 | **34.30** | 24ms | 1.00 |
| 비동기 (스레드 4) | **24.10** | **0ms** | 1.00 |
| 비동기 (스레드 16) | **18.95** | 20ms | 0.97 |

**루프 지연은 0 이 됐는데 처리량은 30% 떨어졌다.** 스레드를 16개로 늘리자 더 나빠졌다(18.95).

이유는 **CPU 가 1개**이기 때문이다. 스레드를 늘려도 총 CPU 예산은 그대로이고,
스레드들이 서로 코어를 뺏으며 컨텍스트 스위칭 비용만 추가된다.
`c-threadpool16` 의 GC 점유율이 7.5% 로 가장 높은 것도 같은 맥락이다(스레드마다 스택·오버헤드).

> **"이벤트 루프를 막지 마라"는 조언은 CPU 여유가 있을 때만 유효하다.**
> 비동기로 옮기는 것은 일을 **다른 데로 보내는 것**이지 **없애는 것**이 아니다.

다만 얻는 것이 하나 있다. 루프가 안 막히므로 **헬스체크 같은 가벼운 요청은 응답**할 수 있다.
처리량은 같아도 "완전 먹통"은 피한다. 실제로 비동기 쪽 실패율이 0.232% 로
동기(17.222%)보다 훨씬 낮았다 — **처리량이 아니라 응답성이 개선된 것**이다.

### (b) 메모리 — H4 확인. 다만 **첫 구현이 틀렸다**

처음엔 큰 문자열로 메모리를 채우려 했는데 **아무 일도 일어나지 않았다**(p99 6ms, 실패 0%).
컨테이너 안에서 직접 재 보니 원인이 나왔다.

```
문자열 1MB × 200개    →  힙 3.6MB → 4.3MB     (거의 안 늘어남)
객체 2만개 × 200배열  →  힙 3.6MB → 197MB     (제대로 늘어남)
```

큰 문자열은 V8 의 large object space 로 가고, 단일 문자 반복은 최적화되기도 한다.
**GC 를 실제로 괴롭히는 것은 "작은 객체가 아주 많은 경우"** 다. young generation 을 계속 채워
scavenge 를 유발하고, 살아남은 것들이 old space 로 승격되며 major GC 를 부른다.

객체 배열로 바꾸자 즉시 재현됐다.

| 구현 | 실패율 | p99 | 힙 max | GC 점유율 | 루프지연 |
|---|---|---|---|---|---|
| 문자열 2MB/요청 (틀림) | 0% | 6ms | — | — | — |
| 객체 512KB/요청 | **76.1%** | 30,716ms | **249MB** | **4.6%** | **133/210ms** |
| 객체 512KB, 700MB 유지 | **84.2%** | 33,797ms | — | — | — |

**GC 가 CPU 를 대신 잡아먹는다는 증거**: `b-alloc512` 의 앱 CPU 는 **0.24** 로 낮은데
성공 RPS 는 28.7 밖에 안 됐다. CPU 가 남는데 처리를 못 한 것이다.
루프 지연 133ms 평균이 그 답이다 — **GC 일시정지 동안 이벤트 루프가 멈춰 있었다.**

`b-oom` 의 **p50 이 0ms** 인 것이 결정적이다. 절반 이상의 요청이 아무 시간도 안 걸리고
실패했다는 뜻으로, 정상 처리가 아니라 커넥션 자체가 안 된 것이다.
700MB 를 붙잡으려는데 상한이 512MB 이므로 프로세스가 죽고 다시 뜨기를 반복했다.

> **한계**: 객체 할당은 CPU 도 쓴다. (b) 는 메모리만 순수하게 분리하지 못했다.

### (c) 동시성 — **H5 반증. 워커를 늘려도 처리량이 안 늘었다**

| 워커 수 | 실측 RPS | 루프지연 avg/max | 힙 max |
|---|---|---|---|
| 1 | 35.69 | 24/76ms | 32MB |
| 2 | 35.75 | **406/2286ms** | 50MB |
| 4 | 37.06 | **800/2613ms** | 91MB |

**1 → 4 워커에서 처리량이 4% 늘었다.** 사실상 변화 없음이다.

당연한 결과다. **`cpus=1.0` 이므로 워커가 몇 개든 총 CPU 예산은 1 코어다.**
워커 4개가 1 코어를 나눠 쓰면 각자 0.25 코어씩 받고, 요청 하나에 30ms CPU 가 필요하니
전체 처리량은 그대로다.

오히려 나빠진 것이 있다. **루프 지연이 24ms → 800ms 로 33배 늘었다.**
워커가 CPU 를 못 받아 스케줄되지 못하는 시간이 그대로 루프 지연으로 나타난 것이다.
메모리도 32MB → 91MB 로 늘었다(프로세스마다 자기 힙).

> **수평 확장은 자원이 늘어날 때만 효과가 있다.**
> 같은 CPU 안에서 프로세스만 쪼개는 것은 오버헤드만 추가한다.
> Phase 03 에서 앱을 3대로 늘렸을 때 효과가 있었던 이유는 **컨테이너마다 CPU 가 따로 있었기** 때문이다.

### (d) 큐잉 — H6 확인. 리틀의 법칙과 실측 비교

CPU 30ms 이므로 처리 용량 μ ≈ 33 RPS. 여기에 λ = 120 RPS 를 넣었다.

**리틀의 법칙** `L = λ × W` 로 계산해 보면:

```
정상 상태라면:  L = 33 RPS × 0.03초 = 약 1개
실측 in-flight: 평균 1352개, 최대 1523개
```

**계산값의 1000배가 넘는다.** 이 차이가 곧 **"처리되지 않고 대기만 하는 요청"** 이다.

역으로 리틀의 법칙을 쓰면 대기 시간을 예측할 수 있다.

```
W = L / λ = 1352 / 33 ≈ 41초
실측 p50 = 21.9초,  p99 = 60초(k6 타임아웃)
```

자릿수가 맞는다. **큐 길이만 알면 대기 시간을 계산할 수 있다**는 뜻이고,
이것이 load shedding 을 "큐 길이" 기준으로 판단하는 근거가 된다.

초과분이 매초 87개씩(120 − 33) 쌓이므로 90초면 약 7,800개다.
실측 in-flight 가 1,500 에서 멈춘 것은 k6 의 `maxVUs=1200` 상한 때문이다.
**상한이 없었다면 계속 자랐을 것이다. λ>μ 에서는 안정 상태가 존재하지 않는다.**

## 개선

### 적용한 것 4가지

| 장치 | 설정 | 판단 근거 |
|---|---|---|
| 타임아웃 | `REQUEST_TIMEOUT_MS=500` | 경과 시간 |
| bulkhead | `MAX_CONCURRENT=50` | 동시 처리 수 |
| load shedding | `SHED_INFLIGHT=50`, `SHED_LOOP_LAG_MS=300` | 큐 길이 + 루프 지연 |
| 클러스터 | `CLUSTER_WORKERS=4` | — |

### 전후 비교 (모두 cpu 30ms · 120 RPS 유입)

| | 성공 RPS | **p50** | **p99** | 실패율 | 실패 종류 |
|---|---|---|---|---|---|
| **무보호** (d-queue) | 33.9 | **21,914ms** | 60,029ms | 9.6% | 응답 없음 |
| 타임아웃 500ms | 0.1 | 2,768ms | 59,997ms | **99.8%** | 504 + 응답 없음 |
| **bulkhead 50** | **34.0** | **88ms** | 5,662ms | 70.6% | 503 |
| **shedding** | **35.8** | **493ms** | **2,934ms** | 68.7% | 503 |
| 전부 (워커4 포함) | 30.8 | 572ms | 3,408ms | 71.6% | 503 + 504 |

**핵심 결과 — 성공 처리량은 그대로인데 지연이 250배 짧아졌다.**

```
무보호 : 성공 33.9 RPS, p50 21,914ms
shedding: 성공 35.8 RPS, p50    493ms     <- 44배 개선
bulkhead: 성공 34.0 RPS, p50     88ms     <- 250배 개선
```

성공 처리량이 셋 다 **33~36 RPS 로 같다.** 이론 용량(33 RPS)과 일치한다.
**보호 장치는 처리량을 늘리지 않는다. 처리량은 어차피 CPU 가 정한다.**
바꾸는 것은 **"남는 부하를 어떻게 처리하느냐"** 다 —
무보호는 줄을 세우고(21초 대기), shedding 은 즉시 돌려보낸다(493ms 안에 답).

### 타임아웃만으로는 최악이었다 — 실패율 99.8%

이건 예상하지 못한 결과가 아니라, 구현할 때 주석에 적어둔 한계가 그대로 나온 것이다.

```js
// 주의: 이건 "응답을 포기"할 뿐 실제 작업을 중단시키지는 못한다.
// 이미 시작한 DB 트랜잭션은 계속 돈다.
```

`Promise.race` 로 만든 타임아웃은 **먼저 끝나는 쪽의 결과를 쓸 뿐**이고,
진 쪽(CPU 연산, DB 작업)은 계속 돈다. 자바스크립트에는 실행 중인 작업을 강제 중단하는 수단이 없다.

그래서 이런 일이 벌어졌다.

```
요청 도착 → 큐에 쌓임 → 500ms 지나 타임아웃 504 반환
         → 그런데 서버는 그 요청의 CPU 연산을 여전히 수행 중
         → 큐는 줄지 않음 → 다음 요청도 타임아웃 → ...
```

**응답만 빨리 포기하고 일은 계속했으니, 자원을 다 쓰고도 거의 전부 실패했다.**

> **타임아웃은 사용자를 구하고, load shedding 은 서버를 구한다.**
> 타임아웃만 있으면 사용자도 서버도 못 구한다. 반드시 **받지 않는 장치**와 같이 써야 한다.

### 클러스터 4워커를 더했더니 오히려 나빠졌다

`fix-shed`(p99 2,934ms) 보다 `fix-all`(p99 3,408ms) 이 나빴고, 성공 RPS 도 35.8 → 30.8 로 줄었다.
(c) 에서 본 그대로다 — **CPU 가 1개인데 프로세스를 4개로 쪼개면 손해다.**
루프 지연도 434ms → 1,344ms 로 3배 늘었다.

**교훈: 개선책을 겹쳐 쌓는다고 좋아지지 않는다.** 병목에 맞는 것만 골라야 한다.

### bulkhead vs shedding 의 차이

| | p50 | p99 | in-flight |
|---|---|---|---|
| bulkhead (동시 50 고정) | **88ms** | 5,662ms | 51/51 (딱 고정) |
| shedding (큐50 + 루프지연300ms) | 493ms | **2,934ms** | 32/48 (변동) |

- **bulkhead 는 p50 이 좋다.** 동시 수를 딱 잘라 고정하니 통과한 요청은 거의 안 기다린다.
- **shedding 은 p99 가 좋다.** 루프 지연까지 보고 판단하므로 "서버가 실제로 힘든" 상황을
  더 이르게 감지해 미리 거절한다. in-flight 가 48까지만 올라간 것이 그 결과다.

둘 다 쓰는 것이 맞다. bulkhead 로 상한을 못 박고, shedding 으로 상한 아래에서도
서버가 힘들면 먼저 덜어낸다.

## 재측정

- **CPU 실험은 두 번 모두 이론값과 일치**했다 (`c-workers1` 35.69 vs `a-cpu30` 34.30, 오차 4%).
  같은 조건을 다른 날 다른 배치에서 잰 값이라 재현성이 확인됐다.
- **메모리 실험은 첫 구현이 틀렸고, 고친 뒤 재현됐다.** 틀린 구현의 숫자는 폐기한다.
- **Prometheus 데이터 일부 소실**: 디스크 고갈 사고로 `a-cpu30`, `b-oom`, `c-workers1`,
  `fix-timeout` 의 서버측 지표가 남지 않았다. k6 클라이언트 측정치는 온전해서 그것으로 보고했다.

### 사고 기록 — 디스크 고갈이 데이터를 망가뜨렸다

실험 도중 디스크가 가득 차 **Bash 명령조차 실행할 수 없는 상태**가 됐다.
더 나아가 컨테이너 이미지 저장소가 파일시스템 수준에서 손상됐다.

```
blob sha256:d008c28... input/output error
```

`docker system prune` 조차 손상된 블록을 못 읽어 실패했고, VM 을 재기동해
파일시스템 저널이 복구된 뒤에야 정리됐다. **볼륨은 무사**해서 Phase 01~03 측정 데이터는 살았다
(정리할 때 `--volumes` 를 붙이지 않은 덕분).

> **디스크 고갈은 "공간이 없다"로 끝나지 않는다. 쓰다 만 파일이 남아 데이터를 망가뜨린다.**

## 설명 요청 항목

### 느려지는 것보다 빨리 거절하는 게 나은 이유

이번 측정이 그 답을 그대로 보여준다.

```
무보호   : 성공 33.9 RPS,  p50 21,914ms,  실패 9.6%(응답 없음)
shedding : 성공 35.8 RPS,  p50    493ms,  실패 68.7%(503)
```

**실패율은 7배 늘었는데 이게 개선이다.** 이유가 여섯 가지다.

**① 아무도 안 받을 답을 만들고 있다.** 사용자가 21초를 기다리다 떠났는데 서버는 계속
그 요청을 처리한다. 완성해도 받을 사람이 없다. 가장 바쁠 때 쓸모없는 일에 자원을 쓴다.

**② 재시도 폭풍.** 느려지면 클라이언트가 타임아웃 후 재시도하고, 부하가 2~3배가 된다.
**느려지는 것이 부하를 늘리는 양의 피드백**이다. 빨리 거절하면 이 고리가 끊긴다.

**③ 큐 자체가 자원을 먹는다.** 실측에서 in-flight 가 1,352개였다. 이 요청들은 각각
메모리·소켓·fd 를 차지한다. 줄이 길수록 처리 중인 요청까지 느려진다.

**④ λ > μ 에서는 안정 상태가 없다.** "조금만 느려지고 마는" 지점이 존재하지 않는다.
시간이 갈수록 계속 나빠진다. 유일한 해법은 λ 를 줄이는 것 = 거절이다.

**⑤ 꼬리 지연은 전파된다.** 마이크로서비스에서 A 가 느려지면 A 를 부른 B 도 느려진다.
빠른 거절은 여기서 멈춘다. B 는 503 을 즉시 받고 폴백을 실행할 수 있다.

**⑥ 거절은 정보다.** 503 을 빨리 주면 클라이언트가 선택할 수 있다 — 캐시 사용, 축소된 화면,
다른 리전, 나중에 재시도. 느리면 아무것도 못 하고 기다린다.
그래서 우리 구현은 `Retry-After: 1` 헤더를 같이 보낸다.

> **70% 를 즉시 거절하고 30% 를 493ms 에 처리하는 것이,
> 100% 를 21초 걸려 처리하는 것보다 낫다.** 앞은 부분 가용이고 뒤는 전체 장애다.

### Backpressure 와 Circuit Breaker 의 차이

둘 다 과부하 대응이라 헷갈리지만 **방향이 정반대**다.

```
        ┌──────────── backpressure ────────────┐
        │   "나 벅차니 그만 보내"                │
        ▼                                       │
  [클라이언트] ──요청──▶ [내 서버] ──호출──▶ [DB/외부API]
                                       │
                                       └──── circuit breaker ────┐
                                            "저쪽 맛갔으니 안 부름"  │
```

| | **Backpressure** | **Circuit Breaker** |
|---|---|---|
| 방향 | **들어오는 것**을 제한 | **나가는 것**을 차단 |
| 무엇을 보나 | 내 큐 길이, 동시성, 루프 지연 | 상대의 실패율·응답시간 |
| 동작 | 수용을 늦추거나 거절(503) | 회로를 열어 호출을 아예 안 함 |
| 상태 | 연속적 — 조절 | 이산적 — 닫힘/열림/반열림 |
| 보호 대상 | **나 자신** | **상대방 + 나** |

**이번 Phase 에서 구현한 것은 전부 backpressure 다.** `shouldShed()` 가 보는 것은
내 in-flight 와 내 루프 지연이지, DB 의 상태가 아니다.

**Circuit breaker 의 상태 전이**

```
닫힘(closed)   정상. 호출을 통과시킴
   ↓ 실패율이 임계치 초과
열림(open)     호출을 아예 안 함. 즉시 실패 반환
   ↓ 일정 시간 경과
반열림(half)   시험 삼아 몇 개만 통과시켜 봄
   ↓ 성공하면 닫힘 / 실패하면 다시 열림
```

**핵심은 "열려 있는 동안 상대에게 가는 부하가 0 이 된다"** 는 점이다.
그래서 상대가 **회복할 시간**을 얻는다. Backpressure 는 이걸 못 한다 —
나를 보호할 뿐, 상대를 쉬게 해주지는 않는다.

Phase 03 의 헬스체크와도 구분된다. 헬스체크로 죽은 서버를 빼는 것은 **LB 가** 하는 일이고,
circuit breaker 는 **애플리케이션이 스스로** 판단해 호출을 끊는 것이다.

**둘은 보완적이다.**

```
[내 서버]
   ├─ 입구: backpressure 로 받는 양 제한        ← 내가 안 무너지게
   └─ 출구: circuit breaker 로 아픈 의존성 차단  ← 상대가 회복하게
```

## Phase 05 로 넘길 것

1. **Circuit breaker 는 아직 구현하지 않았다.** DB 를 의도적으로 느리게 만들고
   앱이 스스로 호출을 끊는 실험이 남았다.
2. **앱 히스토그램의 최대 버킷이 10초**라 그 이상을 구분하지 못한다. 버킷을 늘리거나
   과부하 실험에서는 k6 측정치를 기준으로 삼아야 한다.
3. **총 DB 커넥션 = 인스턴스 수 × 풀 크기.** 다음 Phase(커넥션 풀)의 출발점이다.
4. **저장소를 iCloud 동기화 밖으로 이동** — 이번엔 디스크 고갈로 실제 데이터 손상까지 갔다.
