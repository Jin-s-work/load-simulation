# 06. 앱과 DB 사이에 커넥션 풀러를 넣는다

Phase: 06 · 2026-08-11

Phase 05 에서 **총 커넥션 = 앱 대수 × 풀 크기** 라는 곱셈을 확인했다.
앱 3대 × 풀 40 = 120 으로 `max_connections=100` 을 넘겨 `too_many_clients` 35건을 봤고,
커넥션 하나가 사적메모리 **3.1MB** 를 먹는다는 것도 쟀다.

이번엔 그 곱셈을 끊는다. 앱과 DB 사이에 **PgBouncer** 를 넣어
"앱이 여는 커넥션"과 "DB 가 받는 커넥션"을 분리한다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — 프록시 없이 앱을 3대→6대로 늘리면 DB 커넥션이 30→60 으로 그대로 곱해진다.
**H2** — 앱 6대 × 풀 20 = 120 이면 `max_connections=100` 을 넘겨 연결이 거부된다.
**H3** — PgBouncer(transaction)를 넣으면 **앱 대수와 무관하게** DB 커넥션이 고정된다.
**H4** — 커넥션이 줄면 Phase 05 의 회귀식(`10MB + 3.1MB × 커넥션`)만큼 메모리가 준다.
**H5** — session 모드는 접힘이 거의 일어나지 않는다(1:1).
**H6** — PgBouncer 는 단일 스레드이므로 CPU 를 조이면 여기가 병목이 된다.
**H7** — PgBouncer 가 죽으면 전체 DB 접근이 끊긴다(SPOF).

---

## 설명: 앱 풀이 있는데도 왜 프록시인가

풀 크기 설정은 **앱 인스턴스 하나 기준**이다. DB 가 받는 건 `인스턴스 수 × max` 이고,
**이 총합을 아는 주체가 아무도 없다.** 앱은 자기 10개만 보고, DB 는 합쳐진 결과만 받는다.

| 앱 대수 | 풀 10 | 풀 20 | 풀 40 |
|---|---|---|---|
| 1대 | 10 | 20 | 40 |
| 3대 (Phase 03~05) | 30 | 60 | **120 ✗** |
| **6대 (이번)** | **60** | **120 ✗** | 240 ✗ |

**풀 크기를 하나도 안 바꿔도 앱 대수만 늘리면 터진다.** 그리고 이 곱셈이 특히 나쁜 이유는
방향이 반대이기 때문이다.

```
앱 늘림 -> 처리량 ↑ (원하는 것)
        -> DB 커넥션 ↑↑ -> 프로세스 ↑↑ -> 메모리·스케줄링 ↑↑ -> 처리량 ↓
```

**확장하려는 행위가 확장을 막는다.**

프록시가 하는 일은 하나다 — **총량을 아는 주체를 만든다.**
앱→PgBouncer 커넥션은 소켓 하나(수 KB)지만, PgBouncer→Postgres 커넥션은
**프로세스 하나(수 MB + work_mem)** 다. 비싼 것과 싼 것 사이에 경계를 긋는 것이다.

**앱 풀과 프록시는 대체 관계가 아니다.** 앱 풀을 없애면 매 요청마다 PgBouncer 에
TCP 연결을 새로 열게 된다. 둘 다 필요하다.

## 설명: session / transaction / statement

세 모드의 차이는 **서버 커넥션을 언제 반납하느냐** 하나다.

```
session      클라이언트가 연결을 끊을 때
transaction  COMMIT/ROLLBACK 할 때
statement    쿼리 하나 끝날 때
```

반납이 빠를수록 더 많이 접을 수 있지만, **세션에 남아 있어야 할 상태**가 깨진다.

| 기능 | session | transaction | statement |
|---|:--:|:--:|:--:|
| 멀티문 트랜잭션 | ✅ | ✅ | **❌** |
| `SET` 세션 변수 | ✅ | ❌ | ❌ |
| 세션 레벨 advisory lock | ✅ | ❌ | ❌ |
| `LISTEN` / `NOTIFY` | ✅ | ❌ | ❌ |
| 임시 테이블 | ✅ | ❌ | ❌ |
| 명명된 prepared statement | ✅ | ⚠️ | ❌ |
| 트랜잭션 내 advisory lock | ✅ | ✅ | ❌ |
| `SELECT FOR UPDATE` | ✅ | ✅ | ❌ |

깨지는 이유는 전부 같다 — **다음 쿼리가 다른 서버 커넥션으로 갈 수 있기 때문**이다.

```
BEGIN; SET work_mem='64MB'; COMMIT;   ← 서버 커넥션 A 에 설정됨
SELECT ...                             ← 서버 커넥션 B 로 감. 설정이 없다
```

**advisory lock 이 특히 조용히 깨진다.** `pg_advisory_lock()` 은 세션에 걸리므로
커넥션 A 에 락이 남고, `pg_advisory_unlock()` 은 B 로 가서 아무것도 못 푼다.
**에러도 안 난다.** transaction 모드에서는 반드시 `pg_advisory_xact_lock()` 을 써야 한다.

**prepared statement 가 ⚠️ 인 이유**: 프로토콜에 두 종류가 있다.

```
unnamed :  Parse("") -> Bind -> Execute        한 번 쓰고 버림
named   :  Parse("stmt_1") -> ... -> Bind("stmt_1")   커넥션에 남음
```

named 는 서버 커넥션에 저장되므로 다음 요청이 다른 커넥션으로 가면
`prepared statement "stmt_1" does not exist` 가 난다.
(PgBouncer 1.21+ 는 `max_prepared_statements` 로 named 도 지원한다.)

**우리 코드는 transaction 모드 호환이다.** 확인한 근거:

```
grep -rn "\.prepare(\|placeholder(" app/src/     -> 없음 (unnamed 를 쓴다)
grep -rn "advisory\|LISTEN\|NOTIFY\|SET "        -> 없음
```

`pg.types.setTypeParser` 는 Node 쪽 파싱이라 서버 세션 상태가 아니다.

**statement 모드는 실험하지 않았다.** 우리 라우트는 `BEGIN ... SELECT FOR UPDATE ...
UPDATE ... INSERT ... COMMIT` 이라 트랜잭션이 쪼개지면 락이 즉시 풀려
재고 차감의 원자성이 깨진다. 측정할 필요 없이 명백한 오류다.

## 설명: 서버리스에서 사실상 필수인 이유

```
전통적:   앱 6대 × 풀 10 = 60          ← 내가 정한 수
서버리스: 동시실행 1000 × 풀 1 = 1000  ← 트래픽이 정하는 수
```

**상한이 트래픽에 연동된다. 잘 될수록 커넥션이 늘고, 성공이 곧 장애가 된다.**
Lambda 동시 실행 기본 한도가 1000 이니 각 인스턴스가 커넥션 하나만 열어도 1000 개다.

게다가 앱 풀의 idle timeout·max lifetime 은 **프로세스가 오래 산다**는 전제 위에 있는데,
서버리스는 그 전제가 없다. 콜드 스타트마다 커넥션을 만들고(= Postgres 가 프로세스를 fork),
인스턴스가 조용히 사라지면 커넥션은 좀비로 남는다. **커넥션 생성/파괴가 정상 동작이 된다.**

그래서 풀러만이 **함수 인스턴스 수와 무관하게 DB 커넥션 수를 고정**할 수 있다.
최적화가 아니라 **아키텍처상 유일한 통제점**이다. RDS Proxy, Supabase Pooler,
Neon proxy 가 전부 이 자리에 있는 이유다.

## 설정

### 구조와 CPU 배분

이 Phase 가 재는 것은 **처리량 확장이 아니라 커넥션 확장**이다.

VM 이 6 CPU 라 앱 6대에 1.0 씩 줄 수 없다. 그래서 **총 앱 CPU 를 2.4 로 고정**했다.

```
3대 구성:  3 × 0.8 = 2.4
6대 구성:  6 × 0.4 = 2.4     <- 총량 동일
```

이렇게 해야 "앱을 늘려서 빨라졌나"가 아니라 "커넥션 수가 어떻게 변했나"만 분리된다.
Phase 04 에서 고정 CPU 를 쪼개봐야 처리량이 안 는다는 걸 이미 확인했으므로
그 변수를 다시 섞을 이유가 없다.

| 항목 | 값 |
|---|---|
| 앱 | 3대(cpus=0.8) 또는 6대(cpus=0.4), `mem=512m` |
| PgBouncer | `edoburu/pgbouncer:v1.23.1-p2`, cpus 1.0(기본) |
| DB | Postgres 16-alpine **설정 무수정**, `max_connections=100` |
| 부하 | 600 RPS / 90초, `HOT_RATIO=0.1` |
| 앱 풀 | 10/앱 (실험별 20) |
| Phase 04/05 주입 | 전부 off (`CPU_BURN_MS=0`, `TX_HOLD_MS=0`, `SLOW_QUERY=0`) |

**앱 코드는 한 줄도 바꾸지 않았다.** 커넥션 문자열의 호스트만 바뀐다.

```
직결   DB_HOST=postgres  DB_PORT=5432
프록시 DB_HOST=pgbouncer DB_PORT=6432
```

앱은 자기가 무엇을 통해 붙는지 모른다. 그게 프록시의 장점 그 자체다.

### 계측 — `SHOW POOLS`

PgBouncer 관리 콘솔을 2초 간격으로 샘플링한다. 이게 이 Phase 의 핵심 증거다.

```
cl_active   앱에서 붙어 활성인 클라이언트 커넥션
cl_waiting  서버 커넥션을 기다리는 클라이언트   <- 프록시 풀이 좁으면 여기가 는다
sv_active   DB 쪽으로 실제로 쓰고 있는 서버 커넥션
sv_idle     DB 쪽 유휴
maxwait     가장 오래 기다린 클라이언트의 대기 시간
```

> **컬럼 위치를 실행해서 확인했다.** PgBouncer 1.23 이
> `cl_active_cancel_req` / `sv_active_cancel` / `sv_being_canceled` 를 끼워 넣어
> 예전 문서의 순서와 다르다. 처음엔 `sv_idle` 을 8번 컬럼으로 읽고 있었는데
> 실제로는 10번이었다. 확인하지 않았으면 **엉뚱한 값을 sv_idle 이라고 기록**할 뻔했다.

### 도구 문제 두 가지

**PgBouncer 가 5432 로 리슨하고 있었다.** 이미지 기본값이다. 그대로 두면
로그만 보고 "postgres 에 붙었는지 pgbouncer 에 붙었는지" 를 구분할 수 없어
`LISTEN_PORT=6432` 로 명시했다.

**앱 4~6호기는 compose profile 로 분리했다.** 기본 구성에서 6대가 뜨면
Phase 01~05 를 재현할 때 커넥션 수가 달라진다. HAProxy 는 6대를 상시 정의하되
안 뜬 인스턴스는 헬스체크로 DOWN 처리된다 — LB 입장에서 "안 뜬 서버"와
"죽은 서버"는 같다.

## 병목 원인

### H1 확인 — 곱셈이 그대로 일어났다

```
앱 3대 -> DB 커넥션 32.0
앱 6대 -> DB 커넥션 50.4     (풀 크기는 10 그대로)
```

**풀 설정을 하나도 안 바꿨는데 앱 대수만으로 커넥션이 늘었다.**
60 이 아니라 50.4 인 것은, Phase 05 에서 확인했듯 node-postgres 가 커넥션을
**필요할 때 하나씩** 열기 때문이다. 상한 60 을 다 쓰지는 않았다.

메모리도 그만큼 늘었다: **111MB → 168MB**.

### H2 확인 — 상한에 닿았고, 관측 도구부터 잃었다

앱 6대 × 풀 20 = 120 을 시도하자:

```
too_many_clients        47건
503 응답                120건
pg_stat_activity 최대   idle 98개   <- max_connections(100) 의 실질 상한
샘플러 마지막 관측      90 커넥션 -> 이후 psql 이 붙지 못해 샘플러 사망
```

Phase 05 의 (a) 와 **똑같은 증상**이다. 그때는 앱 3대 × 풀 40, 이번엔 6대 × 풀 20.
**경로는 달라도 곱이 같으면 같은 곳에서 터진다.**

> **커넥션이 고갈되면 상황을 관찰할 수단부터 잃는다.**
> 표의 어떤 숫자보다 "샘플러가 죽었다"가 이 문제를 잘 보여준다.

### H3 확인 — DB 커넥션이 **22.0 으로 고정**됐다

이게 이번 Phase 의 핵심 결과다.

| | 앱이 연 커넥션 | DB 실제 커넥션 |
|---|--:|--:|
| p3-proxy (앱 3대, 풀 30) | 29.1 | **22.0** |
| p6-proxy (앱 6대, 풀 60) | 50.9 | **22.0** |
| p6-proxy-p20 (앱 6대, 풀 120) | 90.6 | **22.0** |

**앱 대수를 2배로, 앱 풀 상한을 4배로 늘려도 DB 가 받는 커넥션은 22.0 으로 똑같다.**
접힘비가 1.32 → 2.31 → **4.11:1** 로 커졌을 뿐이다.

가장 직접적인 비교는 이것이다.

```
d6-direct-p20   앱6대 × 풀20  직결    -> DB 98개 도달, too_many_clients 47, 503 120건
p6-proxy-p20    앱6대 × 풀20  프록시  -> DB 22.0 고정, 실패 0%
```

**완전히 같은 앱 설정인데, 사이에 프록시가 있느냐 없느냐로 갈렸다.**

### H4 확인 — Phase 05 회귀식이 오차 2% 안에서 재현됐다

Phase 05 에서 뽑은 식: `사적메모리 ≈ 10MB + 3.1MB × 커넥션수`

| DB 커넥션 | 실측 | 추정 | 오차 |
|--:|--:|--:|--:|
| 4.0 | 23MB | 22MB | 4% |
| 7.0 | 32MB | 32MB | 0% |
| 12.0 | 47MB | 47MB | 0% |
| 22.0 | 79MB | 78MB | 1% |
| 32.0 | 111MB | 109MB | 2% |
| 42.0 | 142MB | 140MB | 1% |
| 50.4 | 168MB | 166MB | 1% |

**완전히 다른 구성(프록시 경유)에서도 그대로 맞는다.** 회귀식이 우연이 아니었다.

실제 절감분:

```
d6-direct  DB 커넥션 50.4 -> 168MB
p6-proxy   DB 커넥션 22.0 ->  79MB
                            ────────
                             89MB 절감 (53%)
```

### H5 확인 — session 모드는 접히지 않았고, **실패까지 냈다**

```
cl_active   20/20    <- 앱이 60개를 열려는데 20개만 붙을 수 있었다
cl_waiting  40/40    <- 나머지 40개가 내내 대기
sv_active   20.0     <- DB 커넥션 20개가 전부 묶여 있다
sv_idle      0.0     <- 여유가 없다
maxwait max  84,096.9ms  (84초)
결과        504 × 40건
```

접힘비 **0.91:1** — 사실상 1:1 이다(22.0 중 2개는 샘플러이므로 프록시 몫은 20).

**session 모드는 클라이언트 커넥션 하나가 서버 커넥션 하나를 독점한다.**
클라이언트가 연결을 끊을 때까지 반납하지 않으므로, 앱 풀이 커넥션을 유지하는 한
영원히 묶여 있다. `sv_idle` 이 0.0 인 것이 그 증거다 — 여유 커넥션이 하나도 없었다.

**maxwait 84초**는 어떤 클라이언트가 84초 동안 서버 커넥션을 못 받았다는 뜻이다.
transaction 모드(`p6-proxy`)의 maxwait 은 **0.0ms** 였다.

> **session 모드는 커넥션 수를 줄이지 못한다.** 줄이는 것은 "연결 생성 비용"뿐이다.
> 실무에서 transaction 모드를 쓰는 이유가 이것이다.

### 프록시 풀 크기 곡선 — **Phase 05 에서 못 찾은 최적점이 여기서 나왔다**

| PgBouncer 풀 | k6 p50 | k6 p99 | DB 커넥션 | 메모리 | cl_waiting avg |
|--:|--:|--:|--:|--:|--:|
| 2 | **94.60ms** | **1,454.06ms** | 4.0 | 23MB | **37.7** |
| 5 | 2.69ms | 421.95ms | 7.0 | 32MB | 3.7 |
| **10** | 2.80ms | **154.53ms** | 12.0 | **47MB** | 4.0 |
| **20** | 2.70ms | **148.64ms** | 22.0 | 79MB | 0.0 |
| 40 | 2.83ms | **351.13ms** | 42.0 | 142MB | 0.6 |

**최적점은 10~20 이고, 40 에서는 오히려 나빠졌다** (p99 148.64 → 351.13ms).

Phase 05 에서 앱 풀로는 이 곡선을 못 그렸다. 트랜잭션이 1.9ms 로 너무 빨라
필요 커넥션이 1.14개였고, 풀을 32(총 96)까지 늘려도 경합이 안 생겼다.
**프록시 쪽에서는 커넥션이 실제로 공유되므로 경합이 드러난다.**

풀 2 는 명확한 기아다 — `cl_waiting` 평균 **37.7**, p50 이 2.70ms 에서 **94.60ms** 로 35배.
병목이 DB 가 아니라 `default_pool_size` 로 옮겨갔다.

**메모리까지 보면 10이 가장 경제적이다.** 풀 20 대비 p99 는 6ms 나쁘고 메모리는 32MB 적다.

### H6 확인 — PgBouncer 는 단일 스레드다

`cpus=1.0` → `0.2` 로 조이자:

| | p50 | p99 | cl_waiting avg | sv_active avg |
|---|--:|--:|--:|--:|
| p6-proxy (cpus 1.0) | 2.70ms | **148.64ms** | 0.0 | 4.1 |
| s-cpu02 (cpus 0.2) | 4.78ms | **716.92ms** | **29.5** | 18.9 |

**p99 가 4.8배 나빠졌다.** DB 커넥션은 22.0 으로 같고 실패도 0% 인데,
**프록시가 패킷을 중계하지 못해** 클라이언트 29.5개가 늘 대기 상태였다.

`sv_active` 가 4.1 → 18.9 로 늘어난 것도 같은 이야기다. DB 는 더 바쁜데
처리량은 그대로다 — 프록시가 병목이면 뒤가 아무리 여유로워도 소용없다.

> **Phase 01(앱 단일 스레드), Phase 04(CPU 1개)와 같은 교훈이 세 번째 계층에서 반복된다.**
> 프로세스 하나는 코어 하나만 쓴다.

### `MAX_CLIENT_CONN` 은 프록시가 먼저 거절하는 지점이다

`MAX_CLIENT_CONN=50` 으로 조이자 `cl_active` 가 **50 에서 정확히 멈췄고**,
앱은 `08P01`(프로토콜 위반) 589건을 받아 **실패율 2.577%** 가 됐다.

DB 는 멀쩡했다(커넥션 22.1, 실패 0). **프록시가 방어선 역할을 한 것**이지만,
앱 입장에서는 원인 파악이 어려운 에러다 — `too_many_clients` 처럼 명확하지 않다.

### H7 확인 — SPOF. 그리고 **회복하지 못했다**

부하 중 PgBouncer 를 죽였다.

```
실패율        65.012%
500 Internal  34,578건   <- 대부분
503           1,807건
502              3건
컨테이너 상태  Exited (137) — 런이 끝날 때까지 돌아오지 않았다
```

**`restart: unless-stopped` 를 걸어뒀는데도 재기동되지 않았다.**
`docker kill` 은 Docker 가 "사용자가 의도적으로 멈춘 것"으로 처리하기 때문이다.
결과적으로 이 실험은 **회복 시간을 잰 것이 아니라 "회복하지 못하는 상태"를 잰 것**이다.

**더 중요한 발견은 에러 코드다.** 34,578건이 **500** 으로 나갔다.

원인은 우리 코드에 있다. Phase 05 에서 만든 에러 분류기가 이렇게 돼 있었다.

```js
const transient = ['too_many_clients', 'pool_acquire_timeout',
  'statement_timeout', 'lock_timeout', 'idle_in_tx_timeout', 'deadlock'];
```

프록시가 사라지면 DNS 가 안 풀려 **`ENOTFOUND`** 가 나는데, 이건 목록에 없다.
그래서 500(영구 오류)으로 응답했다.

**실제로는 일시적 장애다.** 클라이언트가 재시도해야 하는 상황인데
"내부 오류"라고 답한 것이다. Phase 04 에서 정리한
"거절은 정보다 — 503 을 빨리 주면 클라이언트가 선택할 수 있다"에 정확히 어긋난다.

## 개선

### 적용

| 개선 | 근거 |
|---|---|
| **PgBouncer transaction 모드 투입** | 커넥션 곱셈을 끊는다 |
| **`default_pool_size` 를 10~20 으로** | 곡선의 최적점 |
| `ENOTFOUND` / `ECONNREFUSED` 를 일시적 오류로 분류 | SPOF 실험에서 발견한 오분류 |

### 버린 대안

- **`max_connections` 를 올린다** — Phase 05 (d) 가 비용을 정량화했다.
  커넥션당 3.1MB 이므로 200 으로 올리면 사적메모리만 630MB 다. 근본 해결이 아니다.
- **앱 풀을 줄인다** — 앱→프록시 커넥션은 싸다(소켓). 줄일 이유가 없고,
  줄이면 Phase 05 (b) 의 풀 기아가 앱 쪽에서 재현된다.
- **PgBouncer 를 앱 사이드카로 배치** — SPOF 는 없어지지만 **접힘 비율을 포기**한다.
  PgBouncer 가 6개면 각자 자기 앱만 알아서 총량을 다시 모르게 된다.
  문제가 한 단계 위로 올라갈 뿐이다.
- **so_reuseport 로 PgBouncer 다중화** — 단일 스레드 병목의 정석 해법이지만,
  이번에 잰 부하(600 RPS)에서는 `cpus=1.0` 이 병목이 아니었다(cl_waiting 0.0).
  **필요하다는 근거가 없어서 넣지 않았다.**

### 프록시 유무 전후 (앱 6대 · 앱 풀 20 · 같은 부하)

| | DB 커넥션 | DB 메모리 | k6 RPS | p99 | 실패율 |
|---|--:|--:|--:|--:|--:|
| **직결** (d6-direct-p20) | **98 (상한 도달)** | 측정 불가 | 486.95 | 117.54ms | **0.214%** |
| **프록시** (p6-proxy-p20) | **22.0** | 79MB | 484.92 | 573.85ms | **0%** |

### 프록시 유무 전후 (앱 6대 · 앱 풀 10)

| | DB 커넥션 | DB 메모리 | k6 RPS | p99 | 실패율 |
|---|--:|--:|--:|--:|--:|
| **직결** (d6-direct) | 50.4 | 168MB | 486.95 | 244.61ms | 0% |
| **프록시** (p6-proxy) | **22.0** | **79MB** | 486.70 | **148.64ms** | 0% |

**커넥션 56% 감소, 메모리 53% 감소, p99 39% 개선, 처리량 변화 없음.**

처리량이 안 변한 것은 **예상된 결과다.** 이 Phase 는 총 앱 CPU 를 2.4 로 고정했고,
Phase 05 에서 필요 커넥션이 1.14개임을 확인했다. 커넥션은 애초에 병목이 아니었다.
**프록시가 바꾼 것은 처리량이 아니라 "확장 가능한 범위"다.**

### p99 는 프록시 홉 때문에 나빠지지 않았다

프록시를 넣으면 네트워크 홉이 하나 늘어난다. 그런데 오히려 p99 가 좋아졌다
(244.61 → 148.64ms). DB 쪽 커넥션이 50.4 → 22.0 으로 줄면서
Postgres 의 프로세스 경합이 줄어든 것으로 보인다.

다만 `p6-proxy-p20` 은 p99 573.85ms 로 나빴다. 앱 풀 상한이 120 이라
클라이언트 커넥션이 90.6개까지 열렸고, `cl_waiting` 이 최대 46 까지 튀었다.
**앱 풀을 무의미하게 크게 잡으면 프록시 앞에서 줄을 서게 된다.**

### 못 고친 것

**SPOF 는 완화하지 못했다.** 대응책 세 가지를 정리했지만
(so_reuseport 다중화 / 앱 사이드카 / 다중화+헬스체크) **어느 것도 측정하지 않았다.**
`s-kill` 은 회복 시간을 재려 했으나 컨테이너가 재기동되지 않아
"회복하지 못하는 상태"만 확인했다. 회복 시간 측정은 Phase 07 이후로 넘긴다.

**`ENOTFOUND` 오분류는 발견만 하고 고치지 않았다.** 고치려면 에러 분류기를
바꾸고 `s-kill` 을 다시 돌려야 하는데, 그건 "한 번에 한 계층" 규칙에서
앱 계층을 다시 건드리는 일이다. Phase 07 시작 시 함께 처리한다.

## Phase 07 로 넘길 것

1. **에러 분류기에 `ENOTFOUND` / `ECONNREFUSED` 를 추가한다.**
   지금은 프록시 장애를 500 으로 답해 클라이언트가 재시도 판단을 못 한다.
2. **SPOF 대응책 실측.** so_reuseport 다중화와 앱 사이드카 배치의
   접힘 비율 / 회복 시간 트레이드오프.
3. **커넥션은 더 이상 병목이 아니다.** DB 커넥션 22개로 486 RPS 를 처리했고
   `sv_active` 는 4.1 뿐이었다. 다음 병목을 찾으려면 **DB 쿼리 자체**를 줄여야 하고,
   그게 Phase 07(캐시)의 출발점이다.
4. **SLO 대비 현황**: 목표 1,000 RPS / p99 < 200ms / 에러율 < 0.1%.
   현재 486 RPS 에서 p99 148.64ms · 실패 0%. **처리량이 목표의 절반이다.**
   총 앱 CPU 2.4 로 고정한 제약 때문이므로, Phase 07 에서는 이 제약을 풀고
   캐시로 DB 왕복을 줄여 처리량을 올리는 것이 과제다.
