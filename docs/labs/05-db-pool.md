# 05. DB를 커넥션 관점에서 터뜨린다

Phase: 05 · 2026-08-11

Phase 01~04 의 병목은 늘 **앱 쪽**이었다. 이번엔 DB 로 내려간다.
주제는 두 개다 — **ORM 커넥션 풀**과 **DB 메모리**.

Phase 03 에서 앱을 1대에서 3대로 늘렸을 때, 커넥션 수는 아무도 신경 쓰지 않았다.
그때 이미 3 × 10 = 30 개를 쓰고 있었다. **수평 확장이 조용히 DB 부하를 3배로 만든 셈**이고,
이번 Phase 는 그 곱셈이 어디서 터지는지 보는 자리다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — 앱 3대 × 풀 40 = 120 이면 `max_connections=100` 을 넘겨 연결이 거부된다.
**H2** — 풀이 너무 작으면 지연의 대부분이 "커넥션 획득 대기"가 된다.
**H3** — 풀 크기를 늘리면 처리량이 오르다가 어느 지점부터 **오히려 나빠진다**(최적점이 존재한다).
**H4** — 커넥션 수에 비례해 Postgres 메모리가 늘어난다.
**H5** — 트랜잭션을 길게 잡거나 락을 경합시키면 커넥션이 물려 풀이 마른다.
**H6** — 느린 쿼리 하나가 풀 전체를 마르게 만든다.
**H7** — 타임아웃 3종, 트랜잭션 범위 축소, 인덱스 추가, 풀 튜닝으로 위 문제들이 개선된다.

## 설명: 풀 파라미터가 각각 막는 문제

네 개는 **무엇을 보호하느냐**가 다르다.

| 파라미터 | 보호 대상 | 없으면 |
|---|---|---|
| **pool size (max)** | **DB** | 앱이 커넥션을 무한정 열어 DB 가 먼저 죽는다 |
| **acquire timeout** | **앱** | 요청이 풀 앞에서 무한정 쌓여 큐가 폭발한다 |
| **idle timeout** | **자원** | 부하가 빠졌는데도 커넥션을 계속 붙잡는다 |
| **max lifetime** | **시간** | 백엔드 메모리 누적, 페일오버 후 좀비 커넥션 |

**pool size 는 앱 인스턴스 하나 기준이다.** DB 가 받는 건 `인스턴스 수 × max` 이고,
**이 총합을 아는 주체가 아무도 없다.** 앱은 자기 10개만 보고, DB 는 합쳐진 결과만 받는다.

**acquire timeout** 은 Phase 04 의 교훈이 그대로 적용된다 — 타임아웃 혼자로는 부족하다.
기다리다 포기해도 앞의 요청들은 여전히 커넥션을 쥐고 있어 큐가 줄지 않는다.

**max lifetime** 은 앞의 셋과 성격이 다르다. "지금 문제"가 아니라 **며칠에 걸쳐 누적되는 문제**를
끊는다. 90초짜리 부하테스트로는 재현할 수 없어서 **이번 Phase 에서 측정하지 않았다.**
개념 설명으로만 남긴다.

## 설명: 커넥션 하나 = 프로세스 하나

Postgres 는 커넥션마다 **OS 프로세스를 fork** 한다. 스레드를 쓰는 대부분의 서버와 다르다.

```
postmaster
├── backend PID 1001   ← 커넥션 1
├── backend PID 1002   ← 커넥션 2
└── ...                   커넥션 100개면 프로세스 100개
```

그래서 커넥션이 비싸다. 커넥션 1개가 먹는 것:

| 항목 | 크기 | 언제 |
|---|---|---|
| 프로세스 기본 | 수 MB | 접속 즉시 |
| `work_mem` | 4MB | 정렬/해시 **노드마다** |
| `temp_buffers` | 8MB | 임시 테이블 사용 시, **세션 끝까지 유지** |
| 카탈로그 캐시 | 수백 KB~ | 쓸수록 누적 |

`work_mem` 이 가장 위험하다. 커넥션당이 아니라 **실행 계획의 노드당**이다.
정렬 3번 + 해시조인 2번이면 한 쿼리가 4MB × 5 = 20MB 를 쓴다.
100 커넥션 × 5 노드 × 4MB = **2GB** 가 최악값이고, `shared_buffers` 는 128MB 뿐이다.

## 설명: 유휴 커넥션은 공짜가 아니다

**idle 커넥션이 계속 먹는 것**

- **프로세스 슬롯** — `max_connections` 한 자리를 차지한다. 놀아도 남이 못 쓴다
- **메모리** — 프로세스 기본 + 누적된 카탈로그 캐시. `temp_buffers` 는 세션이 끝날 때까지 안 돌려준다
- **스냅샷 비용** — 트랜잭션 스냅샷을 만들 때 모든 백엔드를 훑는다.
  **유휴 커넥션이 일하는 커넥션을 느리게 만든다**

**`idle` 과 `idle in transaction` 은 완전히 다르다.**

| 상태 | 뜻 | 심각도 |
|---|---|---|
| `idle` | 트랜잭션 없이 대기 | 자원 낭비 |
| **`idle in transaction`** | **BEGIN 해놓고 아무것도 안 함** | **재앙** |

`idle in transaction` 은 위 비용을 다 내면서 셋을 더 한다.

**① 락을 쥔 채 논다.** `SELECT FOR UPDATE` 로 행을 잠그고 앱이 딴짓을 하면,
그 락은 트랜잭션이 끝날 때까지 유지된다. 같은 행을 노리는 모든 요청이 **무한정** 기다린다
(`lock_timeout` 이 0 이므로).

**② VACUUM 을 막는다.** Postgres 는 "가장 오래된 열린 트랜잭션"보다 나중 데이터를 정리하지 못한다.
30분짜리 `idle in transaction` 하나가 **DB 전체의 청소를 30분간 멈춘다.**

**③ 앱 쪽 커넥션도 같이 묶인다.** 풀에 반납되지 않았으므로, 이런 게 10개면 **풀 전체가 마른다.**

## 설정

### 구조

Phase 04 의 앱 1대 직결이 아니라 **앱 3대 + HAProxy(least-conn)** 로 돌린다.
(a) 의 "앱 대수 × 풀 크기" 가 이번 주제라 여러 대가 있어야 한다.

**Phase 04 의 CPU/메모리 주입은 전부 껐다.** 앱 CPU 가 병목이면 풀 효과가 가려진다.

| 항목 | 값 |
|---|---|
| 앱 | 3대, `cpus=1.2` `mem=512m` |
| DB | Postgres 16-alpine **설정 무수정** |
| `max_connections` | **100** (superuser 예약 3 제외하면 실질 97) |
| `work_mem` / `shared_buffers` / `temp_buffers` | 4MB / 128MB / 8MB |
| `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout` | **셋 다 0 (무제한)** |
| 부하 | 600 RPS / 90초, `HOT_RATIO=0.1` (실험별 조정) |
| HAProxy `timeout server` | 30초 ← (e)(f) 의 504 가 여기서 나온다 |

### 앱에 추가한 손잡이 — `app/src/db.js`

```
PG_POOL_MAX             PG_STATEMENT_TIMEOUT_MS
PG_ACQUIRE_TIMEOUT_MS   PG_LOCK_TIMEOUT_MS
PG_IDLE_TIMEOUT_MS      PG_IDLE_TX_TIMEOUT_MS
PG_MAX_LIFETIME_SEC
```

서버측 타임아웃 3종은 `PGOPTIONS` 로 넘겨 접속 시 세션에 적용한다.
`pool.on('connect')` 에서 `SET` 을 날리는 방법도 있지만 커넥션마다 왕복이 한 번 더 든다.

**DB 에러를 원인별로 나눴다.** 전부 500 으로 뭉뚱그리면 k6 출력만 보고
"커넥션이 없었나 / 쿼리가 느렸나 / 락을 못 잡았나" 를 구분할 수 없다.
`too_many_clients` · `pool_acquire_timeout` · `statement_timeout` · `lock_timeout` 은
**일시적 과부하**이므로 503 + `Retry-After` 로 답한다.

### (f) 를 위해 진짜 느린 쿼리를 만들었다

`pg_sleep()` 으로 가짜 지연을 만들면 **"인덱스 추가로 개선"을 증명할 수 없다.**
가짜 지연은 인덱스로 사라지지 않기 때문이다. 그래서:

1. `reservations` 를 **200만 행**으로 채운다 (`db/seed-bulk.sql`)
2. 트랜잭션 안에 `WHERE event_id = ? AND user_id = ?` 조회를 하나 넣는다
3. **`event_id` 에 인덱스가 없다** — Postgres 는 FK 제약을 만들어도 인덱스를 자동 생성하지 않는다
4. → 순차 스캔 → 커넥션 점유 → 풀 고갈

`id` 를 1~200만으로 결정적으로 만들어, 런 사이 초기화(`db/reset-bulk.sql`)가
`id > 2000000` 인 것만 지우게 했다. 기본 `reset.sql` 은 `TRUNCATE` 라 200만 행을 통째로 날린다.

### 메모리를 두 가지로 잰 이유

처음엔 백엔드 프로세스의 `VmRSS` 를 합산했는데, **공유 메모리를 백엔드마다 중복으로 센다.**

```
유휴 상태, 커넥션 2개:
  VmRSS 합계    92,980 kB
  RssAnon 합계  16,112 kB   ← 사적 메모리만
```

커넥션당으로 환산하면 **"30MB"와 "2MB"의 차이**다. 그대로 뒀으면 (d) 에서 완전히 틀린
결론이 나왔을 것이다. 이후 둘 다 기록한다.

## 병목 원인

### (a) 커넥션 초과 — H1 확인. 다만 **예상보다 훨씬 덜 터졌다**

풀 40 × 3대 = 120 으로 `max_connections=100` 을 넘겼고, `too_many_clients` **35건**이
정확히 기록됐다. 실패율은 **0.141%**(503 × 79) 였다.

**왜 이것밖에 안 터졌나.** node-postgres 는 커넥션을 **필요할 때 하나씩** 연다.
`max=40` 은 상한일 뿐 처음부터 40개를 열지 않는다. 이 부하에서 실제로 필요한 커넥션은
1~2개뿐이라(아래 (c) 참고) 120 에 도달하는 일이 드물었다.

> **`max` 를 크게 잡는 것은 "지금 당장" 터지지 않는다. 트래픽이 튀는 순간에만 터진다.**
> 그래서 더 위험하다 — 평소엔 멀쩡하다가 가장 바쁠 때 죽는다.

가장 인상적인 증거는 숫자가 아니라 **모니터링이 죽은 것**이다.
`psql` 이 커넥션을 못 얻어 샘플러가 39초 만에 멈췄다.
**커넥션이 고갈되면 상황을 관찰할 수단부터 잃는다.**

### (b) 풀 기아 — H2 확인. 지연의 **거의 전부**가 풀 대기였다

풀 1개(총 3개)에 600 RPS 를 넣었다.

```
k6 p99          719.04ms
획득대기 p99    723.10ms   ← 거의 같다
트랜잭션 p50      2.00ms   ← DB 는 놀고 있었다
```

**두 값이 4ms 차이로 일치한다.** 지연의 99% 이상이 "DB 가 느려서"가 아니라
**"커넥션을 못 받아서"** 였다. 풀 `waiting` 이 평균 18.3 으로, 매 순간 18개의 요청이
풀 앞에 줄 서 있었다.

DB 는 한가했다 — `active` 1.6, 락 대기 0. **병목은 DB 가 아니라 풀 크기였다.**

| 16 | 48 | 371ms | 122.7ms |
| 32 | 96 | 16.10ms | 1.0ms |

**풀 2개에서 이미 최적이고, 32까지 늘려도 나빠지지 않았다.**
처리량은 전 구간 486~487 RPS 로 완전히 평평했다.

이유는 **리틀의 법칙**으로 바로 나온다. Phase 04 에서 쓴 그 도구다.

```
L = λ × W = 600 RPS × 0.0019초(트랜잭션 p50) = 1.14
```

**필요한 커넥션이 1.14개다.** 풀 2개면 이미 충분하고, 그 이상은 놀 뿐이다.
`idle` 이 풀 32 에서 23.4 개였던 것이 그 증거다.

**c-pool16 의 371ms 는 풀 크기 탓이 아니다.** 그 런에서만 락 대기 max 21,
`idle in transaction` max 27 이 찍혔다. 다른 런에는 없던 경합이다.
풀 32 가 멀쩡한데 풀 16 만 나쁜 것은 단조롭지 않으므로 **일시적 경합으로 보고
풀 크기 효과로 귀속하지 않는다.**

> **H3 이 안 나온 이유는 실험 설계 때문이다.** 트랜잭션이 1.9ms 로 너무 빨라
> 커넥션 경합 자체가 생기지 않았다. "풀을 키우면 나빠진다"를 보려면 트랜잭션이
> 훨씬 길어야 하는데, 그건 (e)(f) 에서 따로 만들었다.

**그렇다고 큰 풀이 공짜인 것은 아니다.** 처리량은 그대로면서 **메모리만 늘었다.**
그게 (d) 다.

### (d) 메모리 — H4 확인. 커넥션당 **3.1MB** 로 선형이다

| 실측 커넥션 | 사적메모리(RssAnon) |
|--:|--:|
| 5.0 | 26MB |
| 8.0 | 35MB |
| 14.0 | 54MB |
| 24.2 | 86MB |
| 38.6 | 133MB |
| 42.5 | 143MB |

거의 완벽한 직선이다. 기울기와 절편을 뽑으면:

```
사적메모리 ≈ 10MB + 3.1MB × 커넥션수
```

검증: 커넥션 14 → 10 + 43.4 = 53.4MB (실측 54MB)
      커넥션 24.2 → 10 + 75.0 = 85.0MB (실측 86MB)

**커넥션 하나가 3.1MB 를 더 먹는다.** `max_connections=100` 을 다 쓰면 약 320MB 다.
우리 쿼리는 정렬·해시가 없어 `work_mem` 을 거의 안 쓴다. 복잡한 쿼리라면
노드마다 4MB 씩 붙으므로 이 값은 몇 배가 된다.

**VmRSS 를 그대로 믿었다면 커넥션당 30MB 라는 10배 틀린 답이 나왔다.**
`a-exceed-soft` 에서 VmRSS max 1,379MB vs 사적 133MB — **10배 차이**다.
공유 메모리를 백엔드 수만큼 중복으로 세기 때문이다.

### (e) 락 경합 — H5 확인. 커넥션 30개가 **전부** 락에서 멈췄다

핫키 100% + 트랜잭션 200ms 유지.

```
active        30.0  (풀 총량 30 — 전부 사용 중)
락 대기       29.0  (그 중 29개가 락을 기다리는 중)
풀 waiting  2,649  (커넥션을 못 받아 줄 선 요청)
결과        97.04% 실패 (전부 HAProxy 504)
```

**30개 커넥션 중 29개가 아무 일도 못 하고 같은 행의 락을 기다렸다.**
용량을 계산하면 왜 이렇게 되는지 바로 보인다.

```
같은 행을 200ms 씩 잠그므로 이론 처리량 = 1 / 0.2초 = 5 RPS
실제 유입 = 300 RPS
```

**60배 초과다.** λ > μ 이므로 안정 상태가 존재하지 않는다 — Phase 04 (d) 와 같은 구조다.
`lock_timeout` 이 0 이라 아무도 포기하지 않고, 풀은 영원히 마른 채로 있었다.

### (f) 느린 쿼리 — H6 확인. **쿼리 하나가 풀을 통째로 말렸다**

```
active       37.1  ← 풀 총량 30 을 넘는다 (병렬워커 때문)
락 대기         0  ← 락 문제가 아니다. 순수하게 "일이 오래 걸려서"
풀 waiting  2,012
VmRSS max  5,348MB  ← 순차 스캔이 shared_buffers 를 훑은 흔적
결과      85.77% 실패
```

(e) 와 증상은 같지만 **원인이 다르다.** (e) 는 락 대기 29, (f) 는 락 대기 0 이다.
(f) 의 커넥션들은 **실제로 일하고 있었다** — 200만 행을 훑느라.

`EXPLAIN` 이 결정적이다. 인덱스가 없으면 `Parallel Seq Scan` 이 되고
**워커를 2개 더 띄운다.** 커넥션 30개가 실제로는 프로세스 90개가 될 수 있다는 뜻이다.
`active` 37.1 이 풀 총량 30 을 넘은 것이 그 증거다.

> **커넥션 풀 크기를 아무리 잘 잡아도, 쿼리 하나가 느리면 소용없다.**
> 풀은 "동시에 몇 개"를 정하지 "각각 얼마나 오래"를 정하지 못한다.

## 개선

### 적용한 것 넷

| 개선 | 설정 | 노린 것 |
|---|---|---|
| 타임아웃 3종 | `statement=500ms` `lock=200ms` `idleTx=1000ms` `acquire=1000ms` | (e) 무한 대기 차단 |
| 인덱스 추가 | `(event_id, user_id)` 복합 인덱스 | (f) 순차 스캔 제거 |
| 트랜잭션 축소 | 왕복 5회 → 2회 | 커넥션 점유 시간 단축 |
| 풀 튜닝 | 10 → 8 | (c) 결과 반영 |

**트랜잭션 축소**는 두 가지를 바꿨다.

```
① 멱등키 조회를 트랜잭션 밖으로 뺀다
   읽기 전용이고 인덱스가 있다. 트랜잭션 안에 둘 이유가 없다.

② SELECT FOR UPDATE + UPDATE 를 조건부 원자 UPDATE 하나로 합친다
   UPDATE events SET remaining = remaining - $1
   WHERE id = $2 AND remaining >= $1
   RETURNING remaining
   락을 따로 잡을 필요가 없다. UPDATE 자체가 행을 잠근다.
```

### 버린 대안

- **`max_connections` 를 올린다** — 근본 해결이 아니다. 프로세스가 그만큼 늘어
  메모리와 스케줄링 비용이 같이 오른다. (d) 가 그 비용을 정량화했다.
  진짜 답은 Phase 06 의 커넥션 풀러다.
- **`work_mem` 을 올린다** — 우리 쿼리는 정렬·해시가 없어 효과가 없다. 측정 없이 만지지 않는다.
- **재시도 로직** — 락 경합 상황에서 재시도는 부하를 늘린다. Phase 04 에서 확인한
  "느려지는 것이 부하를 늘리는 양의 피드백"과 같은 함정이다.

## 재측정

### 개선 전후

| | 조건 | RPS | p50 | p99 | 실패율 |
|---|---|--:|--:|--:|--:|
| **(f) 전** | f-slowquery | 31.81 | 30,002ms | 30,013ms | **85.77%** |
| **(f) 후** | fix-index | **252.18** | **2.30ms** | **10.50ms** | **0%** |
| **(e) 전** | e-lock | 30.38 | 30,002ms | 30,005ms | 97.04% |
| **(e) 후** | fix-timeouts | 249.27 | **1,002ms** | 1,351ms | 98.15% |
| **(e) 후** | fix-tx | 30.32 | 30,002ms | 30,013ms | **97.06%** |

### 인덱스 하나가 (f) 를 완전히 없앴다

```
처리량   31.81 -> 252.18 RPS   (7.9배)
p50      30,002ms -> 2.30ms    (13,000배)
실패율   85.77% -> 0%
풀 waiting  2,012 -> 0.0
```

**같은 풀 크기(10), 같은 부하(300 RPS), 같은 200만 행에서** 인덱스 하나만 추가한 결과다.
풀은 아무것도 안 바꿨다.

> **"풀이 마른다"는 증상이지 원인이 아니다.** 원인은 쿼리였다.
> 풀 크기를 아무리 늘렸어도 이 문제는 안 풀렸을 것이다.

### 타임아웃은 (e) 를 **고치지 못했다. 대신 빨리 실패하게 만들었다**

```
p50      30,002ms -> 1,002ms   (30배 단축)
실패율   97.04% -> 98.15%      (오히려 늘었다)
획득실패      0 -> 10,774
```

**실패율은 그대로인데 지연만 30배 줄었다.** 이건 Phase 04 의 load shedding 과 같은 성격이다 —
처리 못 할 부하를 **30초 매달아 두는 대신 1초 만에 503 으로 돌려보낸 것**이다.

근본 원인(같은 행을 200ms 잠그는데 300 RPS 유입)은 그대로다. 이론 용량 5 RPS 를
60배 초과하는 상황은 타임아웃으로 해결되지 않는다.

**다만 얻은 것이 있다.** HAProxy 504(30초)가 앱의 503(1초)으로 바뀌었다.
클라이언트가 `Retry-After` 를 받고 판단할 수 있게 됐고, 커넥션이 30초씩 묶이지 않는다.

### 트랜잭션 축소는 **전혀 효과가 없었다** — 예상 실패

```
e-lock   97.04% 실패, p50 30,002ms
fix-tx   97.06% 실패, p50 30,002ms    <- 차이 없음
```

**왕복을 5회에서 2회로 줄였는데 아무것도 안 변했다.**

이유는 명확하다. 트랜잭션 시간의 구성이 이렇다.

```
왕복 5회의 네트워크·파싱 비용  ≈ 1~2ms
TX_HOLD_MS 로 강제한 유지 시간 =  200ms     ← 이게 99% 다
```

**줄인 1ms 는 200ms 앞에서 의미가 없다.** 트랜잭션 범위 축소는 "트랜잭션 안에
불필요한 작업이 있을 때" 효과가 있지, **트랜잭션 안의 실제 작업이 지배적이면 소용없다.**

다만 지연이 어디서 발생하는지는 바뀌었다.

```
e-lock  획득대기 p50 ≥10s   요청이 풀 앞에서 대기
fix-tx  획득대기 p50 0.6ms  커넥션은 바로 받고, 락에서 대기
```

멱등키 조회를 트랜잭션 밖으로 뺀 덕에 그 조회는 커넥션을 짧게 쓰고 반납했다.
**구조는 개선됐지만 병목이 다른 데 있어서 결과가 안 바뀐 것**이다.

### 풀 튜닝

```
fix-pool  풀 8 (총 24), 600 RPS -> 486.95 RPS, p99 110.56ms, 실패 0%
fix-all   풀 8 + 인덱스 + 타임아웃 + 트랜잭션축소, 300 RPS -> 252.17 RPS, p99 97.69ms, 실패 0%
```

> **주의**: `fix-pool` 은 600 RPS, `fix-all` 은 300 RPS 로 돌았다(대용량 시드 실험과
> 조건을 맞추려고). **둘을 직접 비교하면 안 된다.**

`fix-all` 은 200만 행 + 느린 쿼리 경로가 켜진 상태에서 **실패 0%, p99 97.69ms** 였다.
같은 조건의 `f-slowquery` 가 85.77% 실패였으니, 개선 묶음이 제 역할을 했다.

## 이번 Phase 에서 틀린 것

**H3(풀 크기 최적점) 을 재현하지 못했다.** 트랜잭션이 1.9ms 로 너무 빨라
필요 커넥션이 1.14개였고, 풀을 32(총 96)까지 늘려도 경합이 생기지 않았다.
"최적점 이후 나빠진다"를 보려면 트랜잭션이 훨씬 길거나 부하가 훨씬 높아야 한다.

**대신 다른 답을 얻었다.** 큰 풀의 비용은 지연이 아니라 **메모리**로 나타났다 —
커넥션당 3.1MB, 선형. 처리량은 486 RPS 로 평평한데 메모리만 26MB → 143MB 로 늘었다.

**H7 중 트랜잭션 축소가 틀렸다.** 왕복을 줄여도 트랜잭션 안의 실제 작업 시간이
지배적이면 효과가 없다.

## Phase 06 으로 넘길 것

1. **총 커넥션 = 앱 대수 × 풀 크기.** (a) 에서 `too_many_clients` 35건으로 확인했다.
   앱을 6대로 늘리면 같은 풀 크기로도 240 이 된다. **PgBouncer 가 이 곱셈을 끊는다.**
2. **(c) 곡선을 프록시 뒤에서 다시 그린다.** 앱 풀 최적점(2)과 프록시 풀 최적점이
   어떻게 다른지가 Phase 06 의 알맹이다.
3. **커넥션당 3.1MB** 라는 실측값이 프록시 효과를 정량화하는 기준이 된다.
   커넥션 96개 → 20개로 접으면 메모리가 얼마나 주는지 계산할 수 있다.
4. **`max lifetime` 은 여전히 미측정.** 며칠에 걸친 누적이라 짧은 부하테스트로는 못 잡는다.
