# 07. DB 부하를 캐시로 줄인다

Phase: 07 · 2026-08-12

Phase 06 에서 커넥션은 더 이상 병목이 아님을 확인했다 — DB 커넥션 22개로 486 RPS 를
처리했고 `sv_active` 는 4.1 뿐이었다. 남은 병목은 **DB 왕복 횟수 자체**다.

이번엔 그 왕복을 캐시로 줄인다.

---

## 가설

*(측정 전에 작성. 틀려도 고쳐 쓰지 않는다.)*

**H1** — 캐시가 매진 거절을 흡수해 DB 접촉이 크게 준다.
**H2** — 로컬 캐시는 앱 N대에서 같은 키에 miss 가 N번 나므로 Redis 보다 hit ratio 가 낮다.
**H3** — Zipf 분포는 균등 분포보다 hit ratio 가 높다.
**H4** — 2단(로컬+Redis)이 지연과 hit ratio 를 동시에 잡는다.
**H5** — TTL 을 짧게 + 지터 0 으로 두면 동시 만료로 stampede 가 재현된다.
**H6** — TTL jitter 와 singleflight 가 stampede 를 완화한다.
**H7** — Redis 가 죽어도 2단 캐시의 로컬 계층이 받아내 서비스가 유지된다.

---

## 시작하기 전에: 캐시할 게 없었다

Phase 06 마지막 런의 결과 분포를 보니 이랬다.

```
created = 28,196
sold_out = 0
not_found = 0
```

**모든 요청이 예약을 생성했다.** `total_seats` 가 1억이라 절대 매진되지 않았기 때문이다.
즉 이 라우트는 **100% 쓰기**였고, hit ratio 도 DB QPS 감소도 잴 대상이 없었다.

캐시할 수 있는 것과 없는 것을 나누면 이렇게 갈린다.

| | 캐시 가능? | 이유 |
|---|:--:|---|
| 이벤트 존재 여부·메타데이터 | ✅ | 안 바뀐다 |
| **매진 여부** | ✅ | 매진되면 계속 매진이다 |
| `remaining` 의 정확한 값 | ❌ | 매 요청 감소 중 |
| 재고 차감 자체 | ❌ | 반드시 DB 원자적 UPDATE |

그래서 **재고를 현실적인 값으로 줄였다**(`db/reset-scarce.sql`).

```
id ≤ 10   → 200석   (Zipf 상위. 몇 초 안에 매진된다)
id ≤ 100  → 100석
나머지    →  20석    총 29,000석
```

부하 600 RPS × 90초 ≈ 54,000 요청이므로 유지구간 대부분이 매진 상태가 된다.
억지가 아니라 **티켓팅의 실제 모습**이다 — 10만 명이 1만 석을 두고 싸우면
대부분의 요청은 "이미 매진" 이라는 거절이고, 그 거절은 DB 를 안 거치고 끝낼 수 있다.

## 설명: 로컬 캐시 vs Redis

| | 로컬 | Redis | 2단 |
|---|:--:|:--:|:--:|
| 지연 | **가장 빠름**(참조) | 네트워크 왕복 | 대부분 로컬 |
| N대 hit ratio | **나쁨** | **좋음** | 좋음 |
| 메모리 | N배 중복 | 한 벌 | N배 + 한 벌 |
| 무효화 | **불가(TTL만)** | 즉시 | 로컬은 여전히 TTL |
| SPOF | 없음 | **있음** | Redis 죽어도 버팀 |

**로컬 캐시의 진짜 약점은 N대일 때의 miss 횟수**다.

```
앱 3대, 각자 로컬 캐시, 키 하나
-> LB 가 요청을 3대에 뿌린다
-> 3대가 각자 한 번씩 miss 를 낸다
-> 같은 키인데 DB 로 3번 간다
```

Redis 는 공유 저장소라 miss 가 한 번이다. **이번 실험이 이 차이를 정량화한다.**

## 설명: 쓰기 전략

```
cache-aside     앱이 캐시를 직접 관리. 쓰기는 DB 먼저, 캐시는 무효화
write-through   쓰기가 캐시를 통과해 DB 로. 항상 일치하지만 쓰기가 느리다
write-behind    캐시에만 쓰고 DB 는 나중에. 빠르지만 장애 시 유실
```

**이 라우트는 cache-aside 를 강제한다.** 재고 차감이
`UPDATE ... WHERE remaining >= ?` 라는 **조건부 원자 연산**이기 때문이다.
write-through 는 이 원자성을 캐시 계층에서 재현해야 하고,
write-behind 는 돈이 걸린 재고에서 유실 가능성을 받아들이는 것이다.
셋 중 고르는 게 아니라 성격이 정해준다.

## 설명: 무효화와 stale 허용 범위

**틀리는 방향이 두 가지고 손해가 완전히 다르다.**

| 캐시가 틀린 방향 | 결과 | 심각도 |
|---|---|---|
| 재고 있는데 **매진**이라 함 | 살 수 있는 사람을 거절 | 나쁨 — TTL 을 짧게 |
| 매진인데 **재고 있다** 함 | DB 가 0행 반환 → 정상 거절 | **무해** |

**비대칭이다.** 후자는 DB 가 최종 방어선이라 틀려도 정확성이 안 깨진다.
그래서 원칙이 이렇게 선다.

> **캐시는 거절을 빠르게 할 뿐, 허용을 보장하지 않는다.**

구현도 그대로다 — 캐시가 `soldOut` 이면 즉시 거절하고,
`재고 있음` 이면 DB 의 원자적 UPDATE 가 판정한다.
**성공(created) 시에는 캐시를 갱신하지 않는다.** `remaining` 을 써 봐야
다음 요청 전에 이미 틀린 값이 되고, 매 성공마다 캐시를 쓰면 왕복만 는다.

## 설정

| 항목 | 값 |
|---|---|
| 앱 | 3대, `cpus=0.8` (총 2.4 — Phase 06 과 동일) |
| 캐시 | 로컬(Map+TTL) / Redis 7.4-alpine / 2단 |
| 하부 | PgBouncer transaction 모드 + Phase 05 최적화 경로(`TX_OPTIMIZED=1`) |
| 부하 | 600 RPS / 90초 |
| 분포 | uniform / **zipf (s=1.1, 상위10키가 48%)** |
| 재고 | 총 29,000석 (희소) |

Zipf 는 CDF 를 기동 시 한 번 만들고 이진 탐색으로 뽑는다.
매 요청마다 1000개 확률을 계산하면 k6 가 병목이 된다.

### 장애 대비를 코드에 넣었다

```js
redis.on('error', () => { redisReady = false; ... });
```

이게 없으면 Redis 가 죽는 순간 **unhandled error 로 앱이 같이 죽는다.**
fallback 실험이 "앱도 죽는다"로 끝나 버린다.
그리고 Redis 실패는 전부 **miss 로 강등**한다 — 요청을 죽이지 않고 DB 로 보낸다.

기동 순서도 Redis 연결을 먼저 세우고 `listen` 한다. 반대면 기동 직후 몇 초간
캐시 없이 요청을 받아 워밍업 구간 지표가 오염된다.

### Phase 06 숙제 처리

`ENOTFOUND` / `ECONNREFUSED` / `ECONNRESET` 등을 `upstream_unreachable` 로 분류해
**503 + `Retry-After`** 로 답하게 고쳤다. Phase 06 에서 34,578건이 500 으로 나갔던 문제다.

## 병목 원인

### H1 확인 — DB 접촉이 1/4로 줄었다

```
캐시 없음   40,200회
캐시 있음   10,226~11,753회   (71~75% 감소)
```

줄어든 약 29,000회가 전부 **매진 거절**이다. 캐시가 "이 이벤트는 매진"이라고
답하면 DB 를 아예 안 친다. 요청의 57~63%가 매진 거절이었으니 계산이 맞는다.

**처리량은 486.9 RPS 로 전혀 안 변했다.** 도착률을 고정했으므로 당연하다.
캐시가 바꾼 것은 처리량이 아니라 **같은 처리량을 내는 데 드는 DB 비용**이다.

### H2 확인 — 로컬 캐시는 Redis 보다 hit ratio 가 낮다

이번 Phase 에서 가장 선명한 결과다.

| 분포 | 로컬 | Redis | 차이 |
|---|--:|--:|--:|
| uniform | **37.6%** | **64.5%** | **26.9%p** |
| zipf | 70.6% | 81.5% | 10.9%p |

**앱 3대가 각자 캐시를 갖고 있으니 같은 키에 miss 가 3번 난다.** 그 대가가 이 차이다.

**균등 분포에서 차이가 훨씬 크다.** 키가 1000개로 흩어지면 로컬 캐시 3개가
각자 1000개를 채워야 한다. Zipf 는 핫키가 소수라 로컬도 금방 채워져 격차가 줄어든다.

DB 로딩 횟수로 보면 더 직접적이다.

```
local-zipf   11,829회
redis-zipf    7,444회   <- 37% 적다
```

> **로컬 캐시는 인스턴스가 늘수록 나빠진다.** 앱 6대면 격차가 더 벌어졌을 것이다.

### H3 확인 — Zipf 가 균등보다 hit ratio 가 높다

```
로컬:  37.6% -> 70.6%
Redis: 64.5% -> 81.5%
```

편중이 심할수록 적은 키가 반복 조회되므로 당연한 방향이다.
**다만 DB 접촉은 Zipf 쪽이 더 많았다**(10,226 vs 11,572). hit ratio 가 높은데 왜?

균등 분포에서는 **1000개 이벤트가 골고루 팔려 900개가 매진**됐고,
Zipf 에서는 상위 소수만 팔려 **251개만 매진**됐다. 매진된 이벤트가 많을수록
캐시가 끊을 수 있는 요청도 많다. **hit ratio 와 DB 접촉이 항상 같은 방향은 아니다.**

### H4 부분 확인 — 2단은 hit 을 합치지만 p99 는 나빴다

`tiered-zipf` 를 계층별로 보면:

```
로컬에서 71.3% 잡고
남은 28.7% 중 38.3% 를 Redis 가 잡는다
-> 전체 유효 hit = 1 - (0.287 × 0.617) = 82.3%
```

Redis 단독 81.5% 보다 근소하게 높고, **DB 로딩은 7,125회로 가장 적다**(Redis 단독 7,444).

**그런데 k6 p99 는 2단이 가장 나빴다**(33.39ms vs Redis 단독 15.50ms).
Redis p99 도 0.90ms → 2.10ms 로 두 배가 됐다.

이유는 miss 경로가 길어졌기 때문으로 보인다 — 로컬 확인 → Redis 확인 → DB.
hit 일 때는 로컬에서 끝나지만, **miss 일 때는 계층을 다 훑는다.**
꼬리 지연은 miss 경로가 지배한다.

> **2단 캐시는 "둘의 장점만" 갖지 않는다.** hit 은 빨라지지만 miss 는 느려진다.

### H5 **반증** — TTL 만료로는 stampede 가 재현되지 않았다

TTL 1초 + 지터 0 이면 동시 만료가 날 것으로 봤는데, **DB 로딩이 평탄했다.**

```
stampede (TTL 1초, 지터 0)   DB 로딩 avg 177.5/s  max 186.0/s  -> 1.05배
```

**키마다 캐시에 들어간 시각이 다르기 때문이다.** TTL 시계는 삽입 시점부터 도는데,
1000개 키가 부하 중에 제각기 다른 순간 채워졌으니 만료도 자연히 흩어진다.
지터를 0 으로 두어도 **삽입 시각 자체가 지터 역할**을 한다.

그래서 **동시 만료를 강제**했다 — 부하 중 55초에 `FLUSHALL`.

```
flush-none   DB 로딩 avg 29.0/s  max 93.8/s  -> 3.23배 스파이크
```

**이번엔 재현됐다.** 캐시가 한순간에 비면 그 시점의 모든 요청이 동시에 miss 를 낸다.

> **stampede 는 "TTL 이 짧아서" 생기는 게 아니라 "만료가 동기화돼서" 생긴다.**
> 실무에서 이게 나는 상황은 캐시 flush, 재배포, 노드 재시작, 일괄 워밍업이다.

### H6 부분 반증 — singleflight 가 이 stampede 를 못 막았다

```
flush-none  스파이크 3.23배
flush-sf    스파이크 3.68배   <- 오히려 조금 나쁘다
```

**singleflight 는 같은 키에 대한 동시 miss 를 합치는 장치**다.
그런데 FLUSHALL 은 **1000개 서로 다른 키**를 한꺼번에 날린다.
각 키는 한 번씩만 miss 하므로 합칠 동시성이 거의 없다.

`singleflight 공유` 카운터가 그 증거다 — 전체 실험에서 **26~47건**뿐이었다.
5만 요청 중 47건이면 사실상 작동하지 않은 것이다.

**핫키 하나에 몰리는 stampede 라면 달랐을 것이다.** 우리 Zipf 는 상위 키가
18% 를 가져가지만, 그 키의 miss 는 만료 직후 한 순간에만 몰린다.

> **singleflight 는 핫키 stampede 용이지 대량 만료용이 아니다.**
> 대량 만료에는 지터(재적재 시점을 흩뜨림)나 단계적 워밍이 맞는 도구다.

다만 **k6 p99 는 개선됐다**(50.15 → 32.69ms). DB 로딩 스파이크는 비슷한데
꼬리 지연이 줄었다. 런 1회씩이라 이 차이를 확정하기는 이르다.

### H7 확인 — Redis 가 죽어도 서비스는 유지됐다

부하 중 55초에 Redis 를 죽였다.

```
실패율    63.183%   <- 기준선 63.294% 와 같다 (전부 409 매진)
무응답         0건
503            0건
k6 p99      8.58ms  <- 전 실험 중 가장 좋다
로컬 hit    70.9%   <- 로컬 계층이 계속 일했다
캐시 오류      39건  <- Redis 접근 실패. 요청은 안 죽였다
```

**Redis 가 사라져도 사용자에게는 아무 일도 없었다.**

두 가지가 그렇게 만들었다.

**① 2단 구조.** 로컬 계층이 70.9% 를 받아냈다. Redis 가 없어도 대부분의 요청은
로컬에서 끝난다.

**② 실패를 miss 로 강등.** `redisGet` 이 예외를 삼키고 `undefined` 를 돌려주므로,
Redis 실패는 "캐시에 없다"와 같은 취급이 된다. 요청은 DB 로 가서 정상 처리된다.

p99 가 가장 좋았던 것은 Redis 왕복이 사라져서로 보인다 — 죽은 뒤로는
로컬 hit 아니면 바로 DB 이므로 중간 계층이 없다.

> **캐시 장애는 "느려짐" 으로 끝나야지 "장애" 가 되면 안 된다.**
> 그러려면 캐시 접근 실패를 miss 와 같게 취급해야 한다.

## 개선

### 적용

| 개선 | 근거 |
|---|---|
| **Redis(공유) 캐시 채택** | 로컬 대비 hit ratio 26.9%p 높고 DB 로딩 37% 적다 |
| cache-aside | 조건부 원자 UPDATE 라 다른 전략을 쓸 수 없다 |
| 캐시 실패 → miss 강등 | Redis 죽어도 실패율 변화 0 |
| `soldOut` 만 캐시, 성공은 갱신 안 함 | 틀리는 방향이 비대칭이다 |

### 버린 대안

- **2단 캐시** — DB 로딩은 가장 적었지만(7,125) p99 가 가장 나빴다(33.39ms).
  miss 경로가 길어지는 대가가 hit 이득보다 컸다. **단, Redis 장애 대비로는 유효**하므로
  가용성이 더 중요하면 다시 고려할 값어치가 있다.
- **write-through / write-behind** — 위에서 설명한 대로 이 라우트가 배제한다.
- **`remaining` 값을 캐시** — 매 요청 감소하므로 즉시 낡는다. 측정하지 않았다.
- **Redis 락 기반 전역 singleflight** — 로컬 singleflight 조차 47건밖에 안 걸렸다.
  **필요하다는 근거가 없어 넣지 않았다.**

## 재측정

### 캐시 전후 (Zipf, 같은 부하)

| | DB 접촉 | k6 p50 | k6 p99 | 앱 p99 | 처리량 |
|---|--:|--:|--:|--:|--:|
| 캐시 없음 | **40,205** | 1.59ms | 37.44ms | 21.8ms | 486.94 RPS |
| **Redis** | **11,572** | **0.72ms** | **15.50ms** | **6.8ms** | 486.94 RPS |

**DB 접촉 71% 감소, p99 59% 개선, 처리량 변화 없음.**

### 캐시 전후 (균등, 같은 부하)

| | DB 접촉 | k6 p99 | 앱 p99 |
|---|--:|--:|--:|
| 캐시 없음 | **40,200** | 29.72ms | 21.4ms |
| **Redis** | **10,226** | 19.72ms | 9.3ms |
| 로컬 | 10,604 | **10.64ms** | **4.8ms** |

**균등 분포에서는 로컬이 지연은 더 좋았다**(네트워크 왕복이 없으므로).
DB 접촉은 Redis 가 적었다. **지연을 볼지 DB 부하를 볼지에 따라 답이 갈린다.**

### stampede 전후

```
평상시(캐시 채워짐)   DB 로딩 29.0/s
FLUSHALL 직후         DB 로딩 93.8/s   -> 3.23배
```

**완화하지 못했다.** singleflight 는 3.68배로 오히려 나빴고, 지터는
동시 만료 자체를 막지 못한다(이미 비워진 뒤라 지터가 개입할 여지가 없다).

**맞는 해법은 측정하지 않았다.** 후보는 이렇다.
- 만료 전 비동기 갱신(refresh-ahead)
- 단계적 워밍(전체를 한꺼번에 채우지 않는다)
- 캐시 flush 자체를 하지 않는 운영 규칙

## 이번 Phase 에서 틀린 것

**H5 가 틀렸다.** TTL 을 짧게 하고 지터를 0 으로 둬도 stampede 가 안 났다(1.05배).
**삽입 시각이 흩어져 있으면 만료도 흩어진다.** `FLUSHALL` 로 강제해야 재현됐다(3.23배).

**H6 이 부분적으로 틀렸다.** singleflight 는 대량 동시 만료를 막지 못했다(3.68배).
같은 키의 동시 miss 를 합치는 장치인데, 서로 다른 1000개 키가 한 번씩 miss 하는
상황에는 합칠 게 없다.

**H4 가 부분적으로 틀렸다.** 2단 캐시는 DB 로딩을 가장 많이 줄였지만
p99 는 가장 나빴다. "둘의 장점만" 갖지 않는다.

## Phase 08 로 넘길 것

1. **SLO 대비**: 목표 1,000 RPS / p99 < 200ms / 에러율 < 0.1%.
   현재 486 RPS · p99 15.50ms · 무응답 0. **지연은 크게 넘어섰고 처리량이 절반**이다.
   총 앱 CPU 2.4 고정 제약 때문이므로, 처리량을 올리려면 그 제약을 풀거나
   동기 경로를 더 줄여야 한다.
2. **DB 접촉이 여전히 11,572회 있다.** 전부 실제 쓰기(재고 차감 + INSERT)다.
   **캐시로는 더 줄일 수 없다.** 이 쓰기를 큐 뒤로 보내는 것이 Phase 08 의 주제다.
3. **Redis 원자적 카운터(DECR)로 재고를 선점**하는 구조가 Phase 08 의 전제다.
   그래야 "판정은 동기, 반영은 비동기" 로 자를 수 있다. 이번 Phase 가 그 Redis 를 세웠다.
4. **stampede 의 맞는 해법(refresh-ahead 등)은 미측정.**
5. **계측 규칙 추가**: k6 remote-write 를 쓸 때 `name` 태그를 고정하고 `url` 을
   시스템 태그에서 뺀다. 안 그러면 Prometheus 가 죽는다. 이번이 두 번째다.
