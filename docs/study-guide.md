# 1부 · 먼저 알아야 할 것들

## 1-1. 부하 테스트란 무엇인가

기능 테스트는 "이 코드가 맞는 답을 내는가" 를 본다.
부하 테스트는 **"몇 명이 동시에 와도 맞는 답을 제때 내는가"** 를 본다.

혼자 눌러 보면 잘 되던 API 가 1,000명이 동시에 누르면 왜 무너질까.
자원이 유한하기 때문이다. CPU 코어 수, DB 커넥션 개수, 메모리, 네트워크 포트.
평소에는 남아돌지만 어느 지점에서 하나가 먼저 바닥난다.

**그 먼저 바닥나는 자원이 병목(bottleneck)이다.**

핵심은 이거다 — **병목은 항상 하나다.** 여러 개가 동시에 터지지 않는다.
가장 약한 고리 하나가 먼저 끊어지고, 그걸 고치면 그 다음으로 약한 고리가 드러난다.

이 프로젝트는 그 사슬을 10번 끊어 본 기록이다.
끊을 때마다 병목이 어디로 옮겨가는지 봤다.

```
Phase 01  앱 CPU 가 병목
Phase 03  앱을 3대로 → 병목이 다른 데로 이동
Phase 05  DB 커넥션이 병목
Phase 06  프록시로 해결 → 또 이동
Phase 07  DB 접촉 자체가 병목
Phase 08  쓰기 경로가 병목
```

## 1-2. RPS 와 지연 시간

두 가지 축이 있다.

- **처리량 (throughput, RPS)** — 초당 몇 건을 처리하는가
- **지연 시간 (latency)** — 한 건이 얼마나 걸리는가

둘은 별개다. **초당 1,000건을 처리하면서 한 건당 10초가 걸릴 수 있다.**
(파이프라인에 만 건이 밀려 있으면 그렇게 된다.)
그래서 "빠르다" 는 말은 두 축을 다 봐야 의미가 있다.

## 1-3. 왜 평균이 아니라 p99 인가

이 프로젝트가 목표를 `p99 < 200ms` 로 잡은 이유다.

응답 시간 1,000건이 있다고 하자.

```
990건이 20ms,  10건이 10,000ms
평균 = (990×20 + 10×10000) ÷ 1000 = 119.8ms
```

**평균만 보면 120ms 로 멀쩡해 보인다.** 그런데 실제로는 100명 중 1명이 10초를 기다렸다.
그 1명은 앱을 껐을 것이다.

그래서 **분위수(percentile)** 를 쓴다.

| 지표 | 의미 |
|---|---|
| p50 | 절반이 이보다 빠르다 (= 중앙값) |
| p95 | 100명 중 95명이 이보다 빠르다 |
| p99 | 100명 중 99명이 이보다 빠르다 = **가장 느린 1명의 경험** |

p99 를 보는 건 **최악의 사용자를 버리지 않겠다**는 뜻이다.

> 실무에서 "평균 응답 200ms" 라는 보고는 거의 의미가 없다.
> 평균은 소수의 재앙을 다수의 정상으로 덮는다.

## 1-4. SLO 라는 것

**SLO(Service Level Objective)** 는 "우리 서비스가 이 정도는 해야 한다" 는 목표선이다.
이 프로젝트는 시작하면서 이걸 못 박았다.

```
1,000 RPS 지속 · p99 < 200ms · 에러율 < 0.1%
```

**목표를 먼저 정하는 게 왜 중요한가.** 목표가 없으면 측정 결과를 보고
"이 정도면 괜찮네" 라고 사후에 기준을 만들게 된다. 그럼 무엇을 해도 성공이다.
숫자를 먼저 박아 두면 달성/미달이 객관적으로 갈린다.

## 1-5. 리틀의 법칙 — 이 프로젝트를 관통하는 공식

```
L = λ × W

L = 시스템 안에 동시에 들어 있는 것의 개수
λ = 초당 도착하는 개수 (RPS)
W = 하나가 머무는 시간
```

식당으로 보면 직관적이다.
**시간당 60명이 오고 평균 30분 머물면, 가게 안에는 항상 30명이 있다.**

이걸 커넥션 풀에 그대로 적용한다.

```
초당 1,000 요청 × 트랜잭션 20ms = 동시에 20개 커넥션이 사용 중
→ 풀이 20개보다 작으면 요청이 줄을 선다
```

이 프로젝트는 이 공식을 두 방향으로 썼다.

- **Phase 01** — 예측에: "풀 10개 ÷ 트랜잭션 20ms = 500 RPS 가 천장일 것"
- **Phase 09** — 검증에: 실측 소요시간을 넣어 필요 용량을 계산하고 실제 구성과 대조

## 1-6. 부하 생성기의 두 가지 모드 — 이게 제일 중요하다

부하를 거는 도구는 두 방식 중 하나로 동작한다.
**여기서 잘못 고르면 그 뒤의 모든 숫자가 무의미해진다.**

### closed model (VU 기반)

가상 사용자 N명이 이렇게 돈다.

```
요청 보낸다 → 응답 기다린다 → 받으면 다시 보낸다
```

**함정**: 서버가 느려지면 응답이 늦게 오고, 그럼 다음 요청도 늦게 나간다.
**즉 서버가 힘들어질수록 부하가 저절로 줄어든다.**

서버가 가장 괴로운 구간이 표본에서 빠지므로,
**망가진 서버가 실제보다 좋아 보인다.**

### open model (도착률 기반)

```
서버가 어떻든 초당 1,000건씩 계속 도착한다
```

현실이 이렇다. 서버가 느리다고 사용자가 배려해서 덜 오지 않는다.
오히려 안 되니까 새로고침을 눌러서 더 온다.

이 프로젝트는 **전부 open model** 로 갔다. k6 의 `constant-arrival-rate` 다.
Phase 01 에서 같은 서버를 두 모델로 재서 차이를 직접 확인했다(가설 H3).

> 남에게 설명할 때 이 부분을 꼭 넣으면 좋다.
> "부하 테스트를 했다" 는 흔하지만 "왜 open model 이어야 하는가" 를 아는 건 드물다.

# 2부 · 이 프로젝트의 설계

## 2-1. 왜 이걸 만들었나

성능 이야기는 대부분 남의 글로 배운다. "커넥션 풀을 늘려라", "캐시를 써라",
"큐로 비동기 처리해라". 맞는 말인데, **언제 그게 맞고 언제 틀린지는 안 나온다.**

그래서 직접 재보기로 했다. **재지 않은 조언은 믿지 않는다**가 이 프로젝트의 출발점이다.

실제로 재보니 통념 몇 개가 깨졌다.

- 큐로 빼면 빨라진다 → **저부하에서는 오히려 느려졌다**
- 캐시 stampede 는 짧은 TTL 때문이다 → **아니었다**
- 풀이 마르면 풀을 키워야 한다 → **원인은 딴 데 있었다**
- 무거운 연산은 스레드풀로 옮기면 된다 → **처리량은 오히려 떨어졌다**

## 2-2. 왜 라우트가 하나뿐인가

**이게 첫 번째 설계 결정이고 가장 중요하다.**

만약 라우트가 10개라면? 어떤 계층이 터졌을 때
"이게 A 라우트 때문인가 B 라우트 때문인가" 를 분리할 수 없다.
변수가 여러 개면 원인을 특정할 수 없다 — 실험의 기본이다.

라우트가 하나면 **"이번에 바뀐 건 방금 내가 만진 계층 하나뿐"** 이 보장된다.

대신 그 하나를 최대한 잔인하게 골랐다.

## 2-3. 대상 라우트가 실제로 하는 일

`POST /reservations` — 티켓 예약. 트랜잭션 안에서 이렇게 돈다.

```sql
BEGIN
  ① SELECT ... FROM reservations WHERE idempotency_key = $1   -- 중복 요청인가?
  ② SELECT ... FROM events WHERE id = $1 FOR UPDATE           -- 재고 행을 잠근다
  ③ UPDATE events SET remaining = remaining - 1               -- 재고 차감
  ④ INSERT INTO reservations ...                              -- 예약 생성
COMMIT
```

DB 왕복이 5번(BEGIN/COMMIT 포함), 그동안 **커넥션 1개를 계속 붙잡는다.**

### 왜 이게 잔인한가 — 세 가지가 한 번에 들어 있다

**① 락 경합.** `SELECT ... FOR UPDATE` 는 그 행에 잠금을 건다.
같은 이벤트를 노리는 모든 요청이 **한 줄로 선다.** 동시성이 1이 된다.

```
요청 A가 행을 잠금 → B, C, D는 A의 COMMIT을 기다린다
```

**② 커넥션 점유.** 왕복 5번 도는 내내 커넥션을 반납하지 않는다.
리틀의 법칙에 따라 이 점유 시간이 곧 처리량 천장이 된다.

**③ 정합성.** 티켓은 초과 판매되면 안 된다.
100석짜리 공연에 101명을 예약시키면 그건 버그가 아니라 사고다.

**그래서 뒤에서 캐시와 큐를 붙일 때 "빠르게" 와 "틀리지 않게" 가 정면으로 부딪힌다.**
이 충돌을 어떻게 풀었는지가 Phase 07~08 이고, 이 프로젝트에서 제일 재미있는 부분이다.

## 2-4. 일하는 규칙 넷

측정 프로젝트는 규칙이 없으면 결과가 전부 자기합리화가 된다.

### ① 한 번에 한 계층만 건드린다

두 개를 같이 바꿔서 좋아지면, 어느 쪽 공인지 영원히 모른다.
그래서 Phase 02 에서 TLS 비용을 재고 나서, Phase 03 에서는 **TLS 를 아예 껐다.**
이미 안 값이니 변수에서 뺀 것이다.

### ② 가설은 실험 전에 쓰고, 틀려도 고치지 않는다

사람은 결과를 보고 나면 "나는 원래 그럴 줄 알았다" 로 기억을 고쳐 쓴다.
(사후 확신 편향)

**Phase 01 의 주 가설은 틀렸다.** 그 틀린 기록이 문서에 그대로 남아 있고,
왜 틀렸는지가 프로젝트 전체의 방향을 정했다.

### ③ 재기 전에 숫자를 예측하지 않는다

"대략 30% 개선될 것" 이라고 써 두면 결과가 그 근처로 보이기 시작한다.
방향(오른다/내린다)까지만 예측하고 배수는 재서 채운다.

### ④ 부하 생성기부터 의심한다

서버가 1,000 RPS 에서 막히는 게 아니라 **k6 가 1,000밖에 못 쏘는 것**일 수 있다.
그래서 매번 `make sanity` 로 DB 를 안 타는 빈 라우트를 먼저 때린다.
**목표의 3~5배가 안 나오면 그날 잰 건 서버가 아니라 노트북이다.**

## Phase 01 · 취약 기준선

### 질문
> 아무것도 튜닝하지 않았을 때 이 서버의 좌표는 어디인가?

여기서 SLO 를 달성할 생각은 없었다. **비교 대상을 만드는 게 목적**이다.
"개선했다" 고 말하려면 개선 전 숫자가 있어야 한다.

### 가설 (측정 전에 씀)

**커넥션 풀(기본 10개)이 앱 CPU 보다 먼저 마를 것이다.**

근거는 리틀의 법칙이었다. DB 왕복 5회짜리 트랜잭션은 커넥션을 오래 붙잡으니,
`천장 = 풀 크기 ÷ 트랜잭션 소요시간` 으로 제한될 거라고 봤다.

### 결과 — 틀렸다

풀이 마르기 전에 **Node 의 단일 JS 스레드 CPU** 가 먼저 1.0 코어에 붙었다.

100~1,200 RPS 구간을 선형 회귀하니 이런 식이 나왔다.

```
CPU 사용량 = 0.068 + 0.000518 × RPS
             ↑고정비용    ↑요청당 비용

→ 요청 하나당 앱 CPU 518µs
→ 천장 = 1.0 코어 ÷ 518µs ≈ 1,930 RPS  (실측 약 2,000)
```

### 왜 그런가 — Node.js 는 코어를 하나만 쓴다

Node 는 **단일 스레드 이벤트 루프**로 돈다.
Fastify 라우팅, Drizzle 쿼리 빌드, pg 프로토콜 파싱, JSON 직렬화가 **전부 한 스레드**에서 돈다.

즉 6코어 머신이어도 Node 프로세스 하나는 **1코어만 쓴다.**
DB 를 기다리는 동안은 다른 요청을 처리할 수 있지만(비동기 I/O),
**CPU 를 쓰는 일은 순서대로 하나씩** 할 수밖에 없다.

그래서 커넥션 풀에 도달하기도 전에 CPU 가 먼저 찼다.

### 이 단계가 남긴 것

**병목은 CPU 다.** 이 한 문장이 다음 세 단계의 방향을 정했다.

```
Phase 02  TLS 도 그 CPU 를 먹는다 → 얼마나?
Phase 03  CPU 가 병목이면 앱을 늘리면 되지 않나?
Phase 04  CPU 자체를 태워서 모델이 맞는지 검증하자
```

## Phase 02 · TLS 핸드쉐이크

### 질문
> HTTPS 는 그 CPU 예산을 얼마나 가져가나?

### 알아야 할 배경 — 핸드쉐이크는 비싸다

HTTPS 연결을 맺을 때 서버는 **개인키로 서명**을 한다. 이건 비대칭키 연산이라 비싸다.
연결이 맺어진 뒤의 실제 데이터 암호화(AES)는 대칭키라 훨씬 싸고,
요즘 CPU 에는 하드웨어 가속까지 있다.

**즉 비싼 건 연결을 맺는 순간뿐이다.**

여기서 **keep-alive** 가 중요해진다. 커넥션 하나를 재사용하면 핸드쉐이크는 처음 한 번뿐이다.
끄면 요청마다 핸드쉐이크가 발생한다.

### 결과

- **keep-alive 켜짐**: HTTP 와 차이가 거의 없음
- **keep-alive 꺼짐**: **천장이 절반으로** 떨어짐

### 해법과 그 논리

TLS 종료를 nginx 로 옮겼다. 그런데 여기서 재미있는 게 있다.

**합계 CPU 는 오히려 늘어난다.** 프록시 홉이 하나 추가되니까.
그런데도 이득이다. 왜?

> **앱은 코어를 하나밖에 못 쓰고, nginx 는 여러 개를 쓴다.**
> 병목 자원이 서로 다르다.

앱의 1코어는 귀하고, nginx 가 쓰는 나머지 5코어는 놀고 있었다.
**전체 자원을 더 쓰더라도 병목 자원을 아끼면 이긴다.**

이게 성능 최적화의 핵심 감각이다 — 총합을 줄이는 게 아니라 **병목을 옮기는 것**.

### 세부 — 프록시 홉 비용을 따로 뺐다

"nginx 평문 통과" 를 별도로 쟀다. 이걸 안 빼면 프록시 홉 비용까지 TLS 탓으로 잡혀
**TLS 비용이 과대평가된다.**

## Phase 03 · 로드밸런서

### 질문
> 앱을 3대로 늘리면 병목은 어디로 옮겨가나?

### 왜 HAProxy 였나

Phase 03 실험의 절반이 **"죽은 백엔드를 언제 알아채는가"** 다.
그런데 **오픈소스 nginx 에는 능동(active) 헬스체크가 없다.**

| 방식 | 동작 |
|---|---|
| 능동 헬스체크 | LB 가 주기적으로 `/healthz` 를 찔러본다. 죽으면 **사용자 요청 오기 전에** 안다 |
| 수동 헬스체크 | 실제 사용자 요청이 실패해야 안다 |

nginx 오픈소스판은 수동만 된다(능동은 상용 nginx Plus 기능).
수동만으로는 "감지까지 몇 초" 를 잴 수가 없다 — **재려면 사용자 요청이 먼저 죽어야 하니까.**

HAProxy 는 오픈소스판에 `check inter 2s fall 3 rise 2` 가 다 들어 있다.

### 결과 — 두 가지가 크게 나왔다

**① 분배 알고리즘: least-conn 대 round-robin — p99 차이 7.4배**

느린 백엔드가 1대 섞였을 때,

```
round-robin  1→2→3→1→2→3 ...  느린 놈한테도 똑같이 보낸다
least-conn   연결이 적은 쪽으로  느린 놈은 연결이 쌓이니 자동으로 피한다
```

round-robin 은 "공평하게" 나누는데, **공평한 게 최선이 아니다.**
아픈 서버한테 계속 일을 주면 그쪽으로 간 요청만 다 죽는다.

**② graceful shutdown(drain) 유무 — p99 차이 45배**

인스턴스를 그냥 죽이면 LB 가 알아챌 때까지(최대 6초) 그쪽으로 간 요청이 전부 실패한다.
drain 은 "이제 새 요청 그만 주세요" 를 먼저 알리고, 처리 중인 것만 끝내고 내려간다.

**배포 방식이 아키텍처만큼 중요하다**는 게 여기서 나온다.
아무리 잘 만들어도 배포할 때마다 p99 가 45배 튀면 소용없다.

## Phase 04 · 앱서버의 물리적 한계

### 질문
> Phase 01 에서 세운 모델이 진짜 맞나?

모델은 이거였다.

```
처리량 천장 = CPU 상한 ÷ 요청당 CPU
```

이걸 검증하려면 **요청당 CPU 를 내가 조절**할 수 있어야 한다.
그래서 라우트에 "일부러 CPU 를 태우는" 코드를 넣었다.

### 결과 — 모델이 맞았다

| 요청당 태운 CPU | 이론값 (1000/X) | 실측 |
|---|---|---|
| 10ms | 100 RPS | **100.20 RPS** |
| 30ms | 33.3 RPS | **34.30 RPS** |

오차 3% 이내. **성능은 예측 가능한 물리다.**

### 발견 ① — 스레드풀로 옮겨도 처리량은 안 는다

"Node 가 단일 스레드라 CPU 작업에 약하다면, 워커 스레드로 보내면 되지 않나?"

해봤다.

```
이벤트 루프 지연:  크게 개선 → 0
처리량:            34.3 → 24.1 RPS   ← 오히려 떨어졌다
```

**왜?** 일을 다른 데로 **보낸** 것이지 **없앤** 게 아니기 때문이다.
CPU 총량은 그대로인데 스레드 간 데이터 전달 비용만 추가됐다.

> 교훈: **CPU 병목은 CPU 를 줄여야 풀린다.**
> 어디서 도느냐를 바꾸는 건 응답성(latency)을 개선하지 처리량(throughput)을 개선하지 않는다.

### 발견 ② — 빨리 거절하는 편이 낫다

**load shedding** 을 넣었다. 서버가 과부하면 **받자마자 503 으로 거절**하는 것이다.

결과가 처음엔 이상해 보인다.

```
실패율:  9.6%  →  68.7%     (7배 악화??)
p50:     21,914ms → 493ms   (44배 개선)
성공 처리량: 그대로
```

**실패율이 7배 늘었는데 이게 개선이다.**

왜냐면 shedding 이 없을 때 그 9.6% 밖의 요청들은 **성공하긴 했는데 21초가 걸렸다.**
21초면 사용자는 이미 떠났다. 그 사람을 위해 서버가 21초 동안 일한 것이다.
그 낭비된 CPU 때문에 뒤에 온 사람들도 다 같이 느려진다.

> **응답하지 않는 것도 실패고, 늦게 응답하는 것도 실패다.**
> 못 할 일은 빨리 거절해서 자원을 지키는 게 전체에 이롭다.

이걸 이해하면 "에러율이 낮으면 좋은 것" 이라는 단순한 생각이 깨진다.

## Phase 05 · DB 커넥션 풀

### 질문
> 앱 CPU 는 이제 수평 확장으로 풀린다. 다음 벽은 DB 인가?

### 알아야 할 배경 — Postgres 는 커넥션 하나가 프로세스 하나

MySQL 은 커넥션당 스레드를 쓰는데, **Postgres 는 커넥션마다 OS 프로세스를 하나 만든다.**

즉 커넥션 100개 = 프로세스 100개. 각자 메모리를 쓰고 컨텍스트 스위칭 대상이 된다.
**커넥션은 공짜가 아니다.**

실측하니 커넥션당 **3.1MB** 가 선형으로 늘었다.

### 이 단계의 진짜 교훈 — 증상과 원인

실험 중에 이런 상황이 나왔다.

```
커넥션 풀이 마른다 (waiting 이 계속 쌓임)
실패율 85.8%
```

**보통 여기서 풀을 키운다.** 그런데 풀이 마르는 건 **증상**이지 원인이 아니다.

원인을 찾으려면 이렇게 물어야 한다.
> **"왜 커넥션이 오래 붙잡혀 있나?"**

찾아보니 **200만 행짜리 순차 스캔 쿼리 하나**가 커넥션 30개를 전부 묶고 있었다.

```sql
SELECT id FROM reservations WHERE event_id = $1 AND user_id = $2
```

`event_id` 는 외래키인데, **Postgres 는 외래키를 만들어도 인덱스를 자동 생성하지 않는다.**
그래서 매번 200만 행을 처음부터 끝까지 훑었다.

### 결과 — 풀은 손도 안 댔다

인덱스 하나를 추가했다.

```
처리량:  7.9배
실패율:  85.8% → 0%
```

> **풀을 키우는 건 대개 증상 완화다. 원인은 그 커넥션을 오래 잡는 쿼리 쪽에 있다.**

그리고 이건 실무에서 제일 흔한 사고 패턴이다 —
개발 DB 에는 데이터가 적어서 멀쩡하다가, 운영에서 행이 쌓이면 터진다.

### 여기서 한 번 틀렸다

처음에 커넥션당 메모리를 재는데 **30MB** 가 나왔다. 너무 컸다.
`VmRSS`(프로세스가 쓰는 물리 메모리)를 프로세스마다 더했는데,
**`VmRSS` 는 공유 메모리를 프로세스마다 중복으로 센다.**

Postgres 프로세스들은 shared_buffers 를 공유하므로 그게 100번 세어진 것이다.
사적 메모리인 `RssAnon` 으로 바꾸니 **3.1MB.** 약 10배 차이였다.

## Phase 06 · DB 프록시 (PgBouncer)

### 질문
> 앱에 이미 커넥션 풀이 있는데 왜 프록시를 또 두나?

### 답 — 앱 풀은 앱마다 따로 놀기 때문

```
앱 1대 × 풀 20 = DB 커넥션 20개
앱 6대 × 풀 20 = DB 커넥션 120개   ← 앱을 늘릴 때마다 곱셈으로 는다
```

앱은 서로를 모른다. 각자 "나는 20개까지만" 이라고 지킬 뿐이다.
**DB 입장에서는 그게 다 합쳐져서 온다.**

### 실험 — 앱을 3대에서 6대로

| | DB 가 받은 커넥션 | 결과 |
|---|---|---|
| 직결 | 상한 98개에 도달 | `too_many_clients` **47건** |
| PgBouncer 경유 | **22개로 고정** | 에러 0 · DB 메모리 53% 절감 |

### 어떻게 120개를 22개로 줄이나 — transaction 모드

PgBouncer 에는 세 가지 모드가 있다.

| 모드 | 커넥션을 언제 반납하나 |
|---|---|
| session | 클라이언트가 연결을 끊을 때 (거의 안 줄어듦) |
| **transaction** | **트랜잭션이 끝날 때마다** |
| statement | 쿼리 하나 끝날 때마다 (트랜잭션 못 씀) |

**transaction 모드가 핵심이다.**

앱이 커넥션을 20개 열어 놓고 있어도, 실제로 트랜잭션을 도는 건 그중 일부다.
나머지는 놀고 있다. 트랜잭션 단위로 빌려주면 **실제 동시 트랜잭션 수만큼만** 있으면 된다.

```
앱이 열어둔 커넥션 120개 (대부분 유휴)
    ↓ PgBouncer
실제로 필요한 DB 커넥션 22개
```

### 대가 — 세션 상태를 못 쓴다

커넥션이 매 트랜잭션마다 다른 앱한테 넘어가므로, **세션에 상태를 남기면 안 된다.**

- 임시 테이블 ✗
- 세션 레벨 advisory lock ✗
- 이름 있는 prepared statement ✗

그래서 코드에서 `pg_advisory_lock`(세션 범위) 을
`pg_advisory_xact_lock`(트랜잭션 범위) 으로 바꿔야 했다.

**"공짜 최적화" 는 없다. 프록시를 넣으면 코드 제약이 따라온다.**

### 서버리스에서 이게 필수인 이유

Lambda 같은 서버리스는 요청이 몰리면 인스턴스가 수백 개로 늘어난다.
각 인스턴스가 자기 커넥션을 열면 **위의 곱셈이 극단적으로 재현된다.**
그래서 AWS 는 RDS Proxy 를 따로 판다. Phase 10 의 전제가 여기서 나온다.

## Phase 07 · 캐시

### 질문
> DB 를 아예 안 치게 만들 수 있나?

### 시작하자마자 막혔다 — 캐시할 게 없었다

`total_seats` 가 1억이라 **아무것도 매진되지 않았다.**
그래서 모든 요청이 "재고 있음 → 쓰기" 였고, **읽기가 없으니 캐시가 무의미했다.**

재고를 희소하게 만드는 `db/reset-scarce.sql` 을 먼저 만들었다.
**매진이 나야 "매진입니다" 라는 읽기 응답이 생기고, 그게 캐시 대상이 된다.**

키 분포도 **Zipf** 로 바꿨다. 균등 분포에서는 모든 이벤트가 골고루 조회돼서 핫키가 안 생긴다.
실제 티켓팅은 인기 공연 몇 개에 트래픽이 몰린다.

> 이건 실험 설계의 교훈이다. **틀린 데이터로 실험하면 틀린 결론이 나온다.**
> 실험 조건을 현실에 맞추는 게 측정보다 먼저다.

### 캐시의 원칙 — 비대칭 오류

여기가 이 프로젝트에서 제일 섬세한 부분이다.

무엇을 캐시할 수 있나?

| 캐시 가능 | 캐시 불가 |
|---|---|
| 이벤트 존재 여부 | `remaining` 의 정확한 값 |
| 메타데이터 | 재고 차감 자체 |
| **매진 여부** | |

그래서 원칙이 이렇게 선다.

> ★ **캐시는 거절을 빠르게 할 뿐, 허용을 보장하지 않는다.**

```
캐시가 "매진" 이라 함    → 즉시 409 거절 (DB 안 감)
캐시가 "재고 있음" 이라 함 → DB 의 원자적 UPDATE 가 최종 판정
```

**틀리는 방향이 비대칭이라 이렇게 자를 수 있다.**

| 캐시가 틀렸을 때 | 결과 |
|---|---|
| 재고 있는데 "매진" 이라 함 | 살 수 있는 사람을 거절 → 나쁘다. TTL 을 짧게 해서 통제 |
| 매진인데 "재고 있음" 이라 함 | DB 가 0행 반환 → 정상 거절 → **무해** |

한쪽 오류만 위험하니 그쪽만 관리하면 된다.
**틀릴 수 있는 걸 인정하고, 틀려도 안전한 방향을 고르는 것** — 이게 캐시 설계다.

### 결과 ① — 로컬 캐시는 인스턴스가 늘수록 손해

```
앱 1 (자기 캐시)     같은 키를 요청 → miss → DB
앱 2 (자기 캐시)     같은 키를 요청 → miss → DB
앱 3 (자기 캐시)     같은 키를 요청 → miss → DB
                     같은 키인데 miss 가 3번
```

```
로컬 캐시 hit ratio   37.6%
Redis(공유) hit ratio 64.5%     ← 26.9%p 차이
```

**앱을 늘리면 로컬 캐시의 효율은 떨어진다.** 확장과 로컬 캐시는 상충한다.

### 결과 ② — Stampede 는 짧은 TTL 때문이 아니다

**Cache stampede** = 캐시가 만료된 순간 그 키를 찾던 모든 요청이 동시에 DB 로 몰리는 것.

통념은 "TTL 이 짧으면 자주 만료되니 위험하다" 다. 재봤다.

```
TTL 1초 + 지터 0     →  스파이크 1.05배 (거의 없음)
FLUSHALL(강제 동시 만료) →  스파이크 3.23배
```

**TTL 이 짧은 건 문제가 아니었다.** 키마다 캐시에 들어간 시각이 다르니
만료 시각도 자연히 흩어진다. 그래서 몰리지 않는다.

**진짜 위험한 건 동기화된 만료다.**

- 배포 직후 (캐시가 통째로 비어 있음)
- 일괄 무효화 (`FLUSHALL`)
- 모든 키를 같은 시각에 넣었을 때

> 대책이 **TTL 지터**(만료 시각을 무작위로 흩기)와 **singleflight**
> (같은 키에 대한 동시 loader 호출을 하나로 합치기)다.
> 다만 원인을 알고 나면 **"지터가 만능이 아니라 동시 만료가 문제"** 라는 게 보인다.

### 결과 ③ — 쓰기 전략은 선택지가 없었다

캐시 쓰기 전략은 셋이 있다.

| 전략 | 방식 |
|---|---|
| **cache-aside** | 앱이 캐시를 읽고, miss 면 DB 에서 읽어 캐시에 채운다 |
| write-through | 앱이 캐시에 쓰면 캐시가 DB 에도 쓴다 |
| write-behind | 캐시에만 쓰고 나중에 DB 에 반영 |

**이 도메인에서는 cache-aside 밖에 안 된다.** 왜?

재고 차감이 **조건부 원자 UPDATE** 이기 때문이다.

```sql
UPDATE events SET remaining = remaining - 1
WHERE id = $1 AND remaining >= 1
```

성공했는지 실패했는지를 **DB 가 정한다.** 캐시에 먼저 쓰고 DB 에 반영하는 방식은
"캐시에는 성공인데 DB 에서는 실패" 를 만들 수 있어서 성립하지 않는다.

**정합성이 중요한 도메인에서는 진실의 원천(source of truth)이 항상 DB 여야 한다.**

### 최종 결과

**DB 접촉 71% 감소.** 매진된 이벤트에 오는 요청이 DB 를 아예 안 친다.

## Phase 08 · 메시지 큐

### 질문
> 쓰기를 큐 뒤로 빼면 스파이크를 흡수할 수 있나?

### 가장 어려운 결정 — 어디까지 동기인가

순진한 방법은 이거다.

```
요청 받음 → 큐에 넣음 → 즉시 202 Accepted → 워커가 나중에 DB 에 반영
```

**티켓팅에서는 이걸 쓸 수 없다.**

매진인데도 202 를 주게 된다. 그리고 나중에
"죄송합니다, 매진되어 취소되었습니다" 를 보내야 한다.
콘서트 티켓에서 이건 사고다.

### 해법 — 판정은 동기, 반영은 비동기

```
① 재고 판정: Redis DECR   (동기)  ← 실패하면 그 자리에서 409
② DB 반영:   큐 → 워커     (비동기) ← 선점 성공분만
```

**왜 Redis `DECR` 인가?**

`DECR` 은 **원자적(atomic)** 이다. 여러 앱이 동시에 호출해도
Redis 가 한 번에 하나씩 처리하고, 각자 다른 결과값을 받는다.

```
재고 100인 상태에서 앱 3대가 동시에 DECR
→ 각각 99, 98, 97 을 받는다. 절대 겹치지 않는다.
```

값이 0 미만이 되면 그 요청은 거절한다.
**초과 판매가 구조적으로 불가능해진다** — 코드로 막는 게 아니라 자료구조가 막는다.

실제로 모든 시나리오에서 `async_inconsistency_total` 이 **0** 이었다.

### 결과 — 큐는 만능이 아니다

| 부하 | 큐 없음 (p99) | 큐 있음 (p99) | |
|---|---|---|---|
| 600 RPS | 95.87ms | **233.56ms** | 2.4배 **나빠짐** |
| 1,500 RPS | 241.05ms | **80.58ms** | 3배 좋아짐 |

**저부하에서는 오히려 느려진다.** 당연하다.
DB 트랜잭션 1회(1.9ms)를 **Redis 왕복 + 브로커 왕복 2회**로 바꾼 셈이니까.

> **큐는 빠르게 만드는 도구가 아니라 밀린 일을 미루는 도구다.**
> 평소에 여유가 있으면 손해고, 순간적으로 넘칠 때만 이득이다.

### 스파이크 흡수 — 이게 큐의 본래 목적

3,000 RPS 스파이크를 걸었다.

```
큐 depth 가 1,833까지 쌓였다가 8초 만에 빠졌다
```

큐가 없으면 이 1,833건은 DB 를 동시에 때려서 전부 타임아웃 났을 것이다.
큐가 있으면 **DB 는 자기 속도대로 처리하고, 넘치는 건 큐가 들고 있는다.**

이걸 **버퍼링** 또는 **부하 평탄화(load leveling)** 라고 한다.

### 진짜 대가는 성능이 아니라 약속

```
201 Created   "예약됐습니다"    ← 확정
202 Accepted  "접수됐습니다"    ← 확정 아님
```

**응답의 의미가 바뀐다.** 사용자에게 하는 말과 UI 를 같이 바꿔야 한다.
"예약 완료" 화면을 띄우면 안 되고, "처리 중" 을 보여주고 나중에 확정을 알려야 한다.

**이게 MQ 도입의 진짜 비용이다** — 인프라 복잡도가 아니라 제품 약속의 변경.

### 멱등성 — 왜 중복이 오는가

메시지 큐는 대개 **at-least-once**(최소 한 번) 를 보장한다.
"정확히 한 번(exactly-once)" 은 분산 시스템에서 사실상 불가능하다.

왜 중복이 생기나?

```
워커가 DB 에 반영 완료 → ack 를 보내려는 순간 죽음
→ 브로커는 ack 를 못 받았으므로 "처리 안 됐구나" 하고 다시 보냄
→ 같은 메시지가 두 번 처리됨 → 티켓이 2장 발급
```

**해결: 멱등성(idempotency).** 같은 요청을 여러 번 처리해도 결과가 한 번과 같게 만든다.

이 프로젝트는 **UNIQUE 제약**으로 잡았다.

```sql
reservations.idempotency_key UNIQUE
```

두 번째 INSERT 는 `23505`(unique violation) 로 튕긴다.
**그걸 에러가 아니라 "이미 처리됨 = 성공" 으로 간주하고 ack** 한다.

> DB 제약조건을 방어선으로 쓰는 게 핵심이다.
> 애플리케이션 코드로 "이미 있나 확인 후 삽입" 하면
> 확인과 삽입 사이에 다른 요청이 끼어들 수 있다(race condition).

### 재시도와 DLQ

실패한 메시지를 어떻게 하나?

**즉시 재시도는 나쁘다.** DB 가 죽어서 실패한 건데 바로 다시 때리면 더 죽는다.

그래서 **지연 재시도 큐**를 만들었다.

```
실패 → retry 큐에 넣는다 (TTL 2초)
     → 2초 뒤 만료되면 dead-letter 설정에 의해 본 큐로 되돌아온다
     → 다시 처리 시도
     → N번 넘게 실패하면 DLQ(Dead Letter Queue)로 격리
```

**DLQ 는 "포기한 메시지 보관함"** 이다. 버리지 않고 모아 두면
나중에 원인을 조사하고 수동으로 재처리할 수 있다.

> 여기서 실제로 버그가 있었다. 4부에서 다룬다.

### 용량 산정 — 리틀의 법칙으로 계산하고 실측과 대조

**앞 단계에서 잰 값만** 넣어서 "1,000 RPS 를 내려면 각 계층이 얼마나 필요한가" 를 계산했다.

| 계층 | 계산 | 필요 | 실제 구성 | 여유 |
|---|---|---|---|---|
| 앱 CPU | `1000 × 518µs` | 0.52 코어 | 6.0 | 11.5배 |
| DB 커넥션 | `(1000×0.288) × 1.9ms` | 0.55개 | 22 | 40배 |

| DB 메모리 | `10MB + 3.1MB × 22` | 78MB | **79MB** | 1.01배 |

`0.288` 은 실제로 DB 를 치는 비율이다(나머지는 캐시에서 끊긴다).

**DB 메모리 회귀식이 Phase 05 · 06 · 09 세 번에 걸쳐 오차 1~2% 로 맞았다.**
이게 중요한 이유 — **한 번 맞는 건 우연일 수 있지만 세 번 맞으면 모델이다.**

### 시나리오 3종

| 시나리오 | 무엇을 보나 | 유지구간 RPS | p99 | 진짜 실패 |
|---|---|---|---|---|
| **soak** 1,000 RPS × 10분 | 오래 버티나 (누수·저하) | 1,005.0 | **105.0ms** | 300 (전부 시작 15초에) |
| **spike** 0 → 2,000 RPS | 급증을 견디나 | 1,728.9 | **182.0ms** | **0** |
| **fault** 앱 1대 강제 종료 | 장애 시 살아남나 | 997.2 | **49.5ms** | **2** |

**앱 1대를 죽였는데 18.3만 요청 중 실패 2건.**
HAProxy 헬스체크가 2초 안에 감지해서 나머지 2대로 넘겼다.

### 여기서 제일 중요한 것 — "실패" 를 어떻게 정의했나

**409 Conflict(매진) 를 실패로 세지 않았다.**

```
진짜 실패 = 무응답 + 502 + 503 + 504
정상 거절 = 409 (매진)
```

**왜?** 409 를 실패로 세면 **티켓이 잘 팔릴수록 실패율이 올라간다.**
매진은 시스템이 정상 동작한 결과지 장애가 아니다.

> 이건 SLI(측정 지표) 설계의 핵심이다.
> **"무엇을 실패로 볼 것인가" 를 정하지 않으면 그 뒤 숫자는 아무 의미가 없다.**

이 정의를 [`docs/slo.md`](slo.md) 에 못 박았다.

### 알람 — 다중 윈도 소진율

"에러율 1% 넘으면 알람" 같은 단일 임계값은 실패한다.

- 짧은 스파이크에도 울린다 → 사람들이 알람을 무시하기 시작한다
- 임계값을 올리면 진짜 장애를 놓친다

그래서 **burn-rate**(오차 예산 소진율) 방식을 썼다.

```
짧은 윈도(5분)와 긴 윈도(1시간)를 같이 본다
둘 다 빠르게 소진 중일 때만 긴급 알람
```

순간적인 튐은 무시하고 지속적인 악화만 잡는다.

# 4부 · 막혔던 순간들

여기가 실제로 시간을 태운 부분이다. 그리고 **면접에서 제일 잘 먹히는 이야기**이기도 하다.

## 4-1. 관측 도구가 측정을 두 번 죽였다

### 무슨 일이

Prometheus 가 메모리 부족으로 죽었다. 두 번.

- **Phase 02** — cAdvisor 가 컨테이너 라벨을 지표에 붙여서
- **Phase 07** — k6 가 **요청 URL 을 라벨로** 붙여서

Phase 07 때는 **실험 12개가 통째로 날아갔다.** 다시 돌려야 했다.

### 왜 그렇게 되나 — 카디널리티

Prometheus 는 **라벨 조합 하나당 시계열 하나**를 만든다.

```
http_requests_total{method="POST", status="201"}          → 시계열 1개
http_requests_total{method="POST", status="409"}          → 시계열 1개
```

여기까지는 괜찮다. 그런데 URL 을 라벨에 넣으면?

```
http_requests_total{url="/reservations?event=1&user=8823"}
http_requests_total{url="/reservations?event=1&user=8824"}
http_requests_total{url="/reservations?event=2&user=1102"}
...
```

**요청마다 다른 시계열이 생긴다.** 실측 **154만 개**였다.
각 시계열이 메모리를 먹으니 Prometheus 가 죽는다.

### 해결

```js
tags: { name: 'reservation' }        // URL 대신 고정 이름을 붙인다
systemTags: [...]                    // 여기서 'url' 을 제거
```

**154만 → 2,901 개.** 500배 줄었다.

### 교훈

> **모니터링은 공짜가 아니다. 재려는 대상보다 재는 도구가 먼저 죽을 수 있다.**

라벨에 **요청마다 달라지는 값**(URL, 사용자 ID, 타임스탬프, 주문번호)을 넣으면 안 된다.
그건 로그에 넣을 것이지 지표에 넣을 것이 아니다.

## 4-2. 평균을 처리량으로 읽어서 틀린 결론을 냈다

### 무슨 일이

Phase 08 에서 "1,189 RPS 에서 천장에 닿았다" 고 썼다. **틀렸다.**

k6 가 출력한 전체 평균 RPS 를 읽었는데, 그 시나리오는 이렇게 생겼다.

```
워밍업 20초 @ 100 RPS
유지  90초 @ 1,500 RPS
```

전체 평균 = `(100×20 + 1500×90) ÷ 115 = 1,191 RPS`

**워밍업 구간이 평균을 끌어내린 것이지 천장에 닿은 게 아니다.**
실제로 CPU 는 6코어 중 2.4코어만 쓰고 있었다. 한참 여유가 있었다.

### 어떻게 알았나

Phase 09 에서 계층별 여유를 계산하다가 숫자가 안 맞았다.
"2.4코어만 쓰는데 왜 천장이라고 했지?" 에서 시작해 되짚었다.

### 처리

**원문을 지우지 않았다.** 취소선을 긋고 `[정정 · Phase 09]` 블록을 세 군데 달았다.
틀린 기록을 지우면 왜 틀렸는지가 사라진다.

### 교훈

> **유지 구간만 잘라서 봐야 한다.** 워밍업·램프업이 섞인 평균은 처리량이 아니다.

## 4-3. 맥이 절전에 들어가서 실험이 1시간 43분 멈췄다

### 무슨 일이

실험을 돌려놓고 자리를 비웠는데, 맥이 절전에 들어갔다 깨어난 뒤
**스크립트가 무한 대기에 빠졌다.** 1시간 43분 뒤에야 발견했다.

원인은 `docker compose exec`. 절전에서 깨면 VM 과의 연결이 끊긴 상태인데
**타임아웃이 없어서 영원히 기다린다.**

### 첫 시도는 불완전했다

시작 대기 부분만 고쳤는데, **드레인 루프와 샘플러 루프에 같은 패턴이 남아 있었다.**
그래서 두 번째로 1시간 4분을 또 날렸다.

### 해결

`docker compose exec` 을 아예 안 쓰기로 했다.

```bash
# 포트가 열렸는지 확인 — 타임아웃 있음
(exec 3<>/dev/tcp/127.0.0.1/"$port") 2>/dev/null

# HTTP 조회 — 타임아웃 있음
curl --max-time 3 -u lts:lts 'http://localhost:15672/api/queues/%2F'
```

### 교훈

> **모든 대기에는 상한이 있어야 한다.**
> 그리고 **같은 패턴이 다른 데도 있는지 반드시 전체를 훑어야 한다.**
> 한 군데만 고치면 다음번에 같은 자리에서 또 막힌다.

## 4-4. 실패율 100% 라고 나왔는데 사실은 정상이었다

### 무슨 일이

Phase 08 에서 비동기 경로를 붙이고 나니 k6 가 **실패율 100%** 를 보고했다.
그런데 DB 를 보니 워커가 **예약 20,323건을 정상 생성**하고 있었다.

### 원인

k6 의 응답 검증 설정이 이랬다.

```js
expectedStatuses(200, 201)
```

그런데 비동기 경로는 **202 Accepted** 를 반환한다.
k6 는 202 를 "예상하지 못한 상태코드 = 실패" 로 셌다.

### 교훈

> **새 상태코드를 도입하면 부하 스크립트도 같이 고쳐야 한다.**
> 그리고 **도구가 실패라고 하면 진짜 실패인지 먼저 확인해야 한다.**
> 이걸 확인 안 했으면 "비동기가 다 망가졌다" 는 잘못된 결론을 냈을 것이다.

## 4-5. 워커 재시도가 한 번도 안 됐다

### 무슨 일이

재시도 로직을 만들어 놨는데, 실제로는 **실패한 메시지가 전부 바로 DLQ 로 갔다.**

코드를 보니 이랬다.

```js
if (attempt > MAX_RETRY) {
  ch.nack(msg, false, false);   // DLQ 로 보냄
} else {
  ch.nack(msg, false, false);   // ← 재시도하려던 건데 똑같다!
}
```

`nack(msg, false, false)` 의 마지막 인자가 `requeue` 인데 `false` 다.
**requeue=false 는 "다시 큐에 넣지 말고 dead-letter 로 보내라" 는 뜻이다.**
두 분기가 완전히 같은 동작을 하고 있었다.

### 왜 그냥 requeue=true 로 안 했나

`requeue=true` 로 하면 **즉시** 큐 맨 앞으로 돌아간다.
DB 가 죽어서 실패한 건데 바로 다시 때리면 무한 루프에 빠진다.

### 해결 — 지연 재시도 큐

```js
// TTL 이 걸린 별도 큐. 만료되면 본 큐로 되돌아간다.
assertQueue(RETRY_Q, {
  arguments: {
    'x-message-ttl': 2000,              // 2초 뒤 만료
    'x-dead-letter-exchange': '',
    'x-dead-letter-routing-key': QUEUE, // 만료되면 본 큐로
  },
});

// 실패했을 때
scheduleRetry(ch, msg, attempt);  // retry 큐로 복사
ch.ack(msg);                      // 원본은 ack — 안 하면 prefetch 를 잡아먹는다
```

RabbitMQ 의 TTL + dead-letter 조합을 **타이머처럼** 쓴 것이다.
검증하니 메시지 2건이 실제로 회복됐다.

### 교훈

> **로직을 짰다고 동작하는 게 아니다.** 실패를 일부러 만들어서 재시도가 도는지 봐야 한다.
> 그리고 라이브러리 인자의 의미를 정확히 알아야 한다 —
> `nack(requeue=false)` 는 "버려라" 지 "다시 해라" 가 아니다.

## 4-6. 커넥션당 메모리가 10배 부풀려 나왔다

앞서 Phase 05 에서 다뤘다. `VmRSS` 는 공유 메모리를 프로세스마다 중복으로 센다.
사적 메모리는 `RssAnon` 이다. 30MB → 3.1MB.

> **지표를 만들 때는 그 지표가 정확히 뭘 세는지 알아야 한다.**

# 5부 · 남에게 설명하기

## 5-1. 3분 버전

> 백엔드 성능 이야기를 전부 남의 글로만 알고 있었습니다.
> "캐시를 써라, 큐로 비동기 처리해라" 같은 조언은 많은데 **언제 그게 맞고 언제 틀린지**는
> 안 나와 있더라고요. 그래서 직접 재보기로 했습니다.
>
> 티켓 예약 API 라우트를 **하나만** 만들었습니다. 여러 개 두면 어디가 터졌을 때
> 원인을 분리할 수 없으니까요. 대신 그 하나를 잔인하게 골랐습니다 —
> 트랜잭션 안에서 DB 를 5번 왕복하고, `SELECT FOR UPDATE` 로 같은 행에 모든 요청이 줄을 서고,
> 티켓이라 초과 판매가 나면 안 됩니다.
>
> 그 앞뒤 계층을 10단계에 걸쳐 하나씩 터뜨렸습니다. 로드밸런서, 앱 CPU, 커넥션 풀,
> DB 프록시, 캐시, 큐 순서로요. 규칙은 네 개였습니다 —
> **한 번에 한 계층만 바꾸고, 가설은 실험 전에 쓰고 틀려도 안 고치고,
> 재기 전에 숫자를 예측하지 않고, 부하 생성기부터 의심한다.**
>
> 결과는 목표였던 1,000 RPS · p99 200ms · 에러율 0.1% 를
> **1,005 RPS · 105ms · 0.05%** 로 넘겼습니다.
> 앱 1대를 강제로 죽인 상태에서도 18.3만 요청 중 실패가 2건이었고요.
>
> 근데 결과보다 재밌었던 건 **통념이 깨진 지점들**이었습니다.
> 큐로 빼면 빨라진다고 알고 있었는데 저부하에서는 오히려 2.4배 느려졌고,
> 캐시 stampede 는 TTL 이 짧아서 생긴다고 알고 있었는데 아니었고,
> 풀이 마를 때 풀을 키우는 건 대개 틀린 처방이었습니다.

## 5-2. 하나만 고른다면 — Phase 05

기술 나열이 아니라 **문제 해결 방식**이 드러나서 가장 설명하기 좋다.

> 커넥션 풀이 마르고 실패율이 85.8% 까지 올라갔습니다.
> 보통 여기서 풀을 키우는데, **풀이 마르는 건 증상이지 원인이 아니라고** 봤습니다.
> 원인을 찾으려면 "왜 커넥션이 오래 붙잡혀 있나" 를 물어야 하니까요.
>
> 찾아보니 200만 행짜리 순차 스캔 쿼리 하나가 커넥션 30개를 전부 묶고 있었습니다.
> `event_id` 가 외래키인데 Postgres 는 외래키에 인덱스를 자동 생성하지 않거든요.
>
> **풀은 손도 안 대고 인덱스 하나를 추가하니 처리량이 7.9배, 실패율이 0% 가 됐습니다.**

## 5-3. 예상 질문과 답

**Q. 왜 라우트가 하나뿐인가요?**
> 변수를 하나로 묶기 위해서입니다. 라우트가 여러 개면 계층이 터졌을 때
> 어느 라우트 탓인지 분리가 안 됩니다. 하나면 "이번에 바뀐 건 방금 만진 계층뿐" 이 보장됩니다.

**Q. k6 를 고른 이유가 있나요?**
> open model 을 지원해서입니다. VU 기반(closed model)은 서버가 느려지면 부하도 같이 줄어서
> **망가진 서버가 실제보다 좋아 보입니다.** 실제 트래픽은 서버 사정을 봐주지 않으니까
> 도착률을 고정하는 방식이 맞습니다.

**Q. 왜 p99 를 봤나요?**
> 평균은 소수의 재앙을 다수의 정상으로 덮습니다.
> 990건이 20ms, 10건이 10초여도 평균은 120ms 로 멀쩡해 보입니다.
> p99 를 보는 건 가장 느린 1% 의 경험을 버리지 않겠다는 뜻입니다.

**Q. 실패율이 68% 로 올랐는데 개선이라는 게 무슨 말인가요?**
> load shedding 얘기입니다. 그전에는 성공하긴 했는데 p50 이 21초였습니다.
> 21초면 사용자는 이미 떠났고, 그 사람을 위해 서버가 21초 동안 일한 겁니다.
> 빨리 거절하니 p50 이 493ms 가 됐고 **성공 처리량은 그대로**였습니다.
> **못 할 일을 빨리 포기해서 자원을 지킨 거죠.**

**Q. 캐시로 재고를 관리하면 초과 판매가 나지 않나요?**
> 그래서 캐시는 **거절만** 빠르게 하고 **허용은 보장하지 않게** 설계했습니다.
> 캐시가 "매진" 이라 하면 즉시 거절하고, "재고 있음" 이라 하면 DB 의 원자적 UPDATE 가
> 최종 판정합니다. 틀리는 방향이 비대칭이라 이렇게 자를 수 있습니다 —
> 매진인데 있다고 하면 DB 가 걸러주니 무해하고,
> 있는데 매진이라 하면 손해지만 TTL 로 통제됩니다.

**Q. 비동기로 바꾸면 초과 판매 위험이 커지지 않나요?**
> 그래서 **판정은 동기로, 반영만 비동기로** 잘랐습니다.
> 재고 선점은 Redis `DECR` 로 동기 처리합니다. `DECR` 이 원자적이라
> 여러 앱이 동시에 불러도 각자 다른 값을 받습니다. 초과 판매가 구조적으로 불가능해요.
> 선점에 성공한 것만 큐로 보내니, 큐에 있는 건 이미 자리가 확보된 것입니다.
> 전 시나리오에서 정합성 위반 0건이었습니다.

**Q. 큐를 넣으면 항상 좋아지나요?**
> 아닙니다. 저부하 600 RPS 에서는 p99 가 95.87 → 233.56ms 로 **나빠졌습니다.**
> DB 트랜잭션 1회(1.9ms)를 Redis + 브로커 왕복 2회로 바꾼 셈이니까요.
> 고부하 1,500 RPS 에서 3배 좋아졌습니다.
> **큐는 빠르게 하는 도구가 아니라 밀린 일을 미루는 도구**라서, 넘칠 때만 이득입니다.

**Q. 제일 고생한 부분은?**
> 관측 도구가 측정을 두 번 죽인 겁니다.
> k6 가 요청 URL 을 지표 라벨로 붙여서 시계열이 154만 개가 됐고 Prometheus 가 OOM 으로 죽었습니다.
> 실험 12개가 통째로 날아갔어요. URL 을 라벨에서 빼니 2,901개가 됐습니다.
> **모니터링 자체가 부하라는 걸 몸으로 배웠습니다.**

**Q. 아쉬운 점은?**
> 세 가지입니다. 메모리 누수는 10분으로는 워밍업 잔여와 구분이 안 돼서 **판정 보류**로 남겼고,
> 진짜 처리량 천장은 안 재봤습니다 — 1,500 RPS 를 요청했고 그만큼 나왔을 뿐
> CPU 는 6코어 중 2.4코어만 썼거든요.
> 그리고 전부 노트북 VM 한 대에서 재서 네트워크 지연이 사실상 0 입니다.
> RTT 가 있는 환경에서는 결론이 달라질 항목이 있습니다.

**Q. 왜 Kafka 가 아니라 RabbitMQ 인가요?**
> Kafka 는 순서와 대용량 로그에 최적화돼 있는데, 여기서 필요했던 건
> **지연 재시도와 DLQ, 실시간 랙 관찰**이었습니다.
> 순서는 애초에 필요 없었어요 — 재고 차감은 `remaining - 1` 이라 교환법칙이 성립하고,
> 정합성은 순서가 아니라 Redis DECR 과 UNIQUE 제약으로 지킵니다.
> 필요 없는 보장에 운영 복잡도를 낼 이유가 없었습니다.

## 5-4. 절대 하면 안 되는 답

**모르는 걸 아는 척하지 않는 게 제일 중요하다.** 이 프로젝트는 오히려
"안 재본 건 모른다" 를 문서에 명시한 게 강점이다.

> ✗ "1,000 RPS 가 이 시스템의 한계입니다"
> ○ "1,000 RPS 를 목표로 잡고 달성했습니다. **진짜 천장은 안 재봤습니다** —
>    CPU 가 6코어 중 2.4코어만 쓰고 있었으니 여유가 있었을 겁니다."

> ✗ "메모리 누수는 없습니다"
> ○ "10분 soak 에서 힙이 분당 0.64MB 씩 늘었는데, **워밍업 잔여인지 누수인지
>    10분으로는 구분이 안 됩니다.** 1시간 이상 돌려봐야 판정할 수 있습니다."
