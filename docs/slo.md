# SLO / SLI 정의와 알람 임계치

Phase 09 산출물. 이 문서는 **운영에 그대로 쓸 수 있는 형태**를 목표로 한다.

---

## 1. SLI — 무엇을 재는가

SLI 는 "좋은 이벤트 ÷ 전체 이벤트" 로 정의한다. 비율로 정의해야
트래픽이 변해도 같은 기준으로 읽을 수 있다.

| SLI | 정의 | 측정 위치 | PromQL |
|---|---|---|---|
| **가용성** | 2xx·409 응답 ÷ 전체 응답 | 앱 | `sum(rate(http_request_duration_seconds_count{status=~"2..\|409"}[5m])) / sum(rate(http_request_duration_seconds_count[5m]))` |
| **지연** | p99 응답시간 | 앱 | `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))` |
| **처리량** | 초당 성공 응답 | 앱 | `sum(rate(http_request_duration_seconds_count{status=~"2.."}[1m]))` |
| **정합성** | 202 후 DB 반영 실패 건수 | 워커 | `sum(increase(async_inconsistency_total[5m]))` |
| **큐 지연** | 발행→처리 p99 | 워커 | `histogram_quantile(0.99, sum by (le) (rate(mq_e2e_latency_seconds_bucket[5m])))` |

### 왜 409 를 "좋은 이벤트" 에 넣는가

**409 SOLD_OUT 은 정상 동작이다.** 매진된 티켓을 못 판 것이지 시스템이 실패한 게 아니다.
이걸 실패로 세면 티켓이 잘 팔릴수록 SLI 가 나빠지는 이상한 지표가 된다.

Phase 07~08 에서 실제로 이 문제를 겪었다 — k6 가 409 를 실패로 세서
실패율이 63% 로 보였지만 무응답·502·503 은 0건이었다.
**"실패율" 이 아니라 "진짜 실패" 를 따로 세야 한다.**

## 2. SLO — 목표

| SLO | 목표 | 측정 창 | 근거 |
|---|---|---|---|
| 가용성 | **≥ 99.9%** | 28일 롤링 | 프로젝트 초기 목표(에러율 < 0.1%) |
| 지연 | **p99 < 200ms** | 28일 롤링 | 프로젝트 초기 목표 |
| 처리량 | **≥ 1,000 RPS 지속** | — | 프로젝트 초기 목표 |
| 정합성 | **202 후 실패 = 0** | 28일 | 돈이 걸린 경로다. 비율이 아니라 절대 0 이어야 한다 |

### 에러 예산

가용성 99.9% → **28일에 40분 19초**.

```
28일 = 40,320분
허용 다운타임 = 40,320 × 0.001 = 40.3분
```

**에러 예산 소진 속도(burn rate)로 알람을 건다.** 절대값보다 소진 속도가
"지금 조치가 필요한가" 를 더 잘 말해준다.

## 3. 알람 임계치

### 다중 창(multi-window) burn rate

단일 임계치는 두 가지로 실패한다 — 짧은 창만 보면 잡음에 울리고,
긴 창만 보면 큰 사고를 늦게 잡는다. **두 창을 AND 로 묶는다.**

| 심각도 | burn rate | 짧은 창 | 긴 창 | 소진 시점 | 대응 |
|---|--:|---|---|---|---|
| **P1 (긴급)** | 14.4× | 5분 | 1시간 | 2일 | 즉시 호출 |
| **P2 (높음)** | 6× | 30분 | 6시간 | 5일 | 근무시간 내 대응 |
| **P3 (낮음)** | 3× | 2시간 | 1일 | 10일 | 티켓 생성 |

```promql
# P1 예시 — 5분과 1시간이 동시에 14.4배를 넘을 때만 울린다
(
  (1 - (sum(rate(http_request_duration_seconds_count{status=~"2..|409"}[5m]))
      / sum(rate(http_request_duration_seconds_count[5m])))) > 14.4 * 0.001
and
  (1 - (sum(rate(http_request_duration_seconds_count{status=~"2..|409"}[1h]))
      / sum(rate(http_request_duration_seconds_count[1h])))) > 14.4 * 0.001
)
```

### 계층별 조기 경보

SLO 위반은 **결과**다. 그 전에 울려야 할 것들을 계층별로 둔다.
임계치는 **이 프로젝트에서 실측한 값** 기준으로 잡았다.

| 계층 | 지표 | 경고 | 위험 | 실측 근거 |
|---|---|--:|--:|---|
| 앱 | 이벤트 루프 지연 | > 50ms | > 200ms | Phase 04: 정상 0~1ms, CPU 포화 시 800ms |
| 앱 | in-flight 요청 수 | > 200 | > 500 | Phase 04: 정상 1~4, 큐 폭발 시 1,352 |
| 앱 | 힙 증가 기울기 | > 1MB/분 | > 5MB/분 | Phase 09 soak 결과 참고 |
| LB | 백엔드 DOWN 수 | ≥ 1 | ≥ 2 | Phase 03: 3대 중 1대 죽으면 나머지가 감당 |
| DB | 커넥션 수 | > 60 | > 85 | Phase 05: max_connections 100, 98에서 샘플러도 접속 불가 |
| DB | `idle in transaction` | > 5 | > 20 | Phase 05: 정상 0~3, 락 경합 시 29 |
| DB | 락 대기 | > 5 | > 20 | Phase 05: 정상 0, 경합 시 29 |
| 풀 | 획득 대기 p99 | > 50ms | > 500ms | Phase 05: 정상 1ms, 기아 시 723ms |
| 풀 | 획득 실패 | > 0 | > 10/분 | Phase 05: `too_many_clients` 35건이 장애 신호였다 |
| 캐시 | hit ratio | < 60% | < 30% | Phase 07: Redis+Zipf 81.5%, 균등 64.5% |
| 캐시 | Redis 오류 | > 0 | > 100/분 | Phase 07: Redis 죽어도 서비스는 유지되나 DB 부하가 는다 |
| 큐 | depth | > 500 | > 5,000 | Phase 08: 정상 1~10, 3000 RPS 스파이크에서 1,833 |
| 큐 | E2E 지연 p99 | > 5s | > 30s | Phase 08: 정상 0.08s, 스파이크 시 4.89s |
| 큐 | DLQ 메시지 | > 0 | > 10 | Phase 08: 전 실험 0건. 0 이 아니면 무조건 조사 |
| 워커 | 처리 실패 | > 0 | > 10/분 | Phase 08: `duplicate` 는 정상이므로 제외할 것 |

### 알람을 걸지 **않을** 것

- **409 비율** — 매진은 정상이다. 이걸로 알람을 걸면 흥행할수록 알람이 온다.
- **`duplicate` 카운터** — at-least-once 의 정상 동작이다.
  Phase 08 에서 2,796건이 나왔지만 전부 UNIQUE 가 정상 처리했다.
- **CPU 사용률 단독** — Phase 04 에서 CPU 0.24 인데 처리를 못 한 경우가 있었다(GC 때문).
  CPU 는 원인 조사용이지 알람 조건이 아니다.

## 4. 대시보드 구성 제안

**한 화면에 이 순서로 둔다.** 위에서 아래로 "증상 → 원인" 이 되도록.

```
1행  SLI 3종      가용성 / p99 / 처리량        <- 지금 SLO 를 만족하는가
2행  에러 분해    409 / 503 / 504 / 무응답     <- 실패가 무슨 종류인가
3행  계층별 큐    앱 in-flight / 풀 waiting / MQ depth  <- 어디에 쌓이는가
4행  자원         앱 루프지연 / DB 커넥션 / 캐시 hit    <- 왜 쌓이는가
```

Phase 04~08 에서 반복해서 확인한 것 — **"어디에 쌓이는가" 를 보면 원인이 거의 좁혀진다.**
앱 in-flight 가 크면 앱 CPU, 풀 waiting 이 크면 커넥션, MQ depth 가 크면 워커다.
